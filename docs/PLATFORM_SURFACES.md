# POD AI Studio 三端边界说明

> 目的：明确区分当前项目中的三个前台/后台系统，避免文档、需求、接口、测试范围混淆。
> 这是“先认清系统边界，再看具体文档”的入口文档。

## 1. 当前系统不是一个站，而是多产品面分工

我们现在已经明确，平台目标里至少有 3 个独立产品面：

1. **管理端（中台）**
2. **测评端**
3. **客户端**

这三者虽然共用同一个后端能力平台，但**职责完全不同**。

当前仓库实际维护范围需要单独说明：

- 已有代码：管理端、测评端、backend、image-ops、vendor-api-ops。
- 暂无代码：客户端。`docs/client/` 只保留历史方案和测试包，不代表当前开发主线。

---

## 2. 管理端（中台）

### 定位

管理端是内部运营与技术管理后台。
它不是给普通业务用户直接创作内容用的，而是负责“配置、管理、测试、监控”。

### 主要职责

- 执行节点管理
- 能力管理
- 工作流管理
- LoRA / 模型 / 版本管理
- 能力测试
- 调度监控
- API Key 管理

### 对应代码

- 前端：`podi-admin-web/`
- 主要页面：`podi-admin-web/src/pages/IntegrationDashboard.tsx`

### 对应文档目录

- `docs/admin/`
- `docs/comfyui/`
- `docs/coze/`
- `docs/api/modules/admin-core.md`
- `docs/api/modules/comfyui-admin.md`

### 一句话理解

**管理端负责“配系统、管能力、看状态”。**

---

## 3. 测评端

### 定位

测评端是内部评测、批量验证、回归测试平台。
它不是正式客户前台，而是用于验证工作流、能力效果和批量结果的一套工具。

### 主要职责

- 工作流评测
- 批量跑图
- LoRA 批测
- 结果标注 / 对比
- 回归测试

### 对应代码

- 前端：`podi-eval-web/`

### 对应文档目录

- `docs/eval/`
- `docs/testing/`
- `docs/ABILITY_EVALUATION.md`
- `docs/api/modules/eval.md`

### 一句话理解

**测评端负责“做内部验证、回归和效果对照”。**

---

## 4. 客户端

### 定位

客户端是对外的正式业务前台。
它是给设计师、运营、业务同学使用的“产品化界面”，第一阶段目标是对齐 `Style3D` 这类竞品的工作台体验；长期目标是成为专业设计生产平台的正式前台。

### 主要职责

- 工作室首页
- AI研发设计
- AI视觉商拍
- AI工具箱
- 任务中心
- 我的素材
- 积分 / 充值 / 账单

### 对应代码

- 当前仓库暂无客户端前端代码目录。
- 历史文档中出现的 `podi-client-web/`、`podi-client-v2/`、`podi-design-web-dev/` 均只作为历史引用。

### 对应文档目录

- `docs/client/`

### 一句话理解

**客户端负责“把能力、方法论和流程组织成业务用户可直接使用的工作台”。**

---

## 5. 三端关系

三端关系不是平级重复，而是上下游分工：

```text
管理端（中台）
  -> 配执行节点 / 能力 / 工作流 / LoRA / 监控

测评端
  -> 验证能力效果 / 批量回归 / 内部评测

客户端
  -> 给业务用户实际使用，消费中台能力
```

也就是说：

- 管理端 = 配置和管理
- 测评端 = 内部测试和验证
- 客户端 = 对外正式使用

补充一条当前阶段原则：

- 管理端和测评端是现行代码主线。
- 客户端是后续产品面，不应拿历史客户端文档直接指导当前中台开发。
- 对话式工作流助手是后续增强层，不是当前客户端的主入口

## 7. 当前最容易混淆的点

### 容易混淆 1：客户端 != 测评端

测评端是内部工具，客户端是正式产品。
不要把测评端页面逻辑当成客户端需求。

### 容易混淆 2：管理端 != 客户端

管理端里有很多技术概念：

- Executor
- Workflow
- Binding
- LoRA

这些不应该直接暴露到客户端。

### 容易混淆 3：三端共用后端，但不是一个体验层

后端共用，不代表前端也该共用交互和页面结构。
三端的 UI、用户逻辑、信息层次都不同。
