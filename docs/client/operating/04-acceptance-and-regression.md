# 04. 验收与回归机制

最后更新：2026-06-02

## 1. 验收原则

客户端第一阶段验收不以“页面是否漂亮”为主，而以用户是否能完成生产闭环为主。

每次交付必须回答：

- 用户能否一眼知道下一步。
- 用户能否提交真实能力。
- 用户能否看到状态、runId 和结果。
- 用户能否处理失败。
- 用户能否保存或继续使用结果。
- 用户能否知道消耗和余额影响。

## 2. 基础回归命令

有客户端代码后，每轮至少运行：

```bash
npm run lint
npm run build
```

如果有 UI 测试：

```bash
npm run test:ui
```

如果本轮涉及后端 business API：

```bash
python -m pytest backend/tests -q
```

实际命令以新客户端目录和仓库配置为准。

## 3. 浏览器走查页面

第一阶段固定走查：

| 路由 | 检查重点 |
| --- | --- |
| `/workbench` | 是否直接看到生产动作和创建/打开工作单 |
| `/workbench/:projectId` | 是否看到下一步、资产、任务和能力入口 |
| `/workbench/:projectId/abilities/:abilityKey` | 是否能输入、提交、看状态、看结果 |
| `/assets` | 是否能筛选、继续创作、下载 |
| `/tasks` | 是否能筛状态、看 runId、看结果、重做 |
| `/exports/:packageId` | 是否能看 manifest 和导出状态 |

## 4. 必测状态

每个异步能力页面必须覆盖：

- 未输入
- 输入合法
- 提交中
- queued
- running
- succeeded
- failed
- runId 缺失或查询失败
- 余额不足
- API gap/能力缺失

## 5. 视觉走查标准

视觉走查不是看“好不好看”，而是看：

- 首屏是否有明确主动作。
- 表单和结果是否同时可理解。
- 任务状态是否足够突出。
- 文案是否短。
- 是否出现技术词干扰用户。
- 是否存在横向溢出、字号过小、对比不足。
- 移动宽度下是否还能完成主动作。

## 6. 交付证据

每轮交付至少保留：

- 关键页面截图。
- 测试命令输出摘要。
- API 调用清单。
- gap 清单。
- 剩余风险。
