# 新客户端整体产品架构（2026-03-16）

> 目标：把“像 Style3D 一样好用的客户端”从产品、交互、用户逻辑、前后端分层几个维度一次性讲清楚。  
> 项目名建议：`podi-client-web`  
> 设计基准：**UI/UX 全面参照 Style3D**，但底层能力全部换成我们的中台。  
>
> 文档状态：历史产品架构基线。
> 本文适合回答“第一轮为什么这么设计”，不适合直接当成当前页面结构真源。
> 当前骨架变化请以 `docs/plans/2026-03-19-style3d-client-rearchitecture-design.md` 为准。
> 本文重点：不是功能清单，而是“这个产品整体应该怎么运转”。

---

## 1. 产品目标

新客户端不是管理后台，也不是评测工具，而是一个真正给业务人员使用的生产工具平台。

它要解决的核心问题不是“有没有很多模型”，而是：

- 让设计师快速把灵感变成图
- 让运营快速把素材变成营销图
- 让业务同学不用懂技术，也能稳定拿到结果
- 让所有图片、视频、任务、历史结果都沉淀在一个地方

所以新客户端要满足 4 个原则：

1. **像工作台，不像后台**
2. **像业务动作，不像技术面板**
3. **像连续创作流程，不像一次性工具**
4. **像产品，不像接口演示页**

---

## 2. 目标用户

我们先不要把所有用户混成一类，至少分成 4 类。

### 2.1 设计师

主要需求：

- 以文生款
- 以款生款
- 图案提取
- 图案融合
- 四方连续
- 局部改款

他们更在意：

- 图的风格对不对
- 参数能不能少一点
- 历史结果能不能快速继续修改
- 示例能不能直接复用

### 2.2 电商运营 / 营销同学

主要需求：

- 裂变套图
- 图生视频
- 服装精修
- 换背景
- 细节图
- 超清 / 放大 / 扩图

他们更在意：

- 出图速度
- 批量效率
- 下载方便
- 是否适合直接用于上架和推广

### 2.3 业务负责人 / 老板视角

主要需求：

- 看成果
- 找历史素材
- 复用模板
- 追踪任务有没有成功

他们更在意：

- 成功率
- 是否好用
- 是否能沉淀资产
- 是否能把常用动作标准化

### 2.4 管理员 / 运维同学

这类人**不在客户端里做复杂配置**。  
他们继续在管理端处理：

- 执行节点
- LoRA
- 工作流
- 能力测试
- 调度监控

这意味着：

- **客户端只做消费能力**
- **管理端才做配置能力**

## 3. 产品结构总图

客户端整体建议分成 7 个一级模块：

1. 工作室
2. AI 研发设计
3. AI 视觉商拍
4. AI 工具箱
5. 任务中心
6. 我的素材
7. 账户与积分中心

它们的关系不是平级孤岛，而是一条完整的创作链：

```text
进入平台
  -> 工作室找到入口
  -> 进入某个功能页上传或选素材
  -> 提交任务
  -> 结果回到当前页面
  -> 同时进入任务中心
  -> 同时沉淀到我的素材
  -> 可再次创作 / 再次加工 / 下载导出
```

这个链路必须打通，否则前台就会变成很多分散工具。

---

## 4. 一级模块的职责

### 4.1 工作室

这是用户进入平台后的主入口。

它不负责复杂操作，主要负责：

- 告诉用户可以做什么
- 让用户快速开始
- 展示最近工作
- 展示最近素材
- 推荐模板和常用动作

一句话：**工作室负责“开始”和“返回”。**

### 4.2 AI 研发设计

这是偏设计创作的模块。

它负责：

- 从文字/参考图生成新设计
- 对款式和图案做再创作
- 提取与生成图案
- 做连续纹理和融合创作

一句话：**研发设计负责“生成设计内容”。**

### 4.3 AI 视觉商拍

这是偏营销图和展示图的模块。

一期先不强推高难的“上身类”，而是先放：

- 裂变套图
- 图生视频
- 细节增强
- 轻量版精修

一句话：**视觉商拍负责“把内容变成营销素材”。**

### 4.4 AI 工具箱

这是偏通用处理的模块。

它负责：

- 超清
- 放大
- 扩图
- 缩放
- DPI

一句话：**工具箱负责“修图和出图处理”。**

### 4.5 任务中心

这是整个平台的运行中心。

它负责：

- 看当前任务状态
- 看历史任务结果
- 看失败原因
- 再次执行

一句话：**任务中心负责“追踪过程”。**

### 4.6 我的素材

这是整个平台的资产中心。

它负责：

- 保存原图
- 保存结果图
- 保存视频
- 支持筛选和复用
- 支持再次创作

一句话：**我的素材负责“沉淀资产”。**

### 4.7 账户与积分中心

这一块之前写轻了，但如果要真正对齐 Style3D 的前台体验，它必须是正式模块。

它负责：

- 展示当前积分余额
- 展示赠送积分 / 充值积分
- 提供充值入口
- 展示点数包 / 套餐
- 查看充值记录
- 查看消费账单
- 查看使用量统计

一句话：**账户与积分中心负责“让用户知道自己还能做多少、花了多少、怎么继续买”。**

## 5. 核心用户逻辑

客户端不是“打开一个页面 -> 做一次任务 -> 结束”，而是一个循环。

### 5.1 用户主循环

```text
找入口
  -> 选功能
  -> 上传素材 / 选择历史素材
  -> 填参数
  -> 提交
  -> 等结果
  -> 预览结果
  -> 下载 / 收藏 / 再来一次 / 继续创作
```

这个循环里最重要的，不是“提交”本身，而是后面的 3 个动作：

- 再次创作
- 继续加工
- 素材沉淀

因为这决定了平台会不会越用越顺。

### 5.2 用户不是每次都从零开始

所以所有功能页都要支持两种进入方式：

#### 方式 A：从功能入口进入

- 工作室 -> 某个功能
- 顶部导航 -> 某个功能

适合第一次使用。

#### 方式 B：从已有素材进入

- 我的素材 -> 再次创作
- 任务中心 -> 再做一次
- 当前结果 -> 继续编辑

适合连续创作。

**这条非常关键。**  
因为真正的业务用户，大部分时间不是“重新开始”，而是“基于已有结果继续做”。

### 5.3 用户的资金/积分循环

除了创作循环，客户端还必须有一条“积分循环”。

```text
进入平台
  -> 看到当前积分
  -> 选择功能
  -> 提交前看到预计消耗
  -> 扣费或冻结额度
  -> 成功后确认扣费 / 失败后释放
  -> 在账户中心查看余额和账单
  -> 积分不足时进入充值
```

这条链如果缺失，前台业务体验就会断。

## 6. 核心交互模型

所有能力页都建议遵守同一套交互模型。

## 6.1 三栏模型

### 左栏：功能切换

用户在同一业务模块下切功能，不跳出当前上下文。

例如在“AI 研发设计”里：

- 以文生款
- 以款生款
- 融合创款
- 图案提取
- 图案融合
- 四方连续

### 中栏：输入与操作

这一栏只做三件事：

- 上传 / 选图
- 填参数
- 提交

### 右栏：案例与结果

这一栏兼顾 3 种内容：

- 示例案例
- 当前结果
- 最近结果

这就是 Style3D 很重要的一点：  
**不是让用户面对一张空白表单，而是始终让他看到“别人怎么做的”和“我做出来是什么样”。**

## 6.2 所有功能页的统一步骤

每个功能都按下面的步骤走：

### 第一步：选择输入

- 上传本地图片
- 从我的素材选择
- 从最近结果选择
- 部分功能支持纯文字输入

### 第二步：填写参数

参数分两层：

- 基础参数
- 高级参数

默认只展示基础参数，避免页面太技术化。

### 第三步：预期提示

在提交前给出清楚提示：

- 会生成什么
- 大概多久
- 是同步还是异步
- 预计消耗多少点数
- 当前余额够不够

### 第三步补充：余额校验

如果当前用户积分不足，不能让他白等到提交失败才知道。

应在提交前就做提示：

- 当前余额
- 本次预计消耗
- 是否可提交
- 去充值入口

### 第四步：提交并进入任务态

点击按钮后不要让用户卡在表单里等待。

需要立刻切换成任务态：

- 排队中
- 处理中
- 已完成
- 失败

### 第五步：结果区承接

结果成功后，当前页直接看到：

- 大图预览
- 下载
- 再来一次
- 继续创作

## 7. 页面交互细节规范

## 7.1 工作室首页交互

工作室首页要像“调度台”，不是展示页。

### 页面结构

1. 顶部欢迎区
2. 快捷开始
3. 智能体卡片
4. 推荐功能
5. 最近任务
6. 最近素材
7. 模板推荐

### 用户操作逻辑

- 新用户先看推荐功能和示例
- 老用户优先看最近任务和最近素材
- 高频用户可以直接从首页上传开始

### 首页的关键目标

- 3 秒内知道能干什么
- 1 次点击进入一个功能
- 2 次点击开始提交任务

## 7.2 功能页交互

### 通用规则

- 页面标题要说“业务动作”，不要说技术能力
- 上传区要明显
- 示例区要可一键套用
- 参数区要层级清楚
- 结果区要支持连续动作

### 结果后的动作

结果出来后，右侧至少给 4 个动作：

- 下载
- 保存到素材库
- 再来一次
- 继续创作

## 7.3 任务中心交互

任务中心不是“日志页”，而是“办事进度页”。

### 用户最关心什么

- 我刚刚那个任务好了没
- 哪个失败了
- 为什么失败
- 能不能重试

### 所以任务列表必须优先显示

- 当前状态
- 缩略图
- 功能名
- 时间
- 失败原因
- 操作按钮

不要把内部 ID 放在最显眼的位置。

## 7.4 我的素材交互

素材页不是简单文件夹，而是“创作起点”。

所以每个素材卡至少要支持：

- 预览
- 下载
- 收藏
- 查看来源
- 用这个继续创作

## 7.5 账户与积分中心交互

这部分建议放在页面右上角头像/账户区域，同时保留独立页面。

### 顶部全局展示

顶栏建议长期显示：

- 当前积分余额
- 充值按钮
- 活动赠送提示

参考 Style3D 的感觉，可以把“连续登录赠送”“免费生成次数”“当前余额”这种信息做成醒目的轻提示区。

### 独立积分页建议包含

1. 当前余额卡片
2. 充值套餐区
3. 最近消费记录
4. 最近充值记录
5. 使用量统计
6. 常见问题

### 用户最常见动作

- 看余额
- 充值
- 看最近扣费
- 对账
- 因余额不足返回后继续提交

## 8. 状态设计

客户端里最容易做差的地方，就是状态管理。

建议统一成 5 个面向用户的状态：

- `待提交`
- `排队中`
- `处理中`
- `已完成`
- `失败`

内部再复杂，前台都统一翻译成这 5 类。

## 8.1 当前页面状态

当前功能页需要维护：

- 表单编辑状态
- 提交中的按钮状态
- 当前任务状态
- 当前结果状态

## 8.2 全局状态

全局需要维护：

- 登录态
- 上传状态
- 任务数量提醒
- 最近素材缓存

## 8.3 状态同步规则

同一个任务一旦成功，要同步更新 3 个地方：

1. 当前页面结果区
2. 任务中心
3. 我的素材

这条一定要打通。

从客户端视角，最核心的只有 7 个对象。

## 9.1 用户 User

字段重点：

- id
- name
- avatar
- role

## 9.2 功能 Capability

字段重点：

- id
- code
- name
- module
- description
- input schema
- output type

## 9.3 任务 Job

字段重点：

- id
- capabilityCode
- title
- status
- createdAt
- updatedAt
- inputSummary
- outputSummary

## 9.4 素材 Asset

字段重点：

- id
- type(image/video)
- url
- thumbnail

- sourceCapability
- tags

## 9.5 项目 Project

## 10. 前后端整体架构

建议采用“客户端前台层 + 客户端接口层 + 中台能力层”的三层结构。

```text
用户
  ->
客户端前台（podi-client-web）
  ->
客户端接口层（/api/client/*）
  ->
中台已有能力接口
  ->
执行节点 / 第三方模型 / OSS
```

## 10.1 为什么要加客户端接口层

因为前台不应该知道这些事情：

- 用的是 Ability 还是 Workflow
- 是同步任务还是异步任务
- 走的是 KIE 还是 ComfyUI
- LoRA 怎么选
- 路由到了哪台执行节点

这些全部都应该被客户端接口层吃掉。

## 10.2 客户端接口层的职责

- 转换前台参数口径
- 转换后端状态口径
- 聚合首页数据
- 聚合任务和素材数据
- 输出统一错误信息

---

## 11. 推荐接口设计

## 11.1 首页

- `GET /api/client/home`

返回：

- 推荐功能
- 最近任务
- 最近素材
- 模板推荐
- 当前积分摘要

## 11.2 功能目录

- `GET /api/client/capabilities`
- `GET /api/client/capabilities/{code}`

返回：

- 前台展示名
- 描述
- 输入表单
- 示例数据
- 是否推荐

## 11.3 提交任务

- `POST /api/client/jobs`

由后端决定：

- 同步直接返回结果
- 异步先建任务再轮询

前台不用关心内部细节。

## 11.4 任务中心

- `GET /api/client/jobs`
- `GET /api/client/jobs/{id}`
- `POST /api/client/jobs/{id}/retry`

## 11.5 素材中心

- `GET /api/client/assets`
- `GET /api/client/assets/{id}`
- `POST /api/client/assets/upload`
- `POST /api/client/assets/{id}/rerun`

## 11.6 账户与积分中心

- `GET /api/client/wallet/summary`
- `GET /api/client/wallet/ledger`
- `GET /api/client/wallet/bills`
- `GET /api/client/wallet/usage-summary`
- `POST /api/client/wallet/recharge-orders`
- `GET /api/client/wallet/recharge-orders/{orderNo}`

客户端聚合层背后可映射现有能力：

- `/api/wallet/v1/balance`
- `/api/wallet/v1/ledger`
- `/api/wallet/v1/bills`
- `/api/wallet/v1/usage-summary`
- `/api/wallet/v1/recharge-orders`
- `/api/wallet/v1/recharge-orders/{orderNo}`

## 12. 错误与异常设计

业务用户最怕的不是失败，而是“看不懂为什么失败”。

所以错误设计必须分层。

## 12.1 对用户展示的错误

只说业务语言：

- 图片上传失败，请重新上传
- 当前任务较多，请稍后再试
- 参数不完整，请检查后重新提交
- 当前服务繁忙，请稍后重试
- 当前积分不足，请先充值

## 12.2 对日志记录的错误

后台保留完整技术信息：

- 能力 ID
- 请求参数摘要
- 原始错误码
- 执行节点
- 第三方错误详情

## 12.3 前台错误展示规则

- 当前页表单错误 -> 表单内提示
- 提交失败 -> 顶部提示条 + 停留当前页
- 运行失败 -> 结果区失败卡片 + 任务中心失败项
- 积分不足 -> 弹出充值引导，不丢当前表单内容

---

## 13. 非功能要求

## 13.1 性能

- 首屏尽量在 3 秒内可操作
- 上传后立即给反馈
- 异步任务状态刷新要足够快
- 示例图和结果图用缩略图优先加载

## 13.2 可维护性

- 不做超大单文件
- 页面、组件、服务分层
- 功能配置尽量数据化

## 13.3 可观测性

- 任务状态流转可追踪
- 接口耗时可追踪
- 失败原因可定位
- 首页、任务中心、结果区状态一致

## 13.4 安全

- 客户端不暴露执行节点细节
- 客户端不暴露管理员能力
- OSS 上传继续走临时凭证
- 结果下载控制权限

## 14. 分期建议

## P0：先上线一个真正可用的客户端

## 15. 当前最重要的架构结论

这一版客户端最核心的不是“再堆多少功能”，而是把 5 件事一次性做对：

1. **入口结构做对**
2. **交互流程做对**
3. **任务状态做对**
4. **素材沉淀做对**
5. **客户端和中台分层做对**

如果这 5 件事做对了，后面再补高难能力，只是加功能。  
如果这 5 件事没做对，功能越多，客户端越难用。
