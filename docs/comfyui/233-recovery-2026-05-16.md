# 233 ComfyUI 白名单后同构恢复任务

## 1. 任务定位

这是一次临时运维恢复任务，不是新的平台架构改造。

目标是让 `117.50.216.233`（4090 机器，简称 233）在白名单保护下重新补齐 ComfyUI 节点、模型和依赖，最终尽量恢复为和 `117.50.80.158`（5090 机器，简称 158）一致的执行节点。

核心原则：

- 安全边界靠 IP 白名单、低权限运行用户、systemd 加固和巡检解决，不靠长期禁用业务能力解决。
- 平台侧保持扁平：不要为了解决 233 单点问题，在中台增加大量特殊路由、特殊文案或长期例外。
- 先修服务器同构，再考虑恢复双机路由；不能为了快速消除 warning 把功能永久写死到单机。
- 任何“放开权限”都必须有白名单、巡检和验证证据作为前提。

## 4. 不做什么

本任务不做以下事情：

- 不新增“233 专属业务逻辑”。
- 不为了单个缺失节点继续扩大中台复杂路由分支。
- 不把 233 永久降级成只跑少数业务的特殊机器。
- 不在代码仓库写入服务器密码、API Key 或其他密钥。
- 不通过公网 Web UI 安装来源不明节点。

## 5. 执行顺序

### 5.1 进入服务器前

- 确认 233 端口 `8079` 仍只允许白名单来源访问。
- 查看最近巡检结果：

```bash

sudo tail -n 120 /var/log/comfyui-security/check.log
```

- 确认 ComfyUI 仍以低权限用户运行：

```bash
systemctl status comfyui --no-pager
ps -eo user,pid,ppid,cmd | grep -E 'ComfyUI|main.py' | grep -v grep
```

### 5.2 安全复核

- 检查可疑进程、可疑外联和临时目录：

```bash
ps aux --sort=-%cpu | head -40
ss -tunap | head -80
find /tmp /var/tmp /dev/shm -maxdepth 2 -type f -mtime -2 -ls 2>/dev/null | head -80
```

- 如果发现 `ironhash`、`downloaded_app`、伪 `supervisord`、`/tmp/python3`、Kryptex pool 等旧指标，先停止恢复任务，按应急流程处理。

## 8. 回滚

如果恢复后发现安全异常：

1. 立即停止 ComfyUI。
2. 保留证据。
3. 回滚或禁用新恢复的高风险节点。
4. 执行巡检脚本。
5. 中台保持或恢复临时 158-only 路由。
6. 只有安全结果干净后再恢复服务。

如果只是节点兼容失败：

1. 不改业务 API。
2. 不增加长期特殊分支。
3. 继续补齐 233 节点或模型。
4. 临时路由限制继续保留，直到强制 233 测试通过。
