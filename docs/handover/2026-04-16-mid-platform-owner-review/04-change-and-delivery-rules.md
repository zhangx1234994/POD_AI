# 变更与交付规则

## 1. 先分析，后修改

不允许“猜测式修改”。所有中台问题都要先给出：

1. 根因判断
2. 影响范围
3. 修改点
4. 回归点

## 2. 改任何接口必须同步 4 件事

1. 请求/响应文档
2. 错误码
3. 状态口径
4. 回归测试

## 3. 不允许只修当前页面问题，不看全链路

例如修一个 Coze 工具箱，至少要同时检查：

- 中台 ability
- workflow / binding
- OpenAPI
- 评测端
- 文档

## 4. 变更说明必须可追溯

提交说明或交付说明里要写清：

- 改了什么
- 为什么改
- 影响哪些模块
- 怎么验证

## 5. 一个中台任务的完成定义

以下 6 项缺任意一项，都不算完成：

1. 功能代码完成
2. 本地验证完成
3. 必要测试通过
4. 文档更新完成
5. 明确写出影响范围
6. 明确写出回归结论

## 6. 标准分析模板

每个中台任务至少输出以下信息：

### 根因

- 现象是什么
- 真正问题在哪一层
- 为什么会发生

### 影响范围

- 后端接口
- 管理端
- 评测端
- 客户端
- Coze / OpenAPI
- 文档与错误码

### 修改点

- 涉及的后端模块
- 涉及的前端联动点
- 涉及的配置、迁移或任务链路

### 回归点

- 成功路径
- 关键错误路径
- 状态流转
- 结果回填
- 跨端一致性

## 7. 发布前最低检查

默认按仓库现有规范执行，至少覆盖：

- 后端测试
- 管理端静态检查
- 评测端静态检查
- 文档同步检查
- 错误码总表检查
- 状态词一致性检查

发布结论必须同时包含：

- 已覆盖的错误场景
- 仍未覆盖的风险
