# 中台能力产品化分层与表面治理框架

## 1. 先说结论

现在中台真正的问题，不是能力不够，而是**内部结构过早暴露到了用户表面**。

用户想解决的是：

- 我现在要做什么
- 我需要准备什么
- 系统会给我什么结果
- 结果之后还能做什么

但中台天然关心的是：

- 走哪个 executor
- 绑哪个 workflow
- 哪个 binding 在生效
- schema 如何映射
- callback 和状态如何回填

这两套语言都对，但不能混在一个界面层里。
所以这轮改造的本质，不是“美化页面”，而是做一次**能力翻译与表面治理**。

## 2. 哲学起点

### 2.1 平台不是模型陈列馆

用户不会因为看见更多模型名而更信任平台。
用户真正购买的是三件事：

- 确定性
- 连续性
- 可复用性

确定性：知道这个功能适合什么，不适合什么。
连续性：结果不是一次性下载，而是下一步工作的起点。
可复用性：好的结果能沉淀为模板、素材和标准动作。

### 2.2 中台的价值不是“复杂”，而是“把复杂藏起来”

如果一个系统把内部对象原样暴露给用户，这不叫透明，这叫把组织成本转嫁给用户。
好的中台不是让用户理解 `executor / workflow / binding`，而是让用户根本不需要理解这些词，也能稳定完成工作。

### 2.3 每个页面都必须回答一个问题

一个页面存在，不是为了“放一个功能”，而是为了帮助用户完成一个判断。

- 登录页：我能不能安全进入这个系统
- 首页：这个平台到底能帮我做什么
- 工作室：我现在从哪里开始
- 工作区：我这一轮具体怎么做
- 任务中心：事情现在进行到哪
- 素材中心：我之前做过什么，接下来能复用什么
- 钱包页：我为什么付费，付费后换来什么确定收益

如果一个页面不能清楚回答它自己的问题，它就会开始堆概念、堆入口、堆术语。

## 3. 四层模型

后续所有改造都建议按 4 层处理，而不是把所有信息都塞进 API 或页面里。

### 3.1 内核层

面向系统运行。

- provider
- executor
- workflow
- binding
- callback
- queue
- status
- error

这一层追求的是可调度、可定位、可回溯。

### 3.2 能力层

面向真实能力资产。

- ability
- capability_key
- input_schema
- default_params
- metadata

这一层追求的是可接入、可测试、可维护。

### 3.3 产品层

面向用户理解。

- 场景
- 工具
- 模板
- 结果
- 下一步动作

这一层追求的是可理解、可选择、可持续使用。

### 3.4 表面层

面向具体渠道。

- 管理端
- 评测端
- 客户端 V1
- 客户端 V2
- Coze 工具箱

这一层追求的是在不同入口下，暴露正确复杂度。

## 4. 当前可直接触及的治理边界

从仓库与服务器现状看，当前已能直接治理以下边界：

- 中台后端：能力定义、展示配置、调用日志、状态口径、错误口径
- 管理端：内部配置、测试、日志追溯、能力视图
- 评测端：证据、回归、接入视图
- 客户端 V1：真实工作流壳层、素材沉淀、展示翻译
- 客户端 V2：品牌化前台与入口重组
- Coze：工具命名、摘要、参数说明、OpenAPI 暴露方式
- Coze Linux 服务器：部署、日志、容量、发布与运行治理

这意味着后续优化可以按“**核心契约不变，展示与组织方式重构**”来做。

## 5. 页面与功能为什么存在

### 5.1 客户端登录

为什么存在：把“游客浏览”和“真实资产、任务、钱包”分开。
提供什么帮助：让用户意识到，登录后看到的不是示例，而是自己的工作数据。
当前来源：

- 登录接口：`/api/auth/login`
- 前台弹窗：`podi-client-web/src/components/LoginDialog.tsx`
- 当前没有独立登录视觉页，也没有专门登录图

当前问题：

- 登录像一个技术弹窗，不像产品入口
- 没有解释“登录之后会发生什么变化”

治理建议：

- 短期不改接口，只补登录场景说明
- 中期把登录从“技术动作”升级成“身份切换说明页”

### 5.2 管理端登录

为什么存在：把中台控制面与业务使用面隔离。
提供什么帮助：让内部同学知道这里是配置、发布、回溯入口，而不是业务操作入口。
当前来源：

- 登录接口同样走 `/api/auth/login`
- 页面文案与结构：`podi-admin-web/src/components/LoginGate.tsx`
- 视觉主要由 `podi-admin-web/src/styles/podi-theme.css` 控制
- 当前没有远程背景图

当前判断：

- 这是内部面，信息应该偏治理和风险，不必做成营销页
- 但也需要比现在更明确地提示“这是中台控制台，不是业务前台”

### 5.3 客户端首页 V1

为什么存在：建立用户对平台价值的第一判断。
提供什么帮助：告诉用户平台不是很多零散工具，而是一条连续创作链。
当前来源：

- 产品文案、场景、模板：`podi-client-web/src/config/clientProduct.ts`
- 案例、导航、素材样例：`podi-client-web/src/mock/content.ts`
- 场景图与案例图：`Unsplash`

当前问题：

- 价值叙事已经有了，但数据仍是配置驱动和 mock 驱动
- 图片资源来自外部公共图库，不是品牌资产

治理建议：

- 首页信息继续保留配置驱动，但从“写死在前端”升级到“可治理内容源”
- 外部图库仅作过渡，后续改为自有品牌图与成果图

### 5.4 客户端首页 V2

为什么存在：承担品牌感、信任感和高层入口组织。
提供什么帮助：让用户在情绪上愿意开始，在结构上知道去哪。
当前来源：

- Hero、分类卡、统计值写在 `podi-client-v2/src/pages/HomePage.tsx`
- 图片仍来自 `Unsplash`
- 统计值目前是静态展示，不是真实经营数据

当前问题：

- 视觉已经偏产品化，但内容控制还停留在页面代码中
- 一旦要扩展，会形成“每个页面自己维护一套内容”

治理建议：

- V2 的方向保留
- 但首页内容必须抽到统一的 surface content 配置层

### 5.5 工作室 / Studio

为什么存在：减少“空白页焦虑”，帮助用户决定从哪里开始。
提供什么帮助：把高频路径、模板、白板和智能体入口放到同一处。
当前来源：

- V1 主要由 `clientProduct.ts`、`toolConfigs.ts`、能力接口共同驱动
- V2 的模板、快捷动作、白板当前写在 `podi-client-v2/src/pages/StudioPage.tsx`
- 图片仍主要来自 `Unsplash`

当前问题：

- 工作室正在承担“开始页、模板页、智能体页、最近工作页”多种职责
- 如果没有聚类规则，很容易继续膨胀

治理建议：

- 工作室只做“开始”和“返回”
- 不把底层对象直接堆到工作室

### 5.6 工作区 / Workspace

为什么存在：承接一次具体创作。
提供什么帮助：把用户输入、必要设置、结果预期和任务状态收在同一操作面。
当前来源：

- 真正能力定义来自 `/api/abilities`
- 字段说明与表单输入受 `input_schema` 和前端配置共同影响
- 本轮已开始增加兼容式 `presentation` 翻译层

当前问题：

- 历史上更像 schema 渲染器，不够像任务引导器
- 用户能看到过多技术词和高级字段

治理建议：

- 保持调用契约不变
- 继续推进“展示层 > 参数层”的改造

### 5.7 任务中心

为什么存在：给用户过程感，避免“提交后失联”。
提供什么帮助：看状态、看失败、看结果、决定是否继续。
当前判断：

- 这里应该是用户的运行中心，不应该是内部日志页
- 任务中心要服务“判断下一步”，不是服务“理解底层链路”

治理建议：

- 用户面只看业务状态
- 内部追溯放管理端和评测端

### 5.8 素材中心

为什么存在：把结果变成资产，而不是一次性文件。
提供什么帮助：下载、复跑、带入下一步、形成模板。
当前来源：

- 客户端沉淀：`podi-client-web/src/services/assetLibrary.ts`
- 当前是 `localStorage` 本地素材库
- 页面读取：`podi-client-web/src/hooks/useClientAssets.ts`
- 无真实数据时回退 `podi-client-web/src/mock/content.ts`

当前问题：

- “素材中心”的产品定义是对的
- 但真正的数据治理还停留在浏览器本地存储，无法跨设备、跨团队、跨会话

治理建议：

- 短期保留本地沉淀壳层
- 中期接真实用户资产接口
- 长期引入团队素材与模板治理

### 5.9 钱包页

为什么存在：把成本、权益和持续使用连接起来。
提供什么帮助：让高频用户理解付费不是购买图片，而是购买更稳定的生产能力。
当前判断：

- 钱包不应该只是充值页
- 它应该解释“为什么值得继续留在系统里生产”

## 6. 当前数据与图片从哪里来，应该由谁控制

### 6.1 应该区分 4 类数据

#### A. 运行真数据

来自真实业务系统。

- 用户身份
- 任务状态
- 结果资产
- 钱包余额
- 调用日志

控制位置：

- 后端接口
- 数据库
- OSS / 媒资系统

#### B. 展示配置数据

来自平台对能力的产品化翻译。

- 工具中文名
- 一句话价值
- 表单标签
- 占位提示
- 是否高级参数
- 下一步推荐

控制位置：

- 中台能力 `metadata.presentation`
- 或后续独立 surface config

#### C. 运营内容数据

来自内容策划，而不是运行时系统。

- 首页 Hero 文案
- 案例卡片
- 模板推荐
- 角色案例
- 品牌介绍

当前控制位置：

- `clientProduct.ts`
- `mock/content.ts`
- `podi-client-v2/src/pages/*.tsx` 内的页面常量

目标控制位置：

- 第一阶段：仓库内统一内容清单
- 第二阶段：管理端内容配置或 CMS

#### D. 品牌媒资数据

来自品牌内容资产，而不是随机互联网图片。

- 登录页主视觉
- 首页场景图
- 案例图
- 模板封面

当前来源：

- 大量使用 `Unsplash`

目标来源：

- 自有 OSS 品牌资产目录
- 真实生成成果中经过审核的可展示样本

### 6.2 控制原则

后续建议按下列原则治理：

- 运行数据由后端控制
- 能力展示由中台 presentation 层控制
- 页面内容由 surface content 层控制
- 品牌图片由媒资资产库控制

不要再让单个 React 页面同时决定：

- 文案
- 图片
- 统计口径
- 工具标签
- 模板推荐

否则后续只会继续碎片化。

### 6.3 对象级控制表

| 对象 | 当前来源 | 当前控制位置 | 目标控制位置 |
| --- | --- | --- | --- |
| 客户端登录说明 | 静态文案 | `podi-client-web/src/components/LoginDialog.tsx` | surface content 配置 |
| 客户端登录主视觉 | 当前无独立主视觉 | 无 | 品牌媒资库 + surface content 配置 |
| 管理端登录说明 | 静态文案 | `podi-admin-web/src/components/LoginGate.tsx` | 仍可保留代码控制，但文案要纳入统一术语表 |
| 首页 Hero 文案 | 静态配置 / 页面常量 | `clientProduct.ts`、`podi-client-v2/src/pages/HomePage.tsx` | surface content 配置 |
| 首页 Hero 图片 | `Unsplash` | 前端页面常量 | 自有 OSS 品牌媒资 |
| 案例卡 / 场景卡 | mock 内容 + 外部图片 | `podi-client-web/src/mock/content.ts`、`clientProduct.ts` | 内容配置 + 审核过的案例资产 |
| Studio 模板封面 | 外部图片 | `podi-client-v2/src/pages/StudioPage.tsx` | 模板中心配置 + 自有封面图 |
| 工具名称 / 字段标签 | 能力 schema + 前端配置混合 | `/api/abilities`、`toolConfigs.ts` | `metadata.presentation` |
| Coze 工具名称 / 摘要 | 后端 OpenAPI 生成 | `backend/app/routers/coze_podi_plugin.py` | `metadata.presentation` + surface rules |
| 任务状态 | 真任务 / 部分前端壳层 | 后端任务接口 + 各端页面 | 后端统一状态口径 |
| 素材列表 | 本地沉淀 + mock 回退 | `assetLibrary.ts`、`mock/content.ts` | 后端素材接口 + OSS |
| 钱包统计 | 当前多为静态或 mock | 前端页面常量 | 后端账户 / 计费接口 |

## 7. 能力聚类规则

后续不要再按厂商或技术类型组织用户体验，而要按“用户意图”聚类。

建议稳定成 5 个一级场景：

1. 新款设计
2. 图案设计
3. 视觉商拍
4. 终稿处理
5. 资产沉淀

对内仍然保留厂商、模型、workflow、executor 维度，但不让它们直接主导用户导航。

## 8. 扩展规则

以后每新增一个能力，不只是在中台里新增一条 `ability`，还必须补齐以下判断：

1. 它服务哪个一级场景
2. 它是主路径能力还是高级能力
3. 它应该在哪些表面出现
4. 它对外叫什么
5. 它的默认输入是什么
6. 它成功后推荐什么下一步
7. 它应该沉淀什么结果资产

如果缺这 7 件事，就说明接入的是“技术能力”，不是“产品能力”。

## 9. 多端暴露规则

建议后续所有能力都走显式暴露矩阵，而不是默认全端可见。

- `internal_only`：仅内部配置/调试可见
- `admin_and_eval`：管理端与评测端可见
- `client_enabled`：客户端可见
- `coze_enabled`：Coze 工具箱可见
- `advanced_only`：仅高级模式展示

这样才能避免：

- 还没产品化的能力提前暴露到客户端
- 内部调试能力误进 Coze
- 高风险能力过早进入普通用户入口

## 10. 后续实现顺序

坚持一个前提：**不改现有接口路径，不破坏现有调用参数，不影响现有业务链路。**

### 第 1 阶段

- 建立统一术语表
- 把工具展示说明收进 `presentation` 层
- 梳理客户端与 Coze 的用户语言

### 第 2 阶段

- 抽离 surface content 配置
- 统一首页、模板、案例、登录说明、品牌图片来源
- 清理页面内部写死内容

### 第 3 阶段

- 接真实素材、任务、钱包数据
- 把本地壳层逐步替换成真实资产中心
- 建立案例与品牌媒资审核机制

### 第 4 阶段

- 形成“新能力接入 = 技术接入 + 产品接入 + 表面接入”的标准流程

## 11. 一句话判断

中台接下来最重要的事情，不是继续堆更多能力，而是让能力真正变成用户能理解、能选择、能持续复用的工作流产品。

技术复杂度可以继续增长，但用户看到的复杂度必须下降。
这就是中台 owner 接手之后最该承担的产品责任。
