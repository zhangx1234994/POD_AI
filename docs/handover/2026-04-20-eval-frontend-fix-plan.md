# 2026-04-20 测评端问题修复方案（给测评端开发）

## 目标

本次目标不是重做测评端页面，而是把“测评端列表/入口异常”这类问题收口成稳定方案，避免继续在前端堆补丁。

当前判断：

- 真正的根因主要在 **后端 `eval_workflow_version` 历史脏数据 + 分类归一化 + 读接口中夹带 seed 写操作**。
- 前端不是根因位，但前端需要补 **降级体验、错误展示、只读容错**，避免后端偶发异常时页面直接不可用。

所以这次前端修改的原则是：

1. 不碰业务契约。
2. 不在前端硬编码修数据。
3. 只做可验证的容错和展示收口。

---

## 当前确认事实

### 1. 真正异常点

线上当前：

- `GET /api/evals/workflow-versions` 返回 `500`
- `GET /api/evals/admin/workflow-versions` 返回 `500`

这说明：

- 页面异常不只是“交互问题”
- 而是列表接口本身仍然可能炸

### 2. 本地代码修复方向是对的

当前本地后端已经补了：

- `EvalWorkflowVersion` 唯一约束
- category 归一化
- 历史重复数据 dedupe
- admin/public 列表接口的 best-effort seed sync 包裹

本地直接跑数据库 + 序列化链路：

- `rows 32`
- `dedup 32`
- `serialize ok`

说明：

- “重复 workflow version 导致列表异常”这条根因，本地已经处理到了

### 3. 前端当前不应该再做的事

不要继续在前端做这些动作：

- 根据 workflow 名称手工过滤重复项
- 根据 category 名称强行重写分组
- 在前端兜底修正历史脏数据
- 把后端 500 当成“空列表”静默吞掉

这些都会把根因藏起来。

---

## 前端需要修改的范围

本次前端只改 3 类内容。

### A. 列表加载失败时的降级体验

目的：

- 后端接口异常时，页面不能整屏空白
- 用户要知道“是列表接口失败”，不是自己操作错了

要求：

1. `workflow-versions` 拉取失败时，显示明确错误区块
2. 错误区块包含：
   - 当前动作：加载测评功能列表失败
   - 简短原因：服务返回异常，请刷新或联系维护者
   - 操作按钮：重试
3. 不要把页面渲染成“没有任何功能”

建议文案：

- 标题：`测评功能列表加载失败`
- 说明：`当前不是你的输入问题，而是功能列表接口没有正常返回。请先重试；如果持续失败，通知中台排查后端日志。`

### B. 列表页只读去重容错

目的：

- 如果线上又出现历史重复数据，前端至少不要把相同 workflow 展示两遍

前端允许做的只读容错：

- 仅在拿到列表结果后，按 `(workflow_id, category)` 做一次只读去重
- 只影响展示，不回写、不改参数、不改分类

注意：

- 这不是根因修复
- 只是前端防止列表重复展示
- 后端 dedupe 仍然是主修复

推荐逻辑：

```ts
key = `${workflow_id}::${category}`
```

如果 key 重复：

- 保留第一条
- 丢弃后续重复项

### C. 管理页 / 测评页共用错误展示口径

目的：

- admin 列表和 public 列表如果都是同类问题，前端用户看到的体验应该一致

要求：

- 测评端列表页、管理页中涉及 workflow version 拉取失败时，错误口径一致
- 不要一处显示“暂无数据”，另一处显示“服务器异常”

统一原则：

- `4xx`：配置/权限/参数问题
- `5xx`：服务端异常
- 网络超时：网络或服务不可达

## 前端不要修改的内容

以下内容前端同学这次不要碰：

### 1. category 业务规则

不要在前端写死：

- 哪些 workflow 属于 `图裂变`
- 哪些 workflow 属于 `图延伸类`
- 哪些 workflow 属于 `通用类`

这些规则必须由后端和 seed 决定。

### 2. workflow 参数 schema 修正

不要因为某条 workflow 展示不对，就在前端本地 patch schema。

例如：

- width/height 默认值
- lora 字段有无
- prompt 是否必填

这些都必须以后端返回为准。

### 3. 在前端继续做“大改版式”来掩盖列表问题

当前问题不是 UI 风格问题。

所以这次不要把下面这些和故障修复混在一起：

- 首页重做
- 分类卡片重做
- 视觉样式全面替换
- 导航结构重新设计

这类改动可以后做，但不属于本次故障修复范围。

优先只看这些文件：

- `podi-eval-web/src/App.tsx`
- 如果列表请求和状态管理已拆分，则改对应的 request/useEffect/hook 文件
- 如果有公共错误提示组件，可复用现有错误卡片/Alert 组件

尽量不要把本次修复扩散到：

- 大量 CSS 文件
- 全局布局
- 无关卡片组件

## 前端实现建议

### 1. workflow list 请求层

增加显式状态：

- `idle`
- `loading`
- `success`
- `error`

不要只靠：

- `list.length === 0`

来推断失败。

### 2. 错误对象保留原始信息

建议保留：

- `status`
- `message`
- `raw body`（可截断）

页面显示可简化，但 console 或调试区域要保留原始错误，方便回查。

### 3. 重试按钮只重拉列表

不要刷新整个页面状态。

重试应只触发：

- workflow version list reload

避免把用户当前已经输入的参数表单全部清空。

### 4. 去重只在渲染前做

不要把 dedupe 结果再写回全局状态源。

建议：

- 请求结果保留原始数组
- 渲染前派生 `displayRows`

这样后续排查时还能看到原始返回。

## 验证标准

前端同学改完后，至少自测这几项：

### 场景 1：接口正常

- 页面能正常拉到 workflow 列表
- 没有重复展示同一条 `(workflow_id, category)`
- 分类和参数展示仍与当前后端一致

### 场景 2：接口返回 500

模拟方式：

- 本地把接口地址改错
- 或在 devtools/network mock 500

预期：

- 页面显示“列表加载失败”
- 有重试按钮
- 不显示成“暂无功能”
- 不整页白屏

### 场景 3：接口返回重复项

可本地 mock 两条相同 `(workflow_id, category)` 数据

预期：

- 页面只展示一条
- 不影响其它正常功能

### 场景 4：重试动作

预期：

- 点击重试后只重拉列表
- 当前已输入的表单参数不应被清空

## 与后端的边界

这次需要明确：

### 前端负责

- 列表请求错误展示
- 只读去重容错
- 重试体验

### 后端负责

- `eval_workflow_version` 去重
- category 归一化
- migration
- seed 同步策略
- 读接口是否允许写数据库

如果前端发现：

- 线上仍返回 500
- 或 category 明显错乱

不要继续在前端硬 patch，直接回给后端。
