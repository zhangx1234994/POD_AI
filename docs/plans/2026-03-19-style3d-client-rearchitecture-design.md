# Style3D 客户端重构设计（2026-03-19）

> 目标：不是继续修现有客户端样式，而是基于与 Style3D 的真实视觉对照，重新定义 `podi-client-web` 的信息架构、页面骨架、组件分层和实施顺序。
> 结论：当前客户端的主要问题不是“UI 不够精致”，而是“前台架构仍然偏能力平台视角”。本次重构要把客户端从“能力展示站”切成“业务工作台”。
> 历史说明：当前仓库已不再包含客户端代码目录，本文只作为历史重构方案参考，不代表当前开发主线。

## 1. 设计结论

通过对 `Style3D` 首页、`Text to Style`、`Creative Merge` 与本地客户端首页、工作台、研发设计页的整页截图对比，可以得到 4 个明确结论：

1. Style3D 的体验核心不是卡片或配色，而是稳定的产品骨架。
2. 它的每个功能页都在让用户立刻开始动作，而不是先理解系统。
3. 它把“模型 / 工作流 / 执行链路”全部隐藏在后面，前台只保留业务动作和案例表达。
4. 我们当前页面的主要失真点，是把中台概念、模块统计、链路标签、说明型 Hero 抬到了用户主视图。

因此本次重构不做“局部改样式”，而做“前台架构重排”。

## 2. 新产品骨架

新的客户端只保留 6 个一级面：

1. 工作室 `Studio`
2. AI 研发设计 `Creative Design`
3. AI 视觉商拍 `Visual Shoot`
4. AI 工具箱 `AI Toolbox`
5. 任务中心 `Tasks`
6. 我的素材 `Assets`

补充说明：

- 钱包 / 积分仍保留，但从一级主导航降为全局状态入口与独立支撑页。
- 项目详情仍保留，但不再作为一级导航入口，而是从工作室 / 任务 / 素材流入。
- 不在客户端暴露“能力数、分组数、专用链路、复用链路、执行方式”等中台视角字段。

新的用户主路径是：

```text
进入首页
  -> 进入工作室
  -> 选择一个业务动作
  -> 在稳定工作区中提交
  -> 结果回到当前页
  -> 同步进入任务中心
  -> 同步沉淀到素材库
```

## 3. 页面架构原则

### 3.1 首页原则

首页只做三件事：

- 建立品牌感
- 提供工作室入口
- 给出最近工作与推荐动作

首页不再承担“模块总览 + 功能大卖场 + 大量说明文案”的职责。
首屏必须是单一主视觉，不允许多个内容层同时争抢注意力。

### 3.2 模块页原则

`研发设计 / 视觉商拍 / 工具箱` 三个模块页不再做成长篇内容页。
它们统一变成“带左侧菜单的工作台壳”，用户进入后默认直接落在第一个高频功能上。

也就是说：

- 模块页 = 功能页容器
- 不再是“模块介绍页 + 功能页”的双层模式

### 3.3 功能页原则

所有功能页统一为三栏式：

- 左栏：业务动作菜单
- 中栏：输入与提交
- 右栏：案例、预期效果、结果回填

这套骨架必须全站稳定。
用户切换 `以文生款 / 图案提取 / 裂变套图 / AI 超清` 时，变的是动作和内容，不变的是交互结构。

## 4. 新路由结构

建议将现有路由重组为：

```text
/home
/studio
/design/:tool
/shoot/:tool
/toolbox/:tool
/tasks
/assets
/wallet
/projects/:projectId
```

关键变化：

- `/home` 只做品牌首页
- `/studio` 作为真正的工作室入口
- `/design/:tool`、`/shoot/:tool`、`/toolbox/:tool` 直接承载实际工作台
- 删除现在“模块概览 + 模块工作区”的重叠层级

默认跳转建议：

- `/` -> `/home`
- 从首页主 CTA -> `/studio`
- 从顶级导航进入模块时，直接进入该模块默认高频工具，如 `/design/text-to-style`

## 5. 页面骨架定义

### 5.1 Home

`Home` 是品牌前台，不是功能列表。

首屏结构：

- 顶部导航
- 单一主视觉 Hero
- 一个主 CTA
- 一个次级 CTA

次屏结构：

- 3 个主业务入口卡
- 1 个“为什么选择我们”的能力说明区
- 1 个案例带

首页禁止事项：

- 不展示任务统计
- 不展示能力分组数
- 不展示中台数据结构感
- 不在首屏放多个并列功能大卡瀑布

### 5.2 Studio

`Studio` 是工作入口页，要像“工作台首页”，不是第二个首页。

结构建议：

- 顶部一句话问题：今天要开始哪类创作
- 智能体 / 工作流快捷入口
- 最近任务
- 最近素材
- 推荐路径

推荐路径示例：

- 先出设计方向 -> 再做图案提取 -> 再做连续纹理
- 先做营销主图 -> 再补细节图 -> 再出短视频

### 5.3 Module Workspace

`Design / Shoot / Toolbox` 统一使用同一个 `WorkspaceLayout`。

结构：

- 左栏固定宽度，承载模块分组和功能切换
- 中栏是表单主区
- 右栏是案例与结果区

顶部只保留：

- 当前模块名
- 当前功能名
- 一句简短动作说明

必须删除的旧内容：

- 大段模块 Hero
- 业务分组数量
- 专用 / 复用统计
- 当前能力 / 图片输入 / 执行方式信号卡
- 与用户动作无直接关系的解释型文案

## 6. 组件重构方案

现有 `ModuleWorkspacePage` 过重，承担了模块介绍、统计、视觉轨道、工作区容器等多种职责。
建议拆成 4 层：

1. `WorkspaceLayout`
2. `WorkspaceSidebar`
3. `WorkspaceComposer`
4. `WorkspacePreview`

### 6.1 WorkspaceLayout

职责：

- 提供稳定三栏布局
- 控制不同模块的壳层样式
- 管理窄屏折叠策略

### 6.2 WorkspaceSidebar

职责：

- 展示业务分组与功能菜单
- 展示当前激活项
- 只保留业务词，不出现链路类型

### 6.3 WorkspaceComposer

职责：

- 上传图像
- 输入提示词
- 选择模板
- 展开高级参数
- 提交任务

这里要从“字段渲染器”升级成“任务编排器”体验：

- 默认只显示必要字段
- 高级参数折叠
- 针对高频动作给出起手模板

### 6.4 WorkspacePreview

职责：

- 展示案例图
- 展示结果图
- 展示前后对照
- 展示“下一步推荐”

重点变化：

- 右栏不再只是“结果面板”
- 要同时承担“教育用户”和“承接结果”的职责

## 7. 数据与接口边界

前台仍然完全复用我们自己的中台接口，但要加一层前台解释层。

建议保留三层：

1. `abilityApi`
2. `workspaceRuntime`
3. `toolPresentationConfig`

职责划分：

- `abilityApi`：只负责接口请求
- `workspaceRuntime`：负责同步调用 / 异步任务 / 结果轮询 / 再来一次
- `toolPresentationConfig`：负责把能力映射成业务动作、模板文案、输入提示、案例说明

关键原则：

- 能力 key 不能直接等于用户可见产品名
- 前台动作名、空状态文案、推荐路径、案例文案都不该散落在页面组件里
- 模块信息、工具定义、业务话术、示例内容要变成统一配置层

## 8. 视觉系统重构原则

### 8.1 需要向 Style3D 靠拢的部分

- 顶部导航更轻、更稳
- 页面背景更干净
- 卡片数量减少
- 主视觉更集中
- 三栏工作台更稳定
- 表单与结果区之间的节奏更清晰

### 8.2 必须避免的部分

- 直接复制对方品牌素材
- 直接模仿对方 logo 或文案
- 使用大量竞品截图作为正式页面素材

### 8.3 我们自己的视觉方向

建议保留 `PODI` 的温暖感，但整体结构要更克制：

- 首页可保留有温度的大片图
- 工作区统一转为浅底、低噪声、强留白
- 色彩重点只保留 1 个主色和 1 个强调色
- 减少现在这种“很多段内容都像主角”的状态

## 9. 实施顺序

### Phase 1：先改骨架

- 重做 `TopNav`
- 新增 `StudioPage`
- 把 `Design/Shoot/Toolbox` 改成统一工作台壳
- 移除当前 `ModuleWorkspacePage` 的模块 Hero 与统计层

### Phase 2：再改工作区

- 重做左侧菜单
- 重做表单区信息层级
- 重做右侧案例 / 结果区
- 为高频功能增加起手模板与下一步推荐

### Phase 3：最后补首页与支撑页

- 重做 `Home`
- 收口 `Tasks / Assets / Wallet`
- 统一页面间导航关系和再来一次链路

## 10. 验收标准

重构完成后，至少满足以下判断：

1. 首页看起来像正式产品，而不是功能集合页。
2. 从任一模块进入后，用户可以在 3 秒内理解“左边选什么、中间做什么、右边看什么”。
3. 页面上不再出现明显的中台视角字段和统计。
4. 高频功能页能明显看出是“业务动作页”，不是“能力调用页”。
5. 即使不解释底层模型，用户也知道每个入口是干什么的。

## 12. 本轮结论

这次不是“继续把现有客户端做漂亮”，而是：

- 用现有中台接口
- 保留已经跑通的真实能力链路
- 把前台重新组织成 Style3D 式工作台产品

也就是说，后端链路尽量不推翻，前端骨架必须重搭。
