# 02. 角色任务地图

## 1. 角色拆分

当前页面的问题之一，是试图用同一套主界面同时服务所有人。
但实际上，至少存在 4 类明确角色：

1. 决策人
2. 业务测试
3. 产品
4. 开发

这 4 类人进入系统时，要完成的任务完全不同。

## 2. 决策人

### 进入目标

- 快速看懂哪些能力值得继续投入
- 看哪些能力已经可以拿去演示或推进
- 看当前主要风险在哪里

### 真正关心的信息

- 当前能力盘点
- 可演示 / 可商用数量
- 代表案例
- 高风险能力
- 近期优化进展
- 建议动作

### 不应该让他先看到的内容

- 参数表单
- 任务状态细节
- 接口文档
- 批量任务明细

### 适合的入口

- 首页总览
- 能力详情中的“概览 / 效果证据”

## 3. 业务测试

### 进入目标

- 判断这个能力是否可商用
- 判断在哪些场景可用、在哪些场景不稳定
- 沉淀可复盘的问题样本

### 真正关心的信息

- 标准样本集
- 代表好例、坏例
- 商用等级
- 不满意原因分布
- 批量通过率
- 导出能力

### 不应该让他先看到的内容

- 过多工程状态词
- 节点和调度信息
- 配置维护入口

### 适合的入口

- 首页总览
- 能力详情中的“效果证据”
- 批量回归

## 4. 产品

### 进入目标

- 判断这个能力当前值不值得继续做
- 找到问题主要集中在哪
- 形成下一版功能规划依据

### 真正关心的信息

- 能力适用场景
- 典型问题分类
- 版本变化趋势
- 失败样本分布
- 商用等级变化
- 需要补的能力或流程

### 适合的入口

- 首页总览
- 能力详情
- 批量回归报告

## 5. 开发

### 进入目标

- 快速看懂怎么接
- 看参数、错误、输出结构
- 判断接入成本和风险

### 真正关心的信息

- API 说明
- 参数 schema
- 请求 / 响应样例
- 输出类型
- 错误码
- 接入注意事项

### 不应该让他先看到的内容

- 长篇业务结论
- 大量打分卡片
- 模糊商用描述

### 适合的入口

- 开发接入页
- 能力详情中的“开发接入”标签

## 6. 角色与页面映射

| 角色 | 首选入口 | 第二入口 | 核心输出 |
| --- | --- | --- | --- |
| 决策人 | 首页总览 | 能力详情概览 | 是否继续投入 |
| 业务测试 | 首页总览 | 批量回归 / 效果证据 | 是否可商用、边界在哪 |
| 产品 | 首页总览 | 能力详情 / 批量回归报告 | 下一步做什么 |
| 开发 | 开发接入 | 能力详情接入标签 | 怎么接、风险在哪 |

## 7. 动线建议

建议未来的主路径统一改为：

```text
进入首页总览
  -> 选择一个能力或场景
  -> 先看结论与代表案例
  -> 再看批量证据或商用等级
  -> 最后进入测试或开发接入
```

这条路径的核心是：

- 先建立判断
- 再进入细节

而不是当前常见的：

```text
先选分类
  -> 先选工具
  -> 先填参数
  -> 先跑任务
  -> 最后自己总结结论
```

## 8. 本轮建议确认

- 是否认可这 4 类角色作为本次改版的主要服务对象
- 是否认可首页不再主要服务“操作”，而主要服务“判断”
- 是否认可开发入口应从主视图中独立出来
