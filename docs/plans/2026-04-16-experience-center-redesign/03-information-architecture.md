# 03. 信息架构草案

## 1. 新结构目标

新的信息架构要解决两个问题：

1. 主路径从“操作导向”切换为“判断导向”
2. 把不同角色真正需要的信息分层展示

## 2. 建议保留的 5 个核心区

1. 首页总览
2. 能力详情
3. 批量回归
4. 开发接入
5. 任务与证据

说明：

- 这 5 个区不是都要做成一级导航，但至少是结构上的 5 个核心内容区。
- “维护配置”可以保留，但不建议继续作为主体验路径的一部分。

## 3. 首页总览

### 职责

- 给所有角色建立全局判断
- 提供进入能力详情、批量回归、接入页的分发

### 首页建议模块

1. 能力总览
   - 全部能力数
   - 可演示数
   - 可试卖数
   - 可交付数
   - 高风险数

2. 焦点能力
   - 最近值得重点关注的能力
   - 带一行结论和状态

3. 商用分级看板
   - 各能力分布到哪个等级

4. 代表案例
   - 每个重点能力至少一个好例 / 坏例

5. 风险摘要
   - 失败率高的能力
   - 主要问题类型

6. 建议动作
   - 继续推进
   - 灰度验证
   - 暂缓投入

### 首页不建议出现的内容

- 大段表单
- 大量任务明细
- 配置维护入口
- 工程链路字段

## 4. 能力详情

### 职责

- 让用户在单个能力上形成完整判断

### 建议 4 个标签

1. 概览
   - 能力定位
   - 适用场景
   - 商用等级
   - 当前结论
   - 最近版本变化

2. 效果证据
   - 代表好例
   - 典型坏例
   - 边界案例
   - 常见失败原因
   - 最近批量结果摘要

3. 体验测试
   - 单次测试入口
   - 参数输入
   - 结果查看
   - 历史记录

4. 开发接入
   - API 文档
   - 参数 schema
   - 错误码
   - 请求 / 响应样例

### 设计原则

- 用户先看到“它值不值得继续看”
- 再看到“为什么”
- 最后才进入操作区

## 5. 批量回归

### 职责

- 把“批量提交工具”升级成“回归报告中心”

### 建议结构

1. 标准样本集选择
2. 能力 / 版本选择
3. 批次提交
4. 批次进度
5. 回归报告
   - 成功率
   - 可用率
   - 不满意率
   - 主要失败原因
   - 典型坏例
6. 导出
   - 全部对照集
   - 不满意样本
   - 问题样本

### 本区的核心变化

现在重点还是“跑任务”。
未来重点应改成“产出报告”。

## 6. 开发接入

### 职责

- 提供清晰、独立的开发视图

### 建议内容

1. 接口说明
2. 参数 schema
3. 请求示例
4. 响应示例
5. 错误码与边界
6. 接入注意事项

### 为什么单独拆出来

如果继续把开发信息塞在单能力测试页里，会同时伤害两件事：

- 业务同学会觉得页面太技术化
- 开发同学仍然需要在大页面里翻找

## 7. 任务与证据

### 职责

- 给需要追溯的人提供完整证据链

### 建议内容

1. 运行记录
2. 标注记录
3. 失败原因
4. 原图 / 结果 / 导出链接
5. 批量报告回溯

说明：

- 这个区应该成为“证据库”，不是主路径入口。
- 它服务的是追溯，而不是首页判断。

## 8. 页面关系

建议未来关系是：

```text
首页总览
  -> 能力详情
  -> 批量回归
  -> 开发接入
  -> 任务与证据

能力详情
  -> 体验测试
  -> 开发接入
  -> 批量回归
  -> 任务与证据
```

## 9. 结构评审建议

本轮建议重点确认：

- 是否接受 5 个核心内容区
- 是否接受能力详情按“概览 / 效果证据 / 体验测试 / 开发接入”组织
- 是否接受批量回归以后以“回归报告”为主输出
