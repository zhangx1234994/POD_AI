# 12. 单功能页交互说明

## 1. 页面目标

单功能页的目标是让用户顺手完成一次体验。
它不是“文档页”，也不是“历史管理页”。

## 2. 主交互链路

```text
进入功能页
  -> 看功能说明
  -> 上传素材 / 填主要参数
  -> 点击开始
  -> 在右侧看状态和结果
  -> 简单评分 / 留备注
```

## 3. 页面区块交互

### 区块 A：功能说明

要求：

- 打开页面就能看到
- 不需要滚动很久
- 文案简短

交互目标：

- 用户立刻知道这个功能适合测什么
- 用户立刻知道不适合测什么

### 区块 B：输入区

要求：

- 第一屏内完成核心输入
- 上传入口突出
- 主参数清晰
- 高级参数默认折叠

交互规则：

- 必填项缺失时，在字段附近提示
- 不要等点击提交后才整体报错
- 提交按钮始终清楚可见

### 区块 C：结果区

要求：

- 与输入区同时可见
- 当前状态清晰
- 最新结果优先展示

交互规则：

- 提交后立即进入“执行中”态
- 成功后自动滚动或聚焦到最新结果
- 失败后在结果区内给出可读错误

### 区块 D：轻量沉淀区

要求：

- 默认展示有限条目
- 不抢主体验流程

交互规则：

- 评分不应打断下一次体验
- 备注保存应有即时反馈
- 更多历史可单独展开

## 4. 页面状态

### 默认态

- 左侧输入、右侧结果占位都存在
- 用户知道从哪里开始

### 执行中

- 按钮禁用或进入 loading
- 状态区显示当前 run 正在处理
- 旧结果与新结果区分清楚

### 成功态

- 新结果成为结果区主内容
- 可直接放大查看
- 可立即打分 / 备注

### 失败态

- 错误贴近结果区
- 提供简短下一步建议

### 空历史态

- 不展示空表格
- 只提示“暂无记录”

## 5. 页面体验原则

### 原则 1：输入和结果必须同屏

如果输入区和结果区被长文档或长历史隔开，体验会明显变差。

### 原则 2：先完成一次体验，再谈复盘

页面结构必须优先支持“完成一次体验”，而不是优先展示过往内容。

### 原则 3：错误必须帮助继续操作

错误提示应包含：

- 发生了什么
- 用户先检查什么
- 是否建议重试

## 6. 功能页交互验收点

1. 用户进入页面后 5 秒内知道怎么开始
2. 第一屏内能完成核心输入
3. 输入和结果能同时看到
4. 结果成功和失败都能被清楚理解
5. 历史和文档不会打断主操作
