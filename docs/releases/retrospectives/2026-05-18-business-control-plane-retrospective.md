# 2026-05-18 业务控制面版本复盘

版本：`0f977db5 feat: stabilize business control plane`  
范围：backend、管理端、测评端、业务接口记录、业务编排只读图、发布 SOP  
线上环境：114 控制面，ComfyUI 执行节点 158/233  

## 1. 本版本目标

本版本原始目标不是单个页面优化，而是把“业务入口、业务运行、子步骤、能力调用、执行节点、OSS 回填、接口调用记录”串成一条能排查的主线。

最终完成：

- 业务接口调用记录补齐：业务方、内部巡检、服务令牌、平台登录都能进入“接口调用”清单。
- 管理端业务能力页改为按业务入口、业务链路、版本管理、治理记录分区。
- 业务链路图展示业务运行的子步骤和执行证据，隐藏不必要的 React Flow 水印。
- 测评端图裂变参数统一为“重绘幅度”，兼容旧 `similarity` 和“相似度”数据。
- 114 发布 SOP 跑通：源检查、测试、构建、部署、smoke、真实 ComfyUI 巡检。

## 2. 本版本暴露的问题

### 2.1 业务概念先后顺序不够清晰

现象：

- 业务能力页一度把“业务入口、版本、处理链路、接口调用清单”混在同一视角里。
- 图裂变版本较多，Coze 旧链路、ComfyUI 新链路、GPT Image 2 链路、保底链路不容易区分。
- 部分版本升级被展示成新功能，用户难以判断哪个是线上默认、哪个是测试版本。

根因：

- 设计时先按技术模块堆叠，而不是先框定业务动线。
- “新功能”和“版本升级”的判定规则没有形成硬约束。

修正：

- 业务入口保持稳定；同一业务目标默认按版本升级处理。
- 只有业务目标、输入输出、独立验收边界或计费边界变化时，才新增业务入口。
- 页面必须先回答：业务方调哪个入口、线上默认跑哪个版本、这次 runId 背后跑了哪些步骤。

### 2.2 逐功能上线检查不足

现象：

- ComfyUI 参数曾出现错传风险，服务健康和接口返回都无法发现。
- “相似度”文案残留在部分测评端入口，和实际 denoise / 重绘幅度语义相反。
- 功能名、角标、发布时间、更新时间、版本说明曾存在不一致。

根因：

- 检查粒度偏服务级，没有按功能逐项核对参数名、默认值、枚举值、页面文案、实际 payload、执行节点和结果回填。

修正：

- 每个功能上线前必须按 `docs/standards/per-feature-release-checklist.md` 检查。
- 图裂变类功能必须检查“重绘幅度”口径，不能出现“相似度”。
- 交付包迭代默认视为版本更新；如果不确定是版本更新还是新功能，必须先确认。

### 2.3 对“真实测试”的口径一度不严格

现象：

- 一度把第三方模型和 ComfyUI 都按“可选消耗”看待。
- 用户纠正：第三方商业模型可以按成本跳过，但 GPU/ComfyUI 是自有能力，必须跑真实链路。

根因：

- 测试策略没有区分“商业模型额度”和“自有 GPU 执行面”。

修正：

- ComfyUI/GPU 核心业务上线必须至少跑一条真实任务。
- 第三方商业模型如果跳过，必须明确写“因成本/额度跳过”，并保留路由、契约和错误路径检查。
- 真实业务巡检必须确认执行节点、结果图、OSS 回填和接口调用记录。

### 2.4 业务流程和技术流程曾混淆

现象：

- 排查时容易先看底层能力日志，而不是先从业务 runId 入口走完整业务链。
- 对“回调”和“轮询”的表达曾产生歧义。

根因：

- 业务方视角和平台内部排障视角没有分层。

修正后的业务流程：

1. 业务方提交业务 API 或 Coze 工具箱。
2. 平台返回 `runId` 或兼容 `taskId`。
3. 业务方按同一个编号轮询结果。
4. 平台把 VL、ComfyUI、OpenAI、评分、回填、回调都记录为这次业务调用的子步骤。
5. 管理端按 runId 展示入口调用、处理步骤、执行节点、结果和错误。

技术排查只能跟随这条业务流程向下钻，不能反过来只看某个能力日志判断业务是否成功。

### 2.5 接口调用记录曾漏掉内部请求

现象：

- 真实 ComfyUI 巡检出图成功，但接口调用清单显示 `NO_ENTRY_LOG`。

根因：

- 原逻辑只在业务 API Key 鉴权时写 usage context；内部请求、服务令牌、平台登录会跳过使用记录。

修正：

- 所有业务入口统一补齐使用记录上下文。
- 巡检通过标准增加：提交 1 条、轮询若干条都能按 `runId/requestId/traceId` 聚合。

### 2.6 线上视觉检查不应只看页面能打开

现象：

- 发布后第一次页面检查时，管理端还在加载能力数据时被跳转，出现 `Failed to fetch`，容易误判为生产包问题。
- 之前也出现过 build 通过但静态包运行时报错的问题。

根因：

- 页面检查需要独立页面、足够等待、记录控制台和 4xx/5xx 响应；不能混在一个浏览器页里快速跳转。

修正：

- 管理端、测评端分开打开，等待网络稳定后检查。
- 检查项至少包含：页面非空、核心文案存在、无生产运行时错误、无关键接口 4xx/5xx、旧错误文案不再出现。

### 2.7 发布脚本源检查受网络波动影响

现象：

- 第一次发布时，脚本 30 秒内没有完成 `git fetch origin/main`，被源检查挡住。
- 单独 fetch 随后成功。

根因：

- GitHub 网络波动不等于代码错误，但正式发布仍必须确认 `HEAD == origin/main`。

修正：

- 网络不稳时先单独 `git fetch origin main`，再用 `GIT_FETCH_TIMEOUT_SECONDS=120` 重跑发布。
- 不允许因为 fetch 慢就跳过真源校验，除非明确记录为紧急例外。

### 2.8 巡检结果和验收记录写入结果不能混为一谈

现象：

- 真实 ComfyUI 图裂变已成功，但写入发版巡检记录时因为没有带服务令牌返回 401。

根因：

- `patrol_business_api.py` 的业务结果和管理端记录写入是两个动作。

修正：

- 业务结果以 `results[].ok` 和最终 run 状态为准。
- 验收记录写入失败时，用服务令牌补录；不重新跑 GPU 任务制造重复成本。

### 2.9 服务器命名和路由讨论必须精确

现象：

- “117 服务器”这个说法不清楚，可能指 158 或 233。
- 233 因安全加固缺节点时，曾考虑从平台侧长期特殊路由规避。

根因：

- 能力机命名和平台路由策略没有强制精确表达。

修正：

- 以后所有 ComfyUI 机器必须写清：`158/5090/117.50.80.158` 或 `233/4090/117.50.216.233`。
- 缺节点优先修服务器同构；只有止血时才临时路由限制，并写明恢复条件。

## 3. 本次被纠正后的硬规则

- 业务流程排查必须从业务入口和 runId 开始，再向下看子步骤、能力日志、执行节点。
- ComfyUI/GPU 自有链路上线必须真实跑图；第三方商业模型可以因成本跳过，但要写清跳过原因。
- 同一业务目标默认做版本升级，不默认新增功能；不确定时必须先确认。
- 功能名称不能随意改；“新版”只能做角标，不能做功能名。
- `bili` / `similarity` / 旧“相似度”在图裂变语境下统一叫“重绘幅度”。
- 业务接口默认轻量返回；完整排障字段只给管理端或 `detail=full`。
- 接口调用清单必须能看到提交、轮询、回调或结果查询。
- 发布后页面检查必须分页面、等网络稳定、看控制台，不允许只看页面能打开。
- 158 和 233 必须精确命名，不再说“117 那台”。
- 不为了单个服务器问题长期增加平台特殊控制点；优先保持执行节点同构。

## 4. SOP 已同步优化

已同步到：

- `docs/standards/release-sop.md`
- `docs/standards/per-feature-release-checklist.md`
- `docs/standards/issue-improvement-log.md`

新增或强化的 SOP 规则：

- 上线前必须写清本次是“新功能”还是“版本升级”。
- ComfyUI 类功能必须真实跑一条业务链路。
- 线上页面走查必须分开管理端和测评端，独立检查控制台。
- 业务巡检报告里 `acceptanceResults` 不能反向污染业务是否成功。
- 发布源检查遇到网络抖动时，放宽 fetch 超时，不直接绕过真源校验。
- 业务接口调用记录必须能按 `runId` 聚合提交和轮询。

## 5. 下一阶段需要继续改善

- 业务链路控制点仍偏多，需要继续收敛为“业务版本配方是唯一真源”。
- 管理端业务编排目前仍以只读展示为主，后续应引入可编辑的工作流编排能力。
- 计费和账单目前是框架阶段，不应阻断当前业务验收，但正式商业化前必须收紧。
- 业务接口清单、接口调用清单、能力调用清单要进一步统一口径，让用户能从业务入口一路钻到能力日志。
- 测评端仍需要按业务分类和沉浸式结果浏览继续产品化。
