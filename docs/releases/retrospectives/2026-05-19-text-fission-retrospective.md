# 2026-05-19 文字强化裂变（文生图）返工复盘

范围：`text_fission` 业务接口、测评端两步交互、ComfyUI 文生图执行链、接口文档和发布验证。  
当前结论：功能链路已经打通并上线，但这个功能耗时明显偏高。主要原因不是单点代码复杂，而是前期没有先把业务形态、接口契约、页面交互、参数真源和验收清单一次性框死，导致多次小返工叠加。

## 1. 功能最终口径

- 业务名称固定为：文字强化裂变（文生图）。
- 业务键固定为：`text_fission`。
- 当前版本固定为：`qwen2512-text2img-v1`。
- 接口形态固定为两步：
  - 第一步：`POST /api/business/text-fission/prompts`，只负责用 VL 生成可编辑提示词草稿。
  - 第二步：`POST /api/business/text-fission/runs`，只接收用户确认后的 `editable_prompt` 并提交 ComfyUI 文生图。
- 第二步不再二次调用 VL。
- 单个 run 固定出 1 张图。
- `steps`、`cfg`、`seed`、采样强度等内部参数不暴露给用户。
- `width` / `height` 不传时跟随原图；手动传入时才覆盖。
- 纯文生图对中文密集图的逐字复刻不稳定，这是工作流/模型质量边界，不应误判为中台链路故障。

## 2. 返工点归因

| 返工点 | 现象 | 直接原因 | 深层原因 | 防复发动作 |
| --- | --- | --- | --- | --- |
| 功能定性和命名反复 | 先后出现 `text_fission`、`text2img-user-editable`、`新版` 等表达，测评端名称也调整多次。 | 接入时没有先确认这是“文字强化裂变”的一个新业务形态，而不是普通旧功能修补。 | 新功能/版本升级判定规则虽然已讨论，但执行前没有强制落到一页规格说明。 | 新能力开工前必须先写“功能定性卡”：业务名、版本、入口、是否替代旧版本、是否新增业务边界。 |
| 两步式业务流程没有先画清 | 第一步 VL 生成提示词、第二步生图的前后关系一开始没有在测评端和接口文档里统一。 | 后端先实现接口，测评端再补交互，导致状态流和字段流后置处理。 | 对“两步式带人工编辑”的功能缺少固定状态机模板。 | 两步式功能必须先定义状态机：待原图、生成草稿、待用户确认、提交生图、轮询结果、失败重试。 |
| 测评端提示词不回填 | 用户点击“先识别提示词”后，生成提示词没有稳定填入输入框。 | 前端字段名、后端返回字段、代理接口之间存在 `editablePrompt` / `editable_prompt` 等映射差异。 | 第一阶段没有把第一步响应字段作为强契约测试；只验证接口成功，没有验证 UI 状态更新。 | 所有“中间态回填”必须有契约测试和页面走查：返回字段、前端赋值、按钮状态、错误提示一起测。 |
| 测评端提示“服务异常”但没有第一时间定位 | 页面出现服务异常 toast，实际链路还需要继续追踪是代理、鉴权、字段还是后端异常。 | 先从代码局部猜测，没有第一时间按浏览器请求、接口响应、后端日志、业务记录四段排查。 | UI 问题缺少固定排查路径。 | 测评端交互异常先按四段查：浏览器网络请求 -> eval 代理接口 -> backend 业务接口 -> 数据库业务记录。 |
| 用户参数暴露过多 | 采样步数、强度、随机种子等一度进入交互或接口讨论。 | 从 ComfyUI 工作流参数向外复制，没有先按业务用户视角筛选。 | 原子工作流参数和业务 API 参数边界没有前置评审。 | 对外业务参数只保留用户能理解并能决策的字段；内部参数必须写入“隐藏参数清单”。 |
| 缺少 `editable_prompt` 时仍创建 queued 脏任务 | 第二步缺提示词能返回错误，但数据库里已留下 queued 业务任务。 | 校验发生在创建 `BusinessRun` 之后。 | 测试只看 HTTP 错误码，没有检查失败请求的副作用。 | 错误路径测试必须检查“不创建任务、不创建步骤、不扣费、不回调”。 |
| 对外返回体过重 | 业务方反馈返回 JSON 太重，包含太多内部步骤和排障信息。 | 管理端排障视角和业务方接入视角混用了同一套返回。 | 轻量返回和调试返回的边界没有在接口设计阶段锁定。 | 对外默认轻量返回；调试字段只能通过 `detail=full`、`includeDebug=true` 或管理端接口返回。 |
| VL 输出结构展示不稳定 | 模型返回的 `text_content` 等结构化字段有数组/对象/字符串差异，页面展示容易异常。 | 对模型返回结构没有统一归一化。 | 第三方/VL 返回是弱结构，不能直接穿透给业务页面。 | 所有模型结构化输出进入页面前必须归一化为展示安全结构。 |
| 默认尺寸错误为 1024x1024 | 线上测试发现原图为横图，但输出变成 1024x1024。 | `business_seed`、`eval_seed`、接口示例里存在 1024 默认值；后端没有兜底读取原图尺寸。 | 尺寸控制点散落，缺少“默认值来自哪里”的单一真源，也缺少宽高枚举测试。 | 运行时以后端业务 payload 为最终真源；测评端和文档不再写会改变行为的默认宽高；测试覆盖“不传宽高跟随原图”。 |
| 实际 payload 没有第一时间作为验收物 | 多次问题都需要最后去查能力日志才确认参数是否真正传到 ComfyUI。 | 上线检查先看接口成功和结果图，没有强制核对执行 payload。 | 图像业务参数问题不会被健康检查发现，必须看执行节点入参。 | 图像业务上线必须核对：业务请求参数、业务步骤 request_payload、能力日志 request_payload、ComfyUI 节点参数。 |
| 质量问题和链路问题混在一起 | 文生图能成功出图，但文字清晰度和实验室效果有差距。 | 中台链路问题、提示词问题、工作流质量问题没有分层记录。 | 质量评估标准没有在接入阶段定义。 | 接入完成只证明链路可用；质量问题单独进入样本包和工作流迭代，不阻塞链路验收但必须标注风险。 |
| 发布 smoke 被历史治理项拦截 | 代码已部署成功，但 smoke 因 `fission:v1` 缺验收记录、执行节点问题未复测而失败。 | 业务治理门禁记录不完整。 | 发布前没有先跑“治理门禁预检查”，导致发布阶段才发现历史数据阻断。 | 正式发布前先跑 smoke 或等价预检查；历史验收、未复测问题、计费观察项必须在发布前收口或明确豁免。 |

## 3. 根因分类

### 3.1 没有先定完整契约

这次返工最多的位置都和契约有关：名称、两步流程、字段、默认值、返回体、错误副作用。代码并不难，但如果契约没有先固定，后端、测评端、文档和测试会反复追着改。

后续规则：

- 新业务能力开工前先写 1 页规格说明。
- 规格说明至少包含：业务名、业务键、版本、是否替代旧版本、接口、入参、出参、错误码、默认值、隐藏参数、测评端流程、真实测试用例。
- 规格说明没有确认前，不开始写后端和前端实现。

### 3.2 控制点分散

本次尺寸问题暴露最明显：同一个默认宽高同时存在于业务 seed、测评 seed、OpenAPI 示例、前端表单和后端 payload 构造中。只改一个地方无法保证最终行为正确。

后续规则：

- 运行时行为以后端业务 payload 为最终真源。
- seed 只负责初始化和同步，不允许成为唯一运行兜底。
- 前端只展示和采集，不写会改变业务语义的隐性默认值。
- 文档示例不能和运行默认值冲突。
- 每个新增参数必须补到控制点矩阵，说明哪里是源头、哪里是派生、哪里只是展示。

### 3.3 测试只覆盖“接口成功”，没有覆盖“业务闭环”

接口返回 200、页面能打开、任务能成功，都不能证明功能合格。本次至少需要同时验证：

- 第一步返回的提示词是否能回填。
- 第二步是否必须携带用户确认后的提示词。
- 缺提示词是否不创建脏任务。
- 不传宽高是否跟随原图。
- 手动传宽高是否覆盖。
- 实际 ComfyUI payload 是否收到正确参数。
- 业务列表、能力调用记录、接口调用记录是否能按 runId 串起来。

后续规则：

- 新业务能力必须有枚举测试用例。
- 测试报告必须包含“业务请求 -> 业务记录 -> 子步骤 -> 能力日志 -> OSS 结果 -> 页面展示”。
- 图像能力必须至少跑一条真实 ComfyUI 任务。

### 3.4 页面交互验证介入太晚

用户多次通过页面发现问题，例如提示词未回填、服务异常、参数文案和结果展示不清晰。说明开发过程中页面走查不够早，且没有按用户操作路径走。

后续规则：

- 后端接口完成后，必须立即走测评端真实页面，不等“全部做完再看前端”。
- 页面验收按用户动作，不按技术模块：上传图片 -> 生成草稿 -> 修改提示词 -> 提交 -> 轮询 -> 看结果 -> 看历史。
- 页面错误提示必须用业务语言，底层异常只进入调试区。

## 4. 新增检查表

后续所有“两步式图像业务能力”必须逐项核对：

| 检查项 | 必须回答的问题 |
| --- | --- |
| 功能定性 | 这是新业务、新版本，还是旧版本修补？是否会改业务方入口？ |
| 状态机 | 是否有中间态？中间态字段如何回填？失败后能否重试？ |
| 参数边界 | 哪些是用户参数？哪些是内部参数？哪些字段必须隐藏？ |
| 默认值 | 默认值来自哪里？不填字段的行为是否有测试？ |
| 返回契约 | 业务方轻量返回是什么？调试版返回是什么？ |
| 错误副作用 | 缺参、依赖失败、超时、并发限制是否不会留下脏任务？ |
| 真实 payload | 能否从能力日志证明参数传到了执行节点？ |
| 页面闭环 | 测评端是否完成上传、生成、编辑、提交、结果、历史全链路走查？ |
| 记录闭环 | 管理端是否能按 runId 看到接口调用、业务任务、处理步骤、能力调用？ |
| 文档闭环 | 接口文档、错误码、枚举表、测评端文案是否一致？ |
