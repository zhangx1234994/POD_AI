# 复盘记录（2026-02-24）

## 背景
- 管理端“能力调用清单”出现“状态 success 但结果列无预览”的感知问题。
- 同一批数据中，部分记录展示了执行器耗时（`response_payload.durationMs`），与全链路耗时（`duration_ms`）口径不一致，容易误判任务是否已完成。

## 本次修复
- 前端统一状态文案与颜色映射（成功/失败/执行中/排队中/已取消），兼容 `success/succeeded/completed/...`。
- 前端统一结果预览解析顺序：`stored_url` → `result_assets` → `response_payload.assets/images/resultUrls/imageUrls/imageUrl`。
- 前端统一耗时展示口径：优先 `duration_ms`（全链路），仅历史脏数据时回退 `response_payload.durationMs`。
- 成功但暂未解析到预览地址时，结果列显示“结果回填中”，避免误导为无结果。
- 后端日志提取兜底增强：`AbilityLogService` 额外支持从 `images/resultUrls/imageUrls` 提取 `stored_url/result_assets`。
- 补充统一规范文档：`docs/standards/interface-consistency.md`，并同步到 API 文档、评测开发文档、AGENTS 纲领。
- 修正历史文档偏差：`/api/tasks/v1/*` 实际仍为兼容链路，文档改为“保留兼容 + 新功能统一走 /api/ability-tasks”。

## 结论
- “完成”定义保持不变：任务状态由链路执行结果决定（success/failed 等）。
- “可预览”是展示层结果回填状态；与“任务完成”分离展示，避免概念混淆。

## 后续建议
- 对历史存量日志补一轮“回填脚本”（从 `response_payload` 回填 `stored_url/result_assets`），减少旧数据出现“成功但无预览”。
- 管理端加一项快速筛选：`状态=成功 且 预览缺失`，便于巡检。
