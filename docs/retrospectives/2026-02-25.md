# 复盘记录（2026-02-25）

## 背景
- LoRA 批量测试在夜间长时间显示“运行中”，白天仍持续占用算力，影响正常业务。
- 操作侧感知混乱：上传慢、页面频繁刷新、无法明确判断“是否已开始执行”，导致重复点击触发重复批次。

## 事实与影响
- 异常批次（已清理）：
  - `batch_1771920989745_9de9512d`
  - `batch_1771920650581_80f7e833`
- 直接影响：
  - 夜间测试结果不可用，人工投入无产出。
  - 白天算力被无效占用，挤压线上正常任务。
  - 用户对系统状态可信度下降（“到底在跑还是卡住”不可判断）。

## 根因
1) **后端状态模型口径错误（核心）**
- 位置：`backend/app/routers/evals_public.py:232`
- 现状：`planned_run_count = planned_image_count * repeat_count`，将“上传失败素材”也计入计划总量。
- 结果：当存在上传失败时，即便所有可执行任务都结束，也可能永远达不到计划总数，批次长期停留在 `running`。

2) **上传与执行阶段可观测性不足**
- 用户无法一眼区分“上传中 / 待提交 / 已提交 / 执行中 / 已完成”。
- 轮询刷新叠加导致页面抖动，进一步放大“不确定感”。

3) **防重复提交约束不够强**
- 用户在不确定状态下再次点击，系统会创建新的同类批次，形成重复执行。

## 本次处置
- 已清理异常批次及关联运行记录，释放算力，避免继续产生脏数据。
- 后端已修复批次状态机口径：计划总量改为“上传成功素材 × 重复次数”，并补充单元测试覆盖上传失败场景。
- 后端已增加“单活批次”保护：同一创建者存在进行中批次时拒绝新建，返回 `BATCH_ACTIVE_EXISTS`。
- 明确后续修复方向：前端分阶段交互、重复提交幂等、异常批次自动兜底。

## 统一改进动作（必须落地）
1. 状态机修正：计划总数以“可执行素材”为准，上传失败作为终态分支参与结算。
2. 交互分层：上传/提交/执行分三段展示，状态词统一，降低误判概率。
3. 重复提交保护：同一批次增加幂等键与后端防重。
4. 自动巡检：增加“长时间 running 且无活动项”的批次巡检与自动告警。
5. 上线门禁：批量功能上线前必须通过“高失败上传 + 大批量 + 网络抖动”场景回归。

## 经验教训
- 批处理功能不能只看“通路能跑”，必须先做“状态机真值表”。
- “可执行总量”与“上传总量”是两个概念，不能混算。
- 任何夜间长跑任务都必须有可解释、可恢复、可终止的闭环。
