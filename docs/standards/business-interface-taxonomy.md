# 业务分类与接口形态准则

## 目标

把中台接口从“技术来源分类”改为“业务分类优先”。

用户、测评端、管理端 API 开放页首先看到的是业务要解决什么问题，而不是 Coze、ComfyUI、KIE、OpenAI 或某个工作流 ID。技术来源只作为同一业务下的实现形态和排障信息。

## 一、分类总原则

1. 一级分类必须是业务意图，不是模型厂商、执行节点或接口类型。
2. 每个业务分类下可以同时存在 Coze 接口、原生接口、原子能力接口和测评入口。
3. 原生业务 API 是长期主入口；Coze 工具箱是业务接入和实验入口；原子能力 API 是内部编排和高级开发入口。
4. 测评端分类必须镜像业务分类；“通用”只能作为临时兜底，不能长期承载可命名业务。
5. 新增接口必须先确定业务分类，再确定接口形态，最后才确定底层执行器。

## 二、业务分类字典

以下分类是当前平台的统一命名。前端展示用中文，接口和配置用 `key`。

| 中文分类 | key | 业务含义 | 当前状态 | 典型能力 |
| --- | --- | --- | --- | --- |
| 花纹提取 | `pattern_extract` | 从商品或素材图中提取可复用花纹资产 | 核心主业务 | 印花提取、LoRA 提取版、VL 辅助提取 |
| 图裂变 | `image_fission` | 基于原图生成变化图、风格变体或高质量裂变图 | 核心主业务 | E7 裂变、多元素花纹裂变、四方裂变 |
| 扩图 | `outpaint` | 向上下左右扩展画面，补背景和构图 | 核心主业务 | FLUX2-Klein 扩图、花纹扩图 |
| 连续图 | `seamless_pattern` | 生成或检查两方、四方连续图 | 重要业务 | 四方连续、两方连续、连续图检查 |
| 抠图 | `cutout` | 移除背景或提取局部主体 | 处理类业务 | 背景抠图、头部抠像 |
| 图像融合 | `image_composition` | 多图融合、参考图合成、主体替换 | 处理类业务 | 多图融合、参考图融合 |
| 图像增强 | `image_enhancement` | 放大、DPI、清晰度、尺寸修复 | 原子能力为主 | 高清放大、DPI、resize、锐化 |
| 图像理解 | `vision_analysis` | 用 VL 模型分析图片结构、元素、风格和风险 | 弹药库能力 | VL 图像分析、标签、提示词建议 |
| 文本与提示词 | `text_prompt` | 文本增强、提示词生成、描述改写 | 辅助业务 | 文字增强、提示词优化、图像描述 |
| 生视频 | `video_generation` | 文生视频、图生视频、商品短视频 | 后续扩展 | Seedance、Sora、KIE 视频 |
| 平台工具 | `platform_tools` | 查询、队列、LoRA、模型目录、任务追踪 | 内部工具 | tasks/get、queue-summary、LoRA catalog |

约束：

- `platform_tools` 不进入业务公开目录，只进入管理端或内部测评。
- `image_enhancement` 中的高清放大等重任务必须继续遵守执行面拆分，不允许回落到 Coze 主机。
- 任何新能力如果暂时放入“通用”，必须在同一版本中写明后续归类，否则视为分类不完整。

## 三、接口形态分层

同一个业务分类下允许多种接口形态并存，但名称、文档和页面必须明确区分。

| 接口形态 | 面向对象 | 入口示例 | 是否长期主入口 | 说明 |
| --- | --- | --- | --- | --- |
| 原生业务 API | 业务方、客户端、MCP、技能、Coze 新工作流 | `/api/business/{business}/runs` | 是 | 标准提交、查询、回调、版本、灰度、统计入口 |
| Coze 工具箱 API | Coze 工作流、已有业务接入 | `/api/coze/podi/.../openapi.json` | 兼容保留 | 不承载长期业务逻辑，逐步调用原生业务 API |
| 原子能力 API | 内部编排、高级开发、测评、管理端 | `/api/abilities/{abilityId}/invoke` | 否 | 直接暴露底层能力，允许技术参数更多 |
| 管理端 API | 平台管理员 | `/api/admin/...` | 管理入口 | 管版本、配置、节点、密钥、日志、验收 |
| 测评 API | 内部测评人员 | `/api/evals/...` | 测试入口 | 用于验证业务和能力，不作为业务方正式接入 |

硬性规则：

- 对外给业务方的正式文档优先写原生业务 API。
- Coze 工具箱可以保留原工作流入参和回调方式，但文档中必须标明所属业务分类。
- 原子能力 API 不直接给普通业务方使用，除非明确该业务方具备高级开发能力。
- 同一能力同时有 Coze 和原生 API 时，管理端页面必须放在同一业务分类下，不允许分散到两个孤立列表。

## 四、原生业务 API 标准

每个进入“业务 API”的能力，必须具备以下最小接口：

| 接口 | 用途 | 必须程度 |
| --- | --- | --- |
| `POST /api/business/{business}/runs` | 提交业务任务 | 必须 |
| `POST /api/business/runs/get` | 按 `runId` 查询结果 | 必须 |
| `POST /api/business/{business}/route-preview` | 不消耗任务，预览命中版本 | 必须 |
| `GET /api/business/openapi.json` | 对外 OpenAPI 汇总 | 必须 |
| `GET /api/business/capabilities` | 业务版本与发布时间 | 必须 |

返回字段必须稳定：

- `runId`
- `status`
- `imageUrls`
- `videoUrls`
- `texts`
- `assets`
- `error`
- `debugUrl`
- `routeInfo`
- `flowSummary`

错误必须覆盖：

- 缺少主图或关键参数
- 业务版本不可用
- 执行节点不可用
- 队列或并发已满
- 上游超时或失败
- 成功但无结果回填
- 回调失败

## 五、Coze 工具箱归属标准

Coze 工具箱不再单独作为业务分类。每个工具箱必须挂到一个业务分类下。

命名建议：

```text
{业务分类} · Coze 工具箱 · {版本或用途}
```

示例：

- `图裂变 · Coze 工具箱 · 高质量多元素花纹`
- `扩图 · Coze 工具箱 · FLUX2-Klein`
- `抠图 · Coze 工具箱 · 背景抠图`

维护规则：

1. 新 Coze 工具箱优先调用原生业务 API；只有底层原子能力尚未业务化时，才允许直接调用原子能力。
2. 已上线旧 Coze 工作流保持兼容，不强制立即替换。
3. 工具箱 OpenAPI 字段变更必须同步测评端、管理端 API 开放页和错误码文档。
4. Coze 工具箱不得直连 ComfyUI、vendor-api-ops 或 image-ops。

## 六、测评端分类标准

测评端一级分类必须使用业务分类字典的中文名，建议按以下顺序：

1. 花纹提取
2. 图裂变
3. 扩图
4. 连续图
5. 抠图
6. 图像融合
7. 图像增强
8. 图像理解
9. 文本与提示词
10. 生视频
11. 平台工具

现有“通用类”需要拆分：

| 当前桶 | 应拆到 | 判断依据 |
| --- | --- | --- |
| 通用图片编辑 | 图像融合 / 图像增强 / 抠图 | 看输出是合成、增强还是抠图 |
| VL 或图像描述 | 图像理解 | 输出为结构化分析、标签、描述 |
| 文字增强 | 文本与提示词 | 输出为文本或提示词 |
| LoRA 查询、队列、任务追踪 | 平台工具 | 不产生业务素材 |
| 商业模型临时试验 | 按业务意图归类 | 不按厂商归类 |

测评卡片必须展示：

- 业务分类
- 接口形态：Coze / 原生业务 API / 原子能力
- 角色：生产主入口 / 灰度对照 / 历史保留 / 辅助工具
- 发布时间
- 最近一次测试状态
- 输出类型：图片 / 视频 / 文本 / 结构化结果 / 普通资源

## 七、管理端 API 开放页标准

管理端 API 开放页必须按业务分类组织，而不是按技术来源平铺。

推荐结构：

```text
花纹提取
  - 原生业务 API
  - Coze 工具箱
  - 原子能力
  - 测评入口

图裂变
  - 原生业务 API
  - Coze 工具箱
  - 原子能力
  - 测评入口

扩图
  - 原生业务 API
  - Coze 工具箱
  - 原子能力
  - 测评入口
```

每个业务分类卡片必须能回答：

- 业务方应该接哪个接口？
- Coze 现在用哪个工具箱？
- 原生业务 API 是否已经可用？
- 当前默认版本是什么？
- 最近测试是否成功？
- 失败时看哪个 `runId/taskId/logId`？

## 八、新能力接入流程

新增能力必须按以下顺序执行：

1. 确定业务分类 `businessKey`。
2. 判断是否需要成为原生业务 API。
3. 若先走 Coze，仍需挂到业务分类下。
4. 若只是内部工具，归入 `platform_tools`，默认不进入公开测评。
5. 补原子能力定义、输入 schema、输出类型和错误码。
6. 补测评端分类、角色、发布时间和最近测试状态。
7. 补管理端 API 开放页入口。
8. 补文档和 smoke 清单。

不允许的做法：

- 先按厂商建分类，例如“OpenAI 类”“KIE 类”。
- 先按技术链路建分类，例如“ComfyUI 类”“Coze 类”。
- 把新能力长期放在“通用类”。
- 只加 Coze 工具箱，不登记业务分类和测试入口。

## 九、当前阶段结论

当前三条主业务已经明确：

- 花纹提取：原生业务 API 已存在，需要继续完善接口展示和测评映射。
- 图裂变：原生业务 API 已存在，需要继续把 Coze 工具箱和测评工作流收拢到同一业务视图。
- 扩图：原生业务 API 已存在，需要继续把旧花纹扩图和 FLUX2-Klein 扩图的版本关系讲清楚。

下一阶段优先级：

1. 先把测评端“通用类”拆成可理解的业务分类。
2. 再把管理端 API 开放页改为业务分类视图。
3. 最后逐步补齐更多原生业务 API，而不是继续只堆 Coze 工具箱。
