# 中台业务主线契约

## 目标

本文件固定中台的业务动线，解决“业务任务、能力调用、Coze 工作流、测评记录、接口调用记录混在一起”的问题。

所有后续页面、接口、测试、文档和排障都必须按这条主线组织：

```text
调用方
  -> 业务入口
    -> 业务任务 runId
      -> 业务版本 / 编排配方
        -> 处理步骤
          -> 原子能力 / 模型 / ComfyUI / 第三方 API
        -> 结果回填 / 轮询 / 可选回调
      -> 计费 / 验收 / 复测 / 回滚证据
```

## 1. 唯一主线

业务主线的详细编排改造规划见 `docs/strategy/business-orchestration-control-plane-v1.md`。该规划固定下一阶段原则：业务版本和 `recipe` 是编排真源，测评端、Coze 和文档只做读取、展示或调用，不再各自维护一套业务流程。

### 1.1 业务调用是主线

一次业务接口调用必须落成一条业务任务：

- 主键：`runId`
- 对外状态：`queued` / `running` / `succeeded` / `failed`
- 对外结果：`imageUrls` / `videoUrls` / `texts` / `resultPayload`
- 对外错误：`errorCode` / `errorMessage` / `debugResponse`

管理端、测评端、业务交付文档都必须把 `runId` 当作第一排障主键。

### 1.2 处理步骤只能挂在业务任务下面

以下内容都不是一级业务任务，只能作为 `runId` 下的处理步骤或证据：

- API Key 入口调用记录、提交记录、轮询记录
- VL 图像理解
- ComfyUI 工作流执行
- OpenAI / 火山 / KIE / 百度等第三方模型调用
- image-ops 原子能力
- 结果上传 OSS
- 回调业务方
- 计费扣减
- 裂变评分

这些记录可以在“处理步骤”里查，但不能用来替代“接口任务清单”判断业务是否成功。

业务配方治理必须覆盖所有可执行步骤，不只检查主能力。步骤能力缺失、未启用、步骤编号重复、主步骤和 `primaryAbilityId` 不一致，都应在业务版本治理状态里提前暴露，避免运行时才发现中间节点断链。

### 1.3 Coze 是调用方，不是业务真源

Coze 工作流可以继续作为业务接入和实验入口，但在中台口径里只属于调用方之一。

新能力优先沉淀到业务 API，再让 Coze 调用业务 API。旧 Coze 工作流继续兼容，但不能反向决定中台业务模型。

## 2. 标准业务动线

### 第 1 步：选业务入口

业务入口必须先归类到业务字典：

| 中文业务 | 标准 key | 说明 |
| --- | --- | --- |
| 花纹提取 | `pattern_extract` | 从原图提取可复用花纹资产。 |
| 图裂变 | `fission` | 基于原图生成变化图、风格变体或高质量裂变图。 |
| 裂变评分 | `fission_evaluate` | 评估裂变结果质量和逻辑合理性，通常作为图裂变后的质检环节。 |
| 扩图 | `outpaint` | 向外扩展画面，补背景和构图。 |

兼容说明：历史 `image_fission` 只作为 `fission` 的别名，页面展示和新数据必须使用 `fission`。

### 第 2 步：提交任务

业务方、Coze、测评端或管理端提交任务后，中台必须创建业务任务并返回 `runId`。

推荐入口：

- `POST /api/business/{business}/runs`
- `POST /api/business/runs/get`

兼容入口：

- `/api/coze/podi/tasks/get` 可以用业务 `runId` 查询，但正式交付仍推荐 `/api/business/runs/get`。

### 第 3 步：选择版本和编排

业务任务必须记录：

- `businessKey`
- `version`
- `businessVersionId`
- `selectedBy`
- `recipeSteps`

页面必须能回答：

- 当前业务默认版本是谁？
- 有没有灰度或指定版本？
- 新版本是替换旧版本，还是新增一个业务能力？
- 底层由哪些处理步骤组成？

版本归属必须先判定清楚：

- 能解释为同一业务目标的，优先作为同一业务的版本升级。
- 只有业务目标、输入输出、接入方式或计费验收边界发生明显变化时，才新增业务入口。
- 例如普通图裂变的 ComfyUI 修补、GPT Image 2 替换、VL 提示词优化都属于 `fission` 的版本；“裂变四方”同时具备裂变和四方连续特性，可以作为新分类或独立业务入口讨论。
- 页面上技术路线只能作为版本族或标签展示，不能替代业务名称。

### 第 4 步：执行处理步骤

每个处理步骤必须记录在业务任务下：

- `stepOrder`
- `stepType`
- `displayName`
- `status`
- `abilityId`
- `abilityTaskId`
- `abilityLogId`
- `durationMs`
- `errorMessage`

处理步骤列表用于排障，不作为业务入口列表。

### 第 5 步：结果回填和查询

业务完成的判断必须同时满足：

- 业务任务进入终态。
- 结果已经回填到平台可访问地址。
- 查询接口能返回业务方需要的轻量结果。

图片类业务必须优先返回自有 OSS 地址。成功但无图、无视频、无文本或无结构化结果时，必须明确失败或显示“结果回填中”，不能展示空白。

### 第 6 步：可选回调

回调不是主查询链路，只是终态通知。

业务方常规链路是：

```text
提交任务 -> 保存 runId -> 轮询结果
```

如果传 `callbackUrl`，中台额外做终态通知。回调失败不等于任务执行失败，但必须在业务任务里可见。

### 第 7 步：计费、验收、复测和回滚

业务任务终态后，继续沉淀运营证据：

- 成本和计费状态
- API Key 使用记录
- 真实样本验收
- 复测记录
- 回滚证据

发版或切默认版本时，只看业务任务和业务版本证据，不看单条原子能力日志做结论。

## 3. 页面组织规则

### 3.1 总览页

只回答三个问题：

- 当前业务是否健康？
- 当前是否能发版？
- 当前最应该处理什么？

总览页不得展开 SQL、第三方原始错误、底层节点堆栈等大段技术内容。

### 3.2 业务能力页

业务能力页必须拆成清晰工作区：

- 业务调用：看入口概览、接口任务清单和单个 `runId` 详情。
- 业务链路：只看当前选中业务的编排图、组件和路由，不混入入口总控。
- 版本管理：看同一业务下的版本族、默认版本、发布时间、更新时间、继承关系、草稿试运行和验收记录。
- 治理记录：看发布门禁、默认切换、回滚、复测和操作记录。

接口任务清单必须把一行解释为一次业务调用 `runId`，列表里直接显示 `runId`、业务入口、版本、状态、结果和底层排障编号。详情弹窗必须先展示“这次业务调用”，再展示下面的处理步骤；不能让用户一进来先看 VL、ComfyUI 或模型调用记录。

业务详情必须直接展示本次 `runId` 的入口调用证据，包括提交次数、查询次数、失败次数、最近调用时间、API Key 名称和最近接口明细。用户不应该为了确认业务方是否正确提交和轮询，再跳到接口调用页手动筛选。

业务链路页只回答“这条业务由哪些组件构成、当前默认版本怎么执行”；不得在同一页塞入业务入口总控、长说明卡或全局处理顺序。

业务链路页必须支持在同一业务下切换具体业务版本。默认先看线上默认版本，但排查 GPT Image 2、ComfyUI、Coze 旧链路或保底版本时，必须能直接切到对应版本查看处理链路、版本族、继承关系、更新说明和主执行能力。

版本管理页必须把技术路线放在版本族里表达，例如 `ComfyUI 自研线`、`商业模型线`、`Coze 旧链路`、`保底回滚`。这些标签不能替代业务名称。

版本族标签的真源是后端业务版本响应里的 `version_line` 字段。前端可以做兼容兜底，但不能在多个页面各自维护一套路线判定规则。

版本继承关系的真源是后端业务版本响应里的 `version_lineage` 字段。第一阶段由 `metadata.versionLineage` 承载，必须至少能表达来源版本、替代版本、本次更新说明、是否破坏兼容、以及“版本升级 / 新功能 / 回滚保底 / 待确认”的判断。版本管理页必须按版本族分组展示，并在版本卡片上显示继承关系，避免后续多个图裂变版本混在一起看不出谁替代谁。

### 3.3 接口调用页

接口调用页从“业务方调用了什么”出发：

- API Key
- 接口路径
- `runId`
- 请求状态
- 轮询频率
- 错误码
- 对应业务任务

不要把轮询记录淹没提交记录；必须支持按 `runId` 聚合查看。

接口调用页负责批量筛选、分页、导出和跨任务排查；单条业务任务详情必须复用同一份入口调用证据，直接展示本次 `runId` 的提交、查询、失败和最近调用明细。两边不能各自计算一套口径。

业务接口状态、参数枚举、接口调用问题码的结构化真源是 `backend/app/constants/business_api_contract.py`。`docs/standards/business-api-enums.md` 是业务方说明文档，管理端接口页和交付审计接口必须优先读后端真源，不能各自维护一份枚举表。

上线后必须把这页纳入固定检查：`podi_release_smoke.py` 的 `business_api_usage_center` 会验证接口调用中心可访问、分页结构正常，并且有业务任务时能按 `runId` 聚合。没有业务流量只提示，不算失败；接口不可访问或有业务任务却没有聚合结果，算上线阻断。

### 3.4 处理步骤页

处理步骤页只用于排查底层：

- VL 是否成功
- 模型是否限流
- ComfyUI 是否排队或超时
- OSS 是否回填
- 回调是否失败

普通业务判断不能从这里开始。

## 4. 新功能准入清单

新增或修改能力前，必须先回答：

1. 这个能力属于哪个业务 key？
2. 它是业务入口，还是某个业务入口下的处理步骤？
3. 如果是业务入口，它是否有 `/api/business/*` 提交和查询接口？
4. 如果只是处理步骤，它会挂在哪个 `runId` 下？
5. 版本变化是替换旧版本，还是新增一个业务入口？
6. 测评端展示名、管理端业务分类、API 文档是否一致？
7. 错误码、枚举值、输入输出示例是否补齐？
8. 上线前是否有真实业务任务样本和回滚证据？

## 5. 反模式

以下做法禁止继续扩大：

- 先按 Coze、ComfyUI、OpenAI 这种技术来源分类，再让用户猜业务含义。
- 把 VL、生成、评分、回调分别当成一级业务任务。
- 用能力调用列表判断整条业务成功，而不看业务任务 `runId`。
- 新版本实际是替换旧版本，却在测评端新增一个同名功能卡。
- 页面展示“缺 key / SQL / 内网地址 / 原始堆栈”等恐慌信息，却没有给出业务动作。
- 文档只写成功示例，不写排队中、失败、错误码和业务方处理动作。

## 6. 验收标准

完成一次业务链路走查时，必须能从页面或报告中看到：

- 业务入口
- 业务版本
- `runId`
- 处理步骤
- 实际执行能力或模型
- 输出链接
- 错误码或成功结果
- API Key 使用记录
- 是否计费
- 是否回调
- 是否可复测或回滚

缺任一项，都不能说这条业务链路已经“看清楚”。
