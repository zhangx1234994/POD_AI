# 中台交付方法论准则

> 目的：把反复返工、口径漂移、上线耗时和“用户帮我们发现问题”的情况转成固定工作方法。  
> 适用范围：中台 backend、管理端、测评端、Coze 工具箱、原生业务 API、原子能力、交付包与发布。

---

## 1. 反思结论

今天暴露的问题不是单个功能 bug，而是工作方法不够稳定。

核心问题：

1. **业务理解没有先形成全景图。**
   - 先实现接口，后补测评端、文档和交付包，导致功能可用但业务方难以验收。
   - 对“Coze 接口、原生业务 API、原子能力、评测接口”的边界没有在每次实现前重新对齐。

2. **契约没有先固定。**
   - `bili` 到底是相似度还是重绘幅度，曾经靠聊天记忆判断，导致前端文案反复修改。
   - 参数别名、默认值、聚合优先级没有先写成契约图，导致代码、页面、JSON 示例和文档不同步。

3. **测试闭环发生得太晚。**
   - 有些问题是用户在页面上发现后才暴露，例如新能力没露出、页面报错、结果区不好用。
   - 后续不能把“用户上线看一眼”当作测试环节，必须先由开发侧完成本地和线上自检。

4. **交付物不是单一代码。**
   - 对业务方来说，真正交付的是：接口、Key、JSON 请求/响应样例、参数说明、错误处理、轮询方式、回调口径和可测试页面。
   - 只完成后端接口，不等于完成业务交付。

5. **发布流程还需要继续工具化。**
   - 每次上线花费大量时间，说明发布 SOP 虽然已有，但仍有验证点分散、手工判断多、报告沉淀不足的问题。

6. **文档沉淀滞后。**
   - 如果参数、流程和类图不沉淀，下一次能力接入会重复踩同样的坑。
   - 文档不能只是事后记录，必须成为实现前的约束和实现后的验收依据。

---

## 2. 总原则

后续所有中台能力开发都遵循：

```text
先业务全景 -> 再接口契约 -> 再实现 -> 再测评端/管理端可见 -> 再交付包 -> 再线上回归 -> 最后沉淀文档
```

禁止反向流程：

```text
先写代码 -> 页面临时补 -> 用户发现问题 -> 再补文档 -> 再反复上线
```

## 3. 四层交付模型

每个新能力必须同时考虑四层，而不是只看其中一层。

| 层级 | 要回答的问题 | 必须产物 |
| --- | --- | --- |
| 业务层 | 业务方到底要解决什么问题？是否属于花纹提取、图裂变、扩图等业务分类？ | 业务名称、业务分类、默认版本、灰度/回滚口径 |
| 接口层 | 业务方怎么提交、怎么轮询、失败怎么处理？ | 请求示例、响应示例、错误码、Key、JSON 示例 |
| 能力层 | 底层调用哪个原子能力、哪个模型、哪个 ComfyUI 工作流？ | 能力定义、输入 schema、输出类型、路由规则、调用日志 |
| 展示层 | 管理端和测评端如何让非技术用户理解？ | 测评入口、管理端记录、可读文案、结果预览、排障提示 |

验收时四层缺一不可。

## 4. 开发前必须先做的事

### 4.0 版本迭代与命名保护

涉及已有功能时，默认按“版本迭代”处理，不按“新增功能”处理；只有业务明确要求新入口、新接口或新测评卡片时，才新增能力入口。

硬性约定：

- 不确定是“新增”还是“替换升级”时，必须先确认，不能自行新增测评入口或业务入口。
- 不得随意修改用户已熟悉的功能名称；底层模型、工作流或参数升级，只能放到版本号、角标、更新时间和更新说明里。
- 功能必须同时保留“发布时间”和“更新时间”：发布时间代表第一次交付给测试或业务的日期，更新时间代表最近一次版本优化日期。
- 每次版本升级只展示最新一条“版本更新说明”，说明本次变更对用户有什么影响，不堆历史流水账。
- 参数默认保持兼容；新增参数必须是非必填，并给出安全默认值。除非明确确认，不允许删除、改名或改变旧参数含义。

### 4.1 业务归类

新增能力前先回答：

1. 属于哪个业务分类？
2. 是原生业务 API、Coze 工具箱、原子能力，还是评测能力？
3. 是否要给业务方正式使用？
4. 是否需要业务版本、灰度、回滚？
5. 是否会被客户端、MCP、技能或后续业务复用？

如果回答不清楚，不能直接开写代码。

### 4.2 契约草图

实现前必须先写最小契约草图：

- 请求字段
- 必填字段
- 可选字段
- 默认值
- 参数别名
- 参数映射
- 状态字段
- 结果字段
- 错误码
- 轮询方式

涉及多步骤编排时，必须补业务流图或类图。

### 4.3 交付清单

实现前就确定最终要交付什么：

- 后端接口
- 管理端入口
- 测评端入口
- 接口文档
- JSON 请求/响应示例
- Key
- 测试报告
- 发布说明

不允许做到最后才发现缺交付包或缺页面入口。

### 4.4 交付包拆分

对业务方交付多个接口时，必须按“一个接口一个目录”拆分。

每个接口目录必须独立包含：

- 完整 README
- 请求示例
- 轮询示例
- 提交返回示例
- 轮询排队中示例
- 成功响应示例
- 失败响应示例
- 参数表
- 枚举值说明
- 鉴权说明
- 常见错误说明

默认不再给业务方交付 Python 或 shell 脚本。正式交付材料只放 JSON 参数样例和字段说明；如果确实需要脚本，只能作为“调试工具包”单独提供，不能替代接口文档。

不允许把多个接口混在一个总 README 或一个总脚本里交给业务开发。总 README 只负责说明目录结构和选型，不负责承载全部接口细节。

## 5. 实现过程方法

### 5.1 先稳定契约，再写适配

参数进入系统后，必须明确聚合优先级：

1. 业务方显式传入的 `inputs` 优先。
2. 顶层字段只在 `inputs` 缺失时补进去。
3. 系统默认值只能补空，不能悄悄覆盖用户输入。
4. VL 或模型编译结果默认只补空，除非配方明确允许覆盖。
5. 前端文案必须跟后端真实语义一致。

### 5.2 业务语言优先

前端和文档主展示必须使用业务语言：

- 用“图裂变 · GPT Image 2 + VL 控制版”，不用 `gpt-image2-vl-v1` 当主名称。
- 用“裂变幅度 / 重绘幅度”，不用“相似度”误导。
- 用“排队中 / 生成中 / 已完成 / 失败”，不让业务方先理解底层状态。
- 技术 ID、workflow ID、executor ID 只放详情或排障区。

### 5.3 输出类型先分类

能力接入时必须先声明输出类型：

- 图片
- 视频
- 文本
- 结构化结果
- 普通资源
- 回调任务 ID

前端展示和巡检必须按输出类型判断，不能默认所有能力都是生图。

### 5.4 不把临时状态写成产品名称

以下词只能作为角标或状态，不能作为功能名称：

- 新版
- 测试版
- 临时版
- 灰度版
- 老版

功能名称必须描述能力本身。

## 6. 测试方法

### 6.1 开发侧必须先自测

不能把用户页面验收当作第一轮测试。

每个能力至少覆盖：

1. 标准成功路径。
2. 缺少必填参数。
3. URL 不可访问。
4. 队列或执行节点不可用。
5. 上游失败。
6. 成功但无结果回填。
7. 轮询终态。
8. 管理端调用记录。
9. 测评端真实展示。

### 6.2 线上回归不能只测接口返回

线上回归必须确认：

- 后端任务创建成功。
- 任务进入队列。
- 能力真正下发到正确执行面。
- 输出落 OSS。
- 业务任务回填。
- 轮询拿到终态。
- 管理端有记录。
- 测评端结果可看。

### 6.3 每次发现问题必须归类

问题归类至少包括：

- 业务理解偏差
- 接口契约偏差
- 参数语义偏差
- 前端展示偏差
- 后端执行偏差
- 数据库/查询偏差
- 发布流程偏差
- 文档缺失

归类后才能决定是修代码、修页面、修文档，还是修流程。

## 7. 发布方法

发布前必须明确：

1. 哪些服务需要更新。
2. 是否有数据库迁移。
3. 是否有 seed。
4. 是否需要更新 114 控制面。
5. 是否需要更新 117 能力服务。
6. 是否影响 Coze 工具箱。
7. 是否影响业务方 JSON 示例、交付包或已发布接口文档。

发布后必须做：

1. `/health`。
2. OpenAPI。
3. 业务 API route-preview。
4. 至少一条真实提交。
5. 轮询终态。
6. 管理端记录。
7. 测评端展示。
8. 错误路径抽查。

发布结果必须记录到报告或周报，不允许只写在聊天里。

## 8. 文档沉淀方法

### 8.1 什么必须写文档

以下内容必须当天沉淀：

- 新接口
- 新业务能力
- 新参数映射
- 新状态词
- 新错误码
- 新发布步骤
- 新测试结论
- 新事故或明显返工原因

### 8.2 文档放哪里

| 内容 | 文档位置 |
| --- | --- |
| 接口请求、响应、错误 | `docs/api/modules/*` |
| 业务流、类图、参数聚合 | `docs/api/examples/*` 或对应业务专题文档 |
| 平台级准则 | `docs/standards/*` |
| 每日/每周复盘 | `docs/weekly/*` |
| 事故复盘 | `docs/retrospectives/*` |
| 当前待办和进度 | `docs/strategy/todo-master-2026q2.md` |

### 8.3 文档不是补充项

如果代码改了但文档没有更新，视为交付未完成。

## 9. Codex 执行纪律

后续我这边执行必须遵守：

1. 不等用户指出明显页面问题；涉及前端时必须本地或线上走查。
2. 不只回答“应该可以”；必须给出测试证据或明确未测风险。
3. 不把代码实现当成交付完成；必须同步测评端、管理端、文档和 JSON 示例。
4. 不凭记忆处理参数；涉及参数语义时先查代码和文档，再修改。
5. 不让用户反复问“下一步做什么”；每轮完成后必须标注状态并给出下一步。
6. 不在发布信号上含糊；只有目标提交已进入 `origin/main` 且更新步骤明确，才说可以更新。
7. 不用技术词替代业务解释；主文案优先让非技术用户看懂。
8. 不把线上错误隐藏掉；临时兜底可以做，但必须记录根因任务。

## 10. 新能力交付检查表

每个新能力交付前逐项确认：

- [ ] 已归入业务分类。
- [ ] 已明确接口形态：原生业务 API / Coze 工具箱 / 原子能力 / 评测能力。
- [ ] 已写请求示例。
- [ ] 已写响应示例。
- [ ] 已写错误示例。
- [ ] 已写参数说明，包含必填、可选、默认值。
- [ ] 已写状态和轮询说明。
- [ ] 已接入测评端。
- [ ] 已接入管理端记录或可观测页面。
- [ ] 已跑成功路径。
- [ ] 已跑至少一个失败路径。
- [ ] 已确认结果回填。
- [ ] 已确认输出类型展示正确。
- [ ] 已准备业务方 JSON 请求/响应示例。
- [ ] 已准备 Key 或说明 Key 获取方式。
- [ ] 已更新文档索引或模块入口。
- [ ] 已记录测试证据和剩余风险。

缺任一项，不能说“具备交付条件”。

### 10.1 两步式图像业务额外检查

文字强化裂变（文生图）的返工证明：只按普通单接口能力接入，会漏掉中间态、字段回填、默认值和错误副作用。后续所有“两步式 / 可编辑中间态 / 先分析再生成”的图像业务，开工前必须补一张功能定性卡：

- [ ] 这是新业务、新版本，还是旧版本修补。
- [ ] 业务名称、版本名称、测评端名称和业务方接口名称已固定。
- [ ] 第一步和第二步的状态机已写清楚。
- [ ] 第一步返回字段能回填到第二步输入框。
- [ ] 第二步必填字段在创建任务前完成校验。
- [ ] 缺参、依赖失败、超时不会创建脏任务或扣费。
- [ ] 用户参数和内部参数已分离；内部参数不进入业务方文档和测评端普通输入区。
- [ ] 默认值真源已明确；不传字段和手动覆盖都要有测试。
- [ ] 轻量返回和调试返回已分离。
- [ ] 真实业务运行后能从能力日志证明参数传到执行节点。

本规则的完整复盘见 `docs/releases/retrospectives/2026-05-19-text-fission-retrospective.md`。

## 11. 当前阶段要立即改进的点

1. 裂变评分补业务包装入口的决策要尽快明确，避免业务方面对两套轮询。
2. 测评端结果区继续优化，图片对比优先于调试信息。
3. `Out of sort memory` 要从查询和索引根因处理，不能只隐藏错误。
4. 业务方交付包要作为正式交付物维护版本，不再临时拼。
5. 每次能力包接入前先建立契约图，避免边做边猜参数。
