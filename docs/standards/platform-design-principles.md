# 平台设计准则（稳定性优先）

> 适用范围：中台、管理端、测评端、Agent 协议与第三方能力接入。

## 1. 先解耦再扩展

- 上传链路、任务提交、结果回填、标注环节必须解耦。
- 禁止“边上传边执行”这类强耦合流程进入主链路。

## 2. 先定义状态再开发页面

- 页面状态词必须先在接口契约中定义并落表。
- 所有异步任务优先采用双阶段字段：
  - `submit_status`
  - `callback_status`
  - `final_status`

## 3. 先定义失败语义再做重试

- 重试前必须定义：可重试条件、幂等键、最大次数、死信处理。
- “超时”必须区分：
  - 软超时：继续等待并可补偿
  - 硬超时：进入失败并记录原因

## 4. 先契约对齐再联调

- 联调前双方必须对齐 OpenAPI/协议文档。
- 字段名、鉴权头、错误码、状态枚举缺一不可。

## 5. 单一事实源（Single Source of Truth）

- 管理端是配置真源；测评端读取，不重复维护枚举。
- 历史兼容字段可保留，但不得形成第二套状态口径。

## 6. 清单版本化与可回滚

- ComfyUI 清单必须版本化，状态至少包含：
  - `draft`
  - `published`
  - `rolled_back`
- 发布默认灰度，失败可回滚，禁止自动删除资源。

## 7. 可观测性是功能的一部分

- 每条链路至少具备：`trace_id/task_id/stage/provider/node_id/retry_count`。
- 失败必须可定位到具体阶段与具体节点。

## 8. 文档同步是发布门槛

每次迭代必须同时更新：

1. API 模块文档（请求/响应/错误）
2. 错误码总表
3. 接口一致性准则
4. 对应功能文档与复盘记录

## 9. 先做能力归类再做页面渲染

- 先定义能力输出归类（`callback_task_id / image_url / json_output`），再开发前端展示。
- JSON 类能力必须直接展示结构化结果，禁止按图片回填链路处理。
- 回调类能力必须统一 task 轮询口径，禁止分散实现多套回调判断逻辑。
- 同一能力的参数枚举必须以“模型维度”维护，文档与接口同步更新。
