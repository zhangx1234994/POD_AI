## 2. 版本层级

项目内同时存在三类版本，必须区分。

### 2.1 平台版本

格式：`vMAJOR.MINOR.PATCH`

对象：

- backend
- podi-admin-web
- podi-eval-web
- 114 控制面发布包
- 发布 SOP 和门禁

示例：

- `v0.1.0`：当前封版基线。
- `v0.1.1`：只修复 bug、文案、发布脚本或小范围兼容问题。
- `v0.2.0`：引入业务编排可视化和控制权收敛。

### 2.2 业务能力版本

对象：

- 图裂变
- 扩图
- 花纹提取
- 裂变评分
- 后续新增业务入口

规则：

- 业务版本不等于平台版本。
- 业务名称不能随版本变化随意改名。
- 新版本如果是替换原功能，必须保留原功能名称，只更新版本号、更新时间、更新说明和角标。
- 业务版本必须记录：`business_key`、`version`、`status`、`release_time`、`updated_time`、`release_note`、`recipe`。

### 2.3 原子能力版本

对象：

- ComfyUI workflow
- OpenAI / 火山 / KIE / 百度模型能力
- VL 组件
- image-ops 原子服务

规则：

- 原子能力版本只说明执行组件自身变化。
- 原子能力版本不能直接暴露成业务方主要入口。
- 原子能力变化如果影响业务入参、出参、质量或成本，必须关联到业务版本更新。

## 3. 平台版本号递增规则

### PATCH：`v0.1.x`

适用：

- 修 bug。
- 修文案。
- 修发布脚本。
- 修页面展示。
- 修历史数据收口。
- 不改变对外接口契约。
- 不改变核心业务流程。

要求：

- 可以较快发布。
- 必须跑标准发布 SOP。
- 必须记录改动原因和验证结果。

### MINOR：`v0.x.0`

适用：

- 新增业务编排 DSL。
- 新增可视化编排页面。
- 新增对外业务接口。
- 新增灰度、回滚、版本治理能力。
- 对管理端信息架构做明显调整。

要求：

- 必须有规划文档。
- 必须有阶段验收标准。
- 必须有回滚方案。
- 必须完成管理端和测评端走查。

### MAJOR：`v1.0.0`

适用：

- 对外商业化稳定版本。
- API、鉴权、计费、回调、文档、SLA 形成正式承诺。

要求：

- 不在当前阶段启动。
- 等中台业务编排、接口调用、版本治理、账单和权限稳定后再定义。

## 4. Git 规则

- `origin/main` 是唯一正式发版真源。
- 正式版本必须从 `main` 打 tag。
- tag 命名：`v0.1.0`、`v0.1.1`、`v0.2.0`。
- tag 只能打在已通过 114 发布 SOP 的 commit 上。
- tag 不复用、不强推、不移动。
- 若发现 tag 版本有问题，发布新的 PATCH 版本修复，不改旧 tag。

## 5. 发布记录规则

每个正式平台版本必须记录：

- 版本号。
- commit。
- 发布时间。
- 发布机器。
- 主要变更。
- 验证结果。
- 已知风险。
- 是否需要能力机同步。
- 是否需要业务方改接入。

记录位置：

- `docs/releases/CHANGELOG.md`
- `docs/standards/issue-improvement-log.md`：只记录问题和改进。
- `docs/strategy/todo-master-2026q2.md`：只记录当前执行进展。

## 6. 业务版本规则

业务版本必须遵循：

- 名称稳定，版本变化不改主名称。
- `release_time` 表示首次发布时间。
- `updated_time` 表示最近更新时间。
- `release_note` 只写这次变更，避免堆历史流水账。
- 业务方默认调用不传版本，走当前默认版本。
- 业务方要灰度或复测时，可以指定版本。
- 默认版本切换必须有验收记录。
- 回滚只切默认版本，不删除历史版本。

示例：

```text
业务：图裂变
主名称：图像裂变 · ComfyUI 颜色锁定版
版本：comfyui-vl-control-v2
角标：已优化
发布时间：2026-05-12
更新时间：2026-05-14
更新说明：增加颜色锁定配置，重绘幅度按统一规则映射 denoise。
```

## 7. 发版门禁与版本关系

平台版本发布前必须确认：

- 平台版本号是否需要递增。
- 业务版本是否有变化。
- 业务版本变化是否已同步测评端和交付文档。
- 对外 API 是否有契约变化。
- 错误码和枚举是否同步。
- 是否需要 Coze 工具箱重新导入。
- 是否需要能力机更新。

不允许：

- 线上已经发布，但没有版本记录。
- 功能名称变化但没有业务版本说明。
- 参数变化但测评端、文档、接口示例不一致。
- 只改代码不更新发布 SOP 或门禁。

## 8. 下个版本建议

建议下一个平台版本为 `v0.2.0`。

主题：

- 控制权收敛。
- 业务编排只读图。
- runId 全链路排障。
- 业务版本、参数 schema、路由策略、测评入口一致性门禁。

不建议把 `v0.2.0` 做成大量新能力接入版本。它应该先解决平台结构问题。
