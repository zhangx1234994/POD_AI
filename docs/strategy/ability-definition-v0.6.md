# v0.6 能力定义与边界准则

最后更新：2026-06-03

本文是 v0.6 的口径基准。后续讨论中台、管理端、测评端、客户端方案时，先按本文判断“什么是能力”，避免把项目、页面动线或客户端业务组装误当成中台主线。

## 1. 一句话定义

**能力是中台对外承诺的、可稳定调用、可治理、可迭代的业务动作。**

它必须能被客户端、测评端或管理端用明确输入触发，并以统一状态、结果、错误、成本和质量证据返回。

## 2. 能力必须满足的条件

一个对象只有同时具备以下条件，才算中台能力：

1. 有清晰业务意图：例如花纹提取、图裂变、扩图、图编辑、产品设计图、模特图、推广视频。
2. 有稳定对外入口：优先是 `/api/business/*`，或明确标注为内部原子能力 API。
3. 有请求 schema、响应 schema 和错误码。
4. 有版本、默认版本、候选版本、回滚版本或等价治理口径。
5. 有路由和底层依赖记录：模型、workflow、executor、LoRA、第三方 API、Key 来源。
6. 有 `runId` 或等价调用 ID，可以排障、回放、追踪状态。
7. 有结果资产沉淀：输出图、视频、文本或结构化结果进入受控媒资/结果记录。
8. 有质量样例、质量标注、成本和调用记录。
9. 有管理端观察入口和测评端验证入口。
10. 有测试覆盖：缺参、依赖失败、超时、队列/并发限制和成功路径。

## 3. 不是能力的东西

以下对象不能作为中台能力主语：

- 客户端项目、工作单、订单、素材夹。
- 客户端页面动线、行业模板、下一步推荐。
- 单个 ComfyUI 节点、单条 prompt、单个模型名。
- 管理端页面、测评端页面。
- 一次临时实验、一张样例图、一次人工选择。
- 只保存资产但没有执行动作的容器。

这些对象可以是能力的上下文、证据、配置或使用场景，但不是能力本身。

## 4. 三类能力层级

### 4.1 原子能力

原子能力是内部技术能力，例如 ComfyUI workflow、OpenAI / KIE / 火山 / 百度模型、image-ops 服务。

要求：

- 只面向中台内部和管理端/测评端。
- 不直接暴露给普通客户端。
- 必须被业务能力封装后才能进入客户端生产链路。

### 4.2 业务能力

业务能力是客户端真正调用的中台能力，例如：

- `pattern_extract` 花纹提取。
- `fission` 图裂变。
- `outpaint` 扩图。
- `image_edit` 直接图编辑。
- `image_edit_chat` AI 改图助手。
- `product_design` 产品设计图，2026-06-03 已补首版业务包装。
- 待补：`product_image_set` 组图 / 多角度。
- 待补：`model_shot` 模特图。
- 待补：`promo_video` 推广视频。

业务能力只暴露业务参数，不暴露 executor、workflow、LoRA、模型和厂商细节。

口径补充：`image_edit_chat` 现阶段可以暂时归类到“图编辑”分类下，方便用户在改图场景中找到入口；但它不是可视化图编辑器的一个模式。它的长期归宿是 Agent 能力，后续会逐步接入更多业务能力，而不只调用 `image_edit`。

### 4.3 Agent 能力

Agent 能力是一种特殊业务能力。它以会话、消息、方案和确认执行为入口，可以调用白名单业务能力，但不能绕过中台能力体系。

当前 v0.6 只承认一个 Agent 能力：

- `image_edit_chat`：AI 改图助手，底层只允许调用 `business.image_edit`。

产品边界必须保持清楚：可视化改图面向“看图、标注、精确提交”，属于 `image_edit` 工作台方向；对话改图面向“自然语言沟通、多轮追改、调用多种技能”，属于 Agent 方向。两者可以共享底层图编辑能力和结果资产，但不能在交互、接口和能力定义上混成一个功能。

后续如果 Agent 要调用花纹提取、裂变、产品设计、模特图或视频，也必须先把这些动作定义成业务能力，再由 Agent 编排调用。

Agent MVP 交付补充：

1. Agent 是后端 Runtime 能力，不是前端聊天组件。前端负责表达、预览、确认和状态反馈；后端负责会话、上下文、路由、队列、执行、成本、Key 池和审计。
2. Agent 可以使用大模型和提示词做意图理解，但最终能力调用必须由后端按白名单、schema、置信度、风险和成本校验后创建业务 run。
3. Agent 后续可内置方法论，但方法论必须版本化，具备阶段、输入输出、可调用能力、人工确认点、失败兜底和验收证据。
4. Agent 的上下文不能无限堆历史对话，必须区分原始消息、工作记忆、资产状态和工具调用证据，并在每轮调用前压缩成可控上下文。
5. Agent 上线门槛必须包含路由稳定性测试、多轮续改、新任务隔离、并发队列、依赖失败、超时和错误契约覆盖。

## 5. 关于项目的口径

中台 v0.6 不以“项目”为主语。

客户端可以有项目、工作单、订单或素材夹，这是客户端业务组装概念。中台只接收必要的调用上下文，例如：

- `clientContextId`
- `clientStepKey`
- `clientRequestId`
- `inputAssetIds`
- `traceId`

现有代码中已经出现的 `projectId` / `business_projects` 只能视为兼容性的调用上下文存储命名，不应继续扩展成中台产品主视角，也不应进入测评端主路径。后续新增文档和页面优先使用“调用上下文”“资产证据”“交付证据”等语言。

## 6. 管理端与测评端边界

管理端只围绕能力治理组织：

- 能力总览。
- 能力详情。
- 版本、路由、成本、质量、失败卡点、回滚。
- runId、步骤、能力调用日志和输出资产。

测评端只围绕能力验证组织：

- 选择能力。
- 上传或选择样例。
- 运行能力。
- 查看结果。
- 记录质量。
- 对比版本。

测评端不做客户端项目流；管理端不做客户端生产动线。

## 7. v0.6 当前判断

v0.6 的封版前置不是“项目底座是否完整”，而是：

1. 已有核心能力是否按能力标准补齐治理和验证入口。
2. `product_design` 是否作为 P0 业务能力补齐。
3. 对话改图是否作为独立 `image_edit_chat` 能力跑通并可解释。
4. 管理端是否能按能力判断稳定性、版本、路由、质量和成本。
5. 测评端是否能按能力完成样例、运行、结果和质量闭环。

客户端业务组装只输出方案和边界，不进入当前中台开发主线。
