# v0.2 业务控制面收敛版方案

最后更新：2026-05-18

## 1. 版本定位

v0.1 已经解决了“能不能跑通”的问题：Coze 工具箱、中台业务接口、测评端、管理端、ComfyUI 双节点、业务回填和发布 SOP 都已经形成基本闭环。

v0.2 要解决的是“能不能长期稳定维护”的问题：业务链条不能再依赖多个分散控制点，页面不能再让用户靠猜，接口、测评、管理端、文档和发布门禁必须从同一份业务配置里读取。

本版本名称：**业务控制面收敛版**。

当前基线：

- 线上稳定基线：`v0.1.x`
- 已验证生产提交：`0f977db5`
- 唯一发版真源：`origin/main`
- 当前核心业务：花纹提取、图裂变、扩图、裂变评分

## 2. 核心问题

当前平台已经暴露出几个结构性问题：

1. 一个业务的控制点太多。参数默认值、页面文案、测评入口、业务接口、OpenAPI、版本信息、路由策略、交付文档分散在多处，导致一次调整经常要改多个位置。
2. 业务版本关系不够清晰。图裂变存在 Coze 旧链路、ComfyUI 自研线、GPT Image 2 商业模型线、保底回滚线，用户很难判断哪个是线上默认、哪个是测试版本、哪个是同一业务升级。
3. 业务链路虽然已经可视化，但仍偏只读展示。它还没有成为真正的业务编排入口，也没有承担参数、路由、版本、步骤治理的唯一配置职责。
4. 接口调用中心还不够业务化。业务方真实调用的是业务接口，但管理端仍容易把一次业务调用拆散成多条底层能力调用，排查时需要人工串联。
5. 文档入口噪音仍偏高。历史迁移方案、旧 Coze 过程文档、旧客户端资料还在索引里出现，容易干扰当前执行判断。

## 3. v0.2 目标

v0.2 只做一件事：把业务能力从“多个页面和配置散着控制”收敛成“业务入口 -> 业务版本 -> 业务配方 -> 执行步骤 -> 结果证据”的单主线。

必须达成：

1. 每个业务能力都有清晰的稳定业务名、版本族、线上默认版本、测试版本、历史版本和回滚版本。
2. 管理端能围绕一次 `runId` 看清入口、版本、步骤、底层能力、执行节点、输入输出、回填、错误和调用方。
3. 业务链路图不只是展示图，而是业务配方的可读入口；后续可逐步升级为可编辑编排器。
4. 测评端、业务接口文档、OpenAPI、交付材料从业务能力 schema 派生，减少手写漂移。
5. 发布前门禁必须检查业务配置、测评入口、接口文档和页面文案一致性。

## 4. 非目标

本版本不做以下内容：

1. 不做完整收费系统。只继续保留调用记录、成本字段、Key 使用记录和未来计费口径。
2. 不做完整可拖拽工作流编辑器。v0.2 先把业务配方真源和只读/半编辑能力打牢。
3. 不重做整个管理端视觉系统。只改主业务动线、关键页面降噪和明显阻碍理解的问题。
4. 不新增大量新模型能力。除非业务必需，否则优先修结构和稳定性。
5. 不为 233 或 158 单独写特殊业务逻辑。执行节点差异只能通过能力标签、节点健康、路由策略表达。

## 5. 版本任务

### 5.1 业务配方唯一真源

目标：一个业务版本只允许有一份核心配方，其他页面都读取它。

要做：

- 梳理 `BusinessCapability.recipe`、`input_schema`、`output_schema`、`version_lineage`、路由字段的责任边界。
- 明确哪些字段属于业务版本，哪些字段属于执行节点，哪些字段属于测评端展示。
- 把图裂变、花纹提取、扩图、裂变评分四个业务先纳入同一套配方口径。
- 对历史 Coze 旧链路只保留为版本族或历史入口，不再和新自有业务接口混在一起命名。

验收：

- 修改一个业务参数名称或默认值时，测评端、OpenAPI、交付文档、管理端版本卡片不会各自漂移。
- 图裂变页面能清楚区分 Coze 旧链路、ComfyUI 自研线、GPT Image 2 商业模型线、保底回滚线。

### 5.2 业务链路工作台

目标：管理端业务链路页从“展示图”升级为“排障和版本理解入口”。

要做：

- 单业务大画布继续保留，默认选中主执行步骤，不选信息量低的入口节点。
- 左侧按稳定业务名和版本族组织，不直接堆内部版本号。
- 右侧展示本步骤的业务含义、入参、默认值、路由、执行节点、输出和错误处理建议。
- 去掉无意义说明块、空白框、过长技术描述，只保留用户能用来判断的内容。
- 对图裂变等多版本业务，增加“当前线上默认 / 本次测试 / 历史保留 / 回滚可用”的可读标签。

验收：

- 非研发用户打开业务链路页，可以在 30 秒内判断当前业务跑的是哪个版本、背后用了哪些组件、失败应该看哪一步。
- 页面不再出现“未命名业务 / 未定版本 / 待确认 / 相似度”等误导性文案。

### 5.3 接口调用中心产品化

目标：业务方调用接口后，管理端能按一次业务调用清楚追踪。

要做：

- 接口调用列表以 `runId` 为主线聚合提交、轮询、失败和回调。
- 区分中台自有业务 API、Coze 工具箱 API、原子能力 API、内部巡检 API。
- 展示 API Key、调用方、业务入口、状态、耗时、错误码、最近轮询、结果数量。
- 对轮询类接口做降噪，避免大量 `/runs/get` 淹没真实提交记录。
- 补齐业务接口状态和错误枚举，文档、页面、返回体一致。

验收：

- 输入一个 `runId` 可以看到完整业务调用链，不需要再去多个列表手动拼。
- 业务方反馈“返回太重”时，可以明确知道他们调用的是提交接口还是查询接口，返回体是否符合轻量契约。

### 5.4 逐功能上线门禁

目标：每个功能上线前都有固定检查，不再靠人工印象。

要做：

- 按功能生成上线检查清单：接口、参数、默认值、枚举、错误、测评入口、页面文案、结果展示、执行节点、回填。
- GPU 自有能力必须真实跑，不允许只用 mock 或只看健康接口。
- 第三方商业模型可按成本选择抽检，但必须记录是否跳过、为什么跳过、风险是什么。
- 对“版本更新还是新增功能”加入门禁确认。
- 对“新版”文案、`bili/similarity/相似度`、内部版本号外露做自动或半自动检查。

验收：

- 发布前能输出一份按功能维度的检查结果。
- 任一功能没有真实跑通、没有返回样例、没有错误枚举、没有页面入口时，不能被标记为可交付。

### 5.5 文档治理和旧资料降噪

目标：当前执行者只看少量真源文档就能恢复上下文。

要做：

- 总索引只保留当前真源、模块入口、历史资料入口三类。
- 旧 Coze 迁移过程文档、旧客户端资料、旧临时方案不再出现在“当前真源”列表。
- 新增文档清理台账，记录哪些文档仍有效、哪些只作历史参考、哪些后续可归档。
- 唯一 TODO 只保留当前执行单，历史执行单保留但明确不再作为开发清单。

验收：

- 新同学按 `docs/README.md` 阅读，不会被旧部署、旧客户端、旧迁移阶段方案带偏。
- 每次新增方案，都能在 `docs/strategy/todo-master-2026q2.md` 找到对应执行项。

## 6. 分阶段计划

### 阶段 A：文档和目标收敛

输出：

- v0.2 方案
- 文档清理台账
- TODO 当前执行单
- 总索引和战略索引更新

验收：

- 当前版本要做什么、不做什么、怎么验收写清楚。
- 旧文档不会继续作为当前执行入口。

### 阶段 B：业务配方和版本族收敛

输出：

- 四个核心业务的版本族整理
- 业务版本继承关系补齐
- 版本命名和显示口径统一

验收：

- 图裂变不同路线可读，不再像多个互不相关功能。
- 版本更新和新增业务分类有明确判断。

### 阶段 C：业务链路和接口调用工作台

输出：

- 业务链路页降噪
- 接口调用中心按 `runId` 聚合
- 业务调用详情下钻到处理步骤和底层能力

验收：

- 出问题时优先从业务调用进入，而不是从底层能力日志反推。

### 阶段 D：上线门禁和测评端联动

输出：

- 逐功能上线检查脚本或接口
- 测评端入口与业务 schema 联动
- 业务交付文档生成或校验规则

验收：

- 一个功能从开发到测评到交付，参数、文案、返回体和错误码不会分裂。

## 7. 上线策略

v0.2 不建议频繁小版本上线。推荐节奏：

1. 本地完成阶段 A + 阶段 B 的结构性调整。
2. 本地启动 backend、管理端、测评端做视觉走查和接口回归。
3. 跑发布前门禁、后端测试、管理端构建、测评端构建。
4. 只在核心路径稳定后更新 114。
5. 更新后按 SOP 跑业务接口、Coze 工具箱、测评端和管理端闭环。

如果只改文档，不需要单独发版；如果改了业务 schema、OpenAPI、管理端或测评端，则必须走完整发布 SOP。

## 8. 风险和处理

| 风险 | 表现 | 处理原则 |
| --- | --- | --- |
| 配方收敛导致兼容字段丢失 | 老业务方调用失败 | 对外字段先兼容，内部逐步归一，不做硬切 |
| 页面继续堆说明文字 | 用户仍看不懂 | 用业务问题组织页面，不用技术概念堆叠 |
| 版本族整理误伤线上默认 | 默认版本被误切 | 默认版本不可直接编辑，必须复制草稿、验收、再切换 |
| 接口调用中心被轮询淹没 | 看不到真实提交 | 提交记录优先，轮询折叠为统计和最近记录 |
| 文档清理误删历史证据 | 无法追溯旧决策 | 先从索引降噪和标注历史开始，不直接物理删除关键文档 |

## 9. 封版标准

v0.2 具备封版条件时，必须满足：

1. 四个核心业务在管理端有清晰业务名、版本族、默认版本和链路图。
2. 图裂变至少能区分 Coze 旧链路、ComfyUI 自研线、GPT Image 2 商业模型线、回滚线。
3. 接口调用中心能按 `runId` 查到提交、轮询、错误和调用方。
4. 测评端核心参数文案与业务 schema 一致，不再出现“相似度”等错误描述。
5. 文档索引已清理，唯一 TODO 已指向 v0.2 当前执行单。
6. 发布 SOP、逐功能上线检查、错误契约和接口一致性文档没有被绕过。
