# 中台控制权收敛与业务编排可视化规划 v1

日期：2026-05-16

基线版本：`v0.1.0`，对应 114 线上封版 commit `904f9a2a`。

本阶段发布节奏：

- 先把本阶段目标在本地做完整。
- 再完成本地测试、页面走查和文档/TODO 标记。
- 然后明确 114 更新步骤、影响范围和回滚口径。
- 最后再更新 114；非紧急问题不边开发边频繁更新生产控制面。

## 1. 目标

下一阶段的核心目标不是继续堆功能，而是把业务链路里的控制权收回来，解决“一个问题要改多处”的结构性问题。

目标平台形态：

```text
业务入口
  -> 业务版本
    -> 业务编排配方
      -> 组件节点
        -> 原子能力 / ComfyUI / 第三方 API / OSS / 回调
```

管理端需要能回答：

- 一个业务入口当前默认跑哪个版本。
- 这个版本由哪些组件组成。
- 每个组件的输入、输出、状态、耗时和错误是什么。
- 如果失败，失败发生在哪一步。
- 如果要换模型、换工作流、灰度或回滚，应该改哪里。

## 2. 当前结构性问题

### 2.1 同一件事由多个地方控制

目前已经出现以下重复控制：

| 事项 | 现在可能存在的位置 | 典型风险 |
| --- | --- | --- |
| 路由到哪台 ComfyUI | 执行节点、工作流绑定、能力 metadata、业务版本 recipe、测评端入口 | 某处改了，线上数据库仍是旧状态，导致路由不一致。 |
| 参数默认值 | ComfyUI workflow JSON、能力 schema、业务 API、测评端表单、交付文档 | `bili/denoise/重绘幅度/锁色` 这类参数容易改漏。 |
| 业务版本 | 业务能力表、测评端卡片、Coze workflow、交付包文档 | 优化版本被误当成新增功能，测试同学找不到入口。 |
| 任务状态 | 业务 run、能力 task、能力 log、测评 run、Coze task | 成功、失败、回填中、轮询中容易互相矛盾。 |
| 接口文档 | 中台业务 API、Coze 工具箱、测评端说明、交付包 | 入参和出参解释不一致，业务方理解成本高。 |

### 2.2 结果

- 修改链路变长。
- 发布门禁难以判断谁是真源。
- 页面出现大量说明文字，但用户仍不知道该做什么。
- 排障时必须在业务任务、能力调用、ComfyUI、VL、OSS、测评记录之间来回跳。

## 3. 单一事实源规则

下一阶段必须按下面的控制权归属收敛。

| 控制事项 | 唯一真源 | 其他位置只能做什么 |
| --- | --- | --- |
| 业务入口、默认版本、发布时间、更新时间、更新说明 | `BusinessCapability` | 测评端、文档、Coze 只读取和展示。 |
| 业务编排步骤 | `BusinessCapability.recipe` | 前端编辑器只生成 recipe，不能另存一套流程。 |
| 原子能力输入 schema | `Ability.input_schema` | 测评端和编排节点表单读取 schema。 |
| 路由策略 | 能力级路由策略 + 执行节点健康 | workflow binding 作为兼容层，必须被门禁校验一致。 |
| 业务任务状态 | `BusinessRun` | 能力任务和日志只能作为子步骤证据。 |
| 子步骤状态 | `BusinessRunStep` | VL、ComfyUI、OpenAI、评分、OSS、回调都挂在 runId 下。 |
| 对外枚举和错误码 | `docs/standards/business-api-enums.md` 和错误码总表 | 页面和交付包引用，不重复写一套。 |

硬规则：

- 业务方只理解业务 API、`runId`、状态、结果、错误码。
- 测评端不再自定义业务名称、参数含义和版本关系。
- Coze 保留为接入层和实验层，不再作为长期业务编排真源。
- ComfyUI workflow 是执行资源，不是业务流程真源。

## 4. 业务编排 DSL 方向

`recipe` 需要从“自由 JSON”逐步收敛为可校验的业务编排 DSL。

建议结构：

```json
{
  "schemaVersion": "podi.recipe.v1",
  "mode": "pipeline",
  "nodes": [
    {
      "id": "input",
      "type": "input",
      "label": "业务输入",
      "outputs": ["image_url", "prompt", "params"]
    },
    {
      "id": "vl",
      "type": "ability",
      "abilityId": "volcengine.doubao_seed_2_0_lite_vl",
      "label": "VL 图像理解",
      "inputs": { "image_url": "{{input.image_url}}" },
      "outputs": ["description", "prompt_suggestion"]
    },
    {
      "id": "generate",
      "type": "ability",
      "abilityId": "comfyui.flux_strong_hq_softstyle_fission_colorlock_v2",
      "label": "图裂变生成",
      "inputs": {
        "url": "{{input.image_url}}",
        "prompt": "{{vl.prompt_suggestion}}"
      },
      "outputs": ["imageUrls"]
    },
    {
      "id": "result",
      "type": "result",
      "label": "结果回填",
      "inputs": { "imageUrls": "{{generate.imageUrls}}" }
    }
  ],
  "edges": [
    { "from": "input", "to": "vl" },
    { "from": "vl", "to": "generate" },
    { "from": "generate", "to": "result" }
  ]
}
```

注意：

- 第一阶段不要求所有历史 recipe 立刻迁移。
- 先提供兼容转换，把旧 `steps` 渲染成只读流程图。
- 新增业务版本必须逐步使用 `schemaVersion=podi.recipe.v1`。

## 5. 可视化编排页面阶段规划

### 阶段 0：冻结现状，建立基线

目标：把当前线上稳定版本固定为 `v0.1.0`，不再在未规划清楚的情况下继续叠功能。

工作：

- 记录 `v0.1.0` 基线 commit、线上服务、核心能力和已知风险。
- 确认所有核心业务入口：花纹提取、图裂变、裂变评分、扩图。
- 梳理每个入口当前真源、重复控制点和页面入口。

验收：

- 有版本记录。
- 有控制权重复点清单。
- 有下一阶段执行清单。

### 阶段 1：只读业务编排图

目标：先解决排障，不急着做拖拽编辑。

工作：

- 管理端业务能力详情新增“编排图”。
- 从 `BusinessCapability.recipe` 渲染节点和连线。
- 节点展示组件名、能力 ID、输入来源、输出目标、是否关键步骤。
- 点击节点展示参数 schema、默认值、路由策略和最近调用结果。
- 业务 run 详情中按同一张图高亮本次执行状态。

进展：

- 2026-05-16：backend 已在业务版本和业务运行详情中输出只读 `orchestration_graph`，图数据直接来自 `BusinessCapability.recipe` 和 `business_run_steps`，不另建第二套流程真源。
- 2026-05-16：管理端业务入口地图、业务版本底层信息和业务 run 详情已接入只读编排图；同一份图数据展示入口、处理步骤、运行状态、输出数量、执行节点和排障编号。
- 2026-05-16：业务运行轻量列表恢复读取结果摘要用于判断结构化输出和已忽略问题，避免只读图上线前继续出现“成功但被误判结果回填问题”的噪音。
- 2026-05-16：编排图节点新增“参数 / 路由”展开详情，后端随节点输出字段摘要、默认值和路由摘要，管理端可直接看到参数真源和执行节点策略。
- 2026-05-17：业务运行详情补齐入口调用证据，按 `runId/requestId/traceId` 关联 API Key 使用记录，直接展示提交、查询、回调、失败和轮询异常，减少在业务页和接口调用页之间来回排查。

验收：

- 打开一个 `runId`，能一眼看到 VL、生成、评分、OSS、回调各在哪一步。
- 失败能定位到具体节点。
- 不需要去能力调用列表里猜哪条属于这次业务。

### 阶段 2：控制权收敛

目标：把重复控制改成“真源 + 校验 + 展示”。

工作：

- 业务版本负责默认版本、发布时间、更新时间、更新说明。
- 能力 schema 负责参数字段、枚举、默认值。
- 路由策略集中到能力和执行节点层，workflow binding 只做兼容映射。
- 测评端从业务版本和能力 schema 读取表单，不单独维护参数含义。
- 发布门禁检查业务版本、测评入口、交付文档、schema、错误码是否漂移。

进展：

- 2026-05-17：发布 smoke 新增 `business_truth_source_consistency` 第一版门禁，同时校验业务版本、业务 OpenAPI、测评目录、只读编排图和业务枚举文档，先覆盖花纹提取、图裂变默认版、GPT Image 2 受控裂变、ComfyUI 颜色锁定裂变、裂变生成图评估和扩图。
- 2026-05-17：测评目录业务接口类条目开始运行时读取 `BusinessCapability`，用业务版本覆盖测评端展示名称、版本、参数 schema、输出 schema 和业务角标；`eval_seed` 只保留入口指针和兼容信息，避免参数默认值、枚举和发布时间在测评端重复维护。
- 2026-05-17：测评端业务接入文档从 schema 自动生成参数说明、枚举说明和返回字段说明，后续新增参数只改业务版本 schema，页面文档随接口同步变化。
- 2026-05-17：业务 OpenAPI 的提交 schema 开始叠加 `BusinessCapability.input_schema`，保留历史兼容字段的稳定说明和 required 顺序，同时让新增参数自动进入业务方接口文档。
- 2026-05-17：业务交付包不再只靠 README 自己维护枚举和错误码，发布 smoke 会同时检查交付 README、JSON 样例、`business-api-enums.md` 和 `error-catalog.md`，缺任一处都会阻断封版。
- 2026-05-17：管理端接口页的交付检查接入后端实时审计，审计逻辑复用发布 smoke 的交付材料规则；页面展示只负责呈现结果，不再自己维护一套“可交付”判断。
- 2026-05-17：管理端业务链路图引入 React Flow 只读交互画布，先解决“看不清链路、不能选节点、参数/路由不聚合”的问题；拖拽编辑、保存编排和版本发布放到下一阶段，不在本轮直接开放。
- 2026-05-17：默认版本控制项加后端硬保护，主能力、配方、业务标识、版本号、输入/输出 schema 和取消默认不能原地修改；新改动必须先复制为草稿版本，再试运行、验收和切默认。
- 2026-05-17：补齐管理端草稿试运行闭环。正式业务入口仍只跑 active 版本；管理端可按 `BusinessCapability.id` 跑 draft/inactive 版本，生成真实 `runId`、步骤记录和业务任务清单记录。
- 2026-05-17：草稿编辑进入最小可用形态。业务版本编辑器新增“草稿编排”，可以按步骤维护 VL/能力组件、顺序、启停和调用能力；所有变更仍写回同一份 `BusinessCapability.recipe`，不建立第二套流程真源。
- 2026-05-17：草稿试运行入口从浏览器 prompt 改为管理端弹窗，统一填写样图、评分生成图、提示词和附加 JSON 参数，后续可继续演进为按业务 schema 生成的试运行表单。
- 2026-05-18：业务版本治理不再只检查主能力，也会检查每个可执行步骤的能力是否存在、是否启用、步骤编号是否重复、主步骤是否与 `primaryAbilityId` 一致；这类问题会在管理端治理状态中提前暴露，避免运行时才发现某个中间节点断链。

验收：

- 修改一个参数，只需要改一处真源，其余位置自动读取或被门禁提示。
- 233/158 这类路由恢复，不再出现“代码允许但数据库绑定没恢复”的情况。
- 测评端和管理端展示名称一致。

### 阶段 3：草稿式可视化编辑

目标：允许在管理端组装业务流程，但不直接影响线上。

工作：

- 引入 React Flow / xyflow 作为画布底座。
- 左侧组件库：输入、VL、提示词组装、能力执行、评分、条件、结果、回调。
- 中间画布：拖拽节点、连线、调整顺序。
- 右侧属性面板：读取能力 schema 渲染参数表单。
- 保存为 `draft` 版本，不允许直接覆盖线上默认版本。
- 支持“试运行草稿”，生成一次完整 runId 和步骤记录。

当前进展：

- 已完成最小闭环：草稿版本可通过步骤编辑器维护 VL/能力步骤，并写回 `recipe.steps`。
- 已完成最小闭环：业务版本卡片可通过页面弹窗提交草稿试运行，不再依赖临时 prompt。
- 未完成：拖拽连线、条件分支、右侧 schema 参数表单、发布申请和验收证据自动绑定仍在下一轮。

验收：

- 可以用页面组出一条图裂变流程草稿。
- 草稿试运行通过后才能申请发布。
- 未通过验收的草稿不能设为默认版本。

### 阶段 4：发布、灰度和回滚

目标：把业务版本治理补完整。

工作：

- 版本状态：`draft`、`testing`、`active`、`deprecated`、`rolled_back`。
- 发布动作必须绑定验收记录、真实样本、回滚目标。
- 支持按比例灰度、按 routeKey 灰度、指定版本调用。
- 回滚只切默认版本，不删除历史版本和运行记录。

验收：

- 新版本上线不需要业务方换接口。
- 发现问题可以在中台切回旧版本。
- 页面能看到哪个版本正在服务、谁发布、何时发布、为什么发布。

### 阶段 5：Coze / Dify / MCP 兼容入口

目标：中台成为核心编排层，外部平台只是入口。

工作：

- Coze 新工作流尽量只调用中台业务 API。
- Dify、MCP、客户端后续也优先接业务 API。
- 如需导出工具箱或 OpenAPI，由业务版本自动生成。

验收：

- 不再因为换一个商业模型就必须手动改多个 Coze workflow。
- 业务方接入方式稳定，内部模型和流程可独立演进。

## 6. 前端技术选择

推荐：

- 管理端画布：React Flow / xyflow。
- 第一阶段只读图不新增复杂编辑依赖也可以先手写轻量布局。
- 第二阶段做草稿编辑时再正式引入画布库。

不建议：

- 直接嵌入 Dify 或 Coze 页面。
- 让业务编排页面编辑 ComfyUI 原生节点。
- 一开始就做完整视觉编程，容易再次扩大复杂度。

## 7. 本轮不做的事

- 不重写 ComfyUI workflow 编辑器。
- 不让业务方直接编辑底层节点。
- 不把 Coze 立刻下线。
- 不把所有历史工作流一次性迁移。
- 不把账单、套餐、收费系统和编排改造绑在同一版本里。
