# v0.3 业务编排工作台与控制点去重方案

最后更新：2026-05-19

## 1. 版本定位

v0.2 已经把业务入口、版本族、接口调用中心、测评端关键文案和逐功能上线门禁收敛到同一条业务主线。

v0.3 要解决的是更深层的问题：业务链条里仍存在多个控制单元，导致一次参数、路由或版本调整需要改多处；业务编排目前也只能看，不能安全地改。

本版本名称：**业务编排工作台与控制点去重版**。

核心目标不是做一个完整 Coze 或 Dify，而是把中台自己的业务编排做成可理解、可受控修改、可验证、可回滚的工作台。

## 2. 当前问题

1. 控制点仍然偏多。业务版本、测评入口、OpenAPI、交付文档、管理端文案、后端 seed、前端兜底映射仍可能各自保留一部分规则。
2. 业务配方可视化还停留在只读。可以看入口、组件和结果，但不能在安全边界内调整步骤参数、默认值、路由和版本说明。
3. 版本继承关系还不够产品化。同一个业务下的迭代版本、灰度版本、回滚版本已经能展示，但还缺“复制为草稿 -> 修改 -> 验证 -> 发布”的固定流程。
4. 业务方接入已经开始转向中台原生 API，但管理端还没有把“接口调用、编排步骤、底层能力调用、验收证据”作为一个完整闭环呈现。
5. 后续要接 VL、MCP、技能、更多商业模型，如果没有组件化框架，每新增一类能力都会继续增加控制点。

## 3. 设计原则

1. **一个业务版本一份配方**：业务版本的输入、输出、步骤、默认值、路由和展示说明都从同一份 recipe 派生。
2. **可编辑但不自由失控**：v0.3 只允许编辑平台已定义的组件和字段，不允许任意代码节点、任意 HTTP 节点或任意脚本。
3. **草稿优先**：线上默认版本不能直接改，只能复制为草稿，草稿验证通过后再发布。
4. **组件先于页面**：先把 VL、ComfyUI、vendor-api、image-ops、评分、回调、计费等抽成组件，再让页面渲染和编辑。
5. **门禁自动读取配方**：上线检查、测评入口、OpenAPI 和交付材料必须从业务配方或其派生物读取，不再手工复制。
6. **不为单台机器写特殊业务逻辑**：158/233 差异只通过执行节点健康、标签、节点兼容性和路由策略表达。

## 4. v0.3 范围

### 必做

1. 控制点盘点矩阵
   - 梳理四个核心业务：花纹提取、图裂变、扩图、裂变评分。
   - 标出每个业务参数当前存在于哪些位置：后端 seed、业务版本、测评入口、OpenAPI、交付文档、前端兜底、发布门禁。
   - 对每个控制点明确：保留、派生、删除或只做兼容。

2. 业务组件目录
   - 建立平台内置组件类型：业务入口、VL 分析、ComfyUI 生图、第三方模型、image-ops、评分、结果回填、回调、计费、人工验收。
   - 每类组件定义输入、输出、错误、路由和可编辑字段。
   - 组件名称使用业务语言，内部能力 ID 只作为排障字段。

3. 受控编排工作台
   - 复用现有 `@xyflow/react`。
   - 第一阶段支持只读图 + 草稿参数编辑 + 节点详情编辑。
   - 不做任意拖拽建复杂图，先支持复制当前业务版本为草稿、调整已有步骤、保存草稿。
   - 每次保存生成配方差异摘要，方便审核。

4. 草稿发布流程
   - 线上默认版本不可直接编辑。
   - 流程固定为：复制草稿 -> 编辑 -> 干跑/真实测试 -> 门禁检查 -> 验收登记 -> 切默认。
   - 回滚只允许切回已验收过的历史版本。

5. 业务调用详情闭环
   - 一个 runId 下展示：接口提交、轮询、业务版本、编排步骤、底层能力、结果、回调、计费和错误。
   - 轮询记录继续折叠，底层能力作为子步骤，不再和业务任务平铺混看。

### 不做

1. 不做完整可视化低代码平台。
2. 不做自由 HTTP 节点、自由脚本节点或任意插件市场。
3. 不做正式收费、支付和套餐。
4. 不做客户端重构。
5. 不把 Coze 工作流全部迁入中台；Coze 仍作为接入层和实验层保留。

## 5. 业务组件初版

| 组件类型 | 业务含义 | 例子 | v0.3 可编辑内容 |
| --- | --- | --- | --- |
| `input` | 业务入口 | 图裂变提交、扩图提交 | 字段说明、必填、默认值 |
| `vl` | 图像理解 | Doubao-Seed-2.0-lite | 使用哪个 VL 组件、提示词模板、输出字段 |
| `comfyui` | 自有 GPU 生图 | 颜色锁定裂变、扩图 | profile、重绘幅度、路由标签、超时 |
| `vendor_api` | 第三方商业模型 | GPT Image 2、Qwen Image Edit | model、质量、尺寸、蒙版、成本标记 |
| `image_ops` | 自研图像处理 | 放大、DPI、尺寸修复 | 强度、尺寸、执行服务 |
| `score` | 质量评估 | 裂变生成图评估 | 评分模型、判定枚举、阈值说明 |
| `result` | 结果整理 | OSS 回填、轻量返回 | 默认返回字段、detail=full 字段 |
| `callback` | 业务通知 | webhook 回调 | 回调策略、失败重试 |
| `billing` | 成本记录 | 按图计费、模型成本 | 只展示和记录，不做扣费 |
| `acceptance` | 验收证据 | 人工验收、样本包 | 验收状态、证据链接 |

## 6. 数据与接口方向

v0.3 尽量不大改表结构，优先复用现有业务版本和 recipe 字段。

建议新增或规范的后端能力：

1. `GET /api/admin/business/component-catalog`
   - 返回可用组件类型、字段、错误、可编辑范围。
   - 已落地（2026-05-19）：后端返回 10 类受控组件：业务入口、图像理解、自有 GPU 生图、第三方模型、图像处理、质量评估、结果整理、业务通知、成本记录、验收证据；每类包含输入、输出、错误、路由、可编辑字段和不可编辑字段。

2. `POST /api/admin/business/capabilities/{id}/drafts`
   - 从当前业务版本复制草稿。

3. `PATCH /api/admin/business/capability-drafts/{draftId}/recipe`
   - 保存受控 recipe 修改。

4. `POST /api/admin/business/capability-drafts/{draftId}/validate`
   - 校验字段、组件、路由、文档、测评入口和门禁。

5. `POST /api/admin/business/capability-drafts/{draftId}/publish`
   - 只允许门禁和验收通过后发布。

如果现有接口已经能覆盖，优先复用现有接口，不为了接口整齐强行新增。

## 7. 管理端动线

业务能力页面按以下顺序重排：

1. 业务入口总览：业务名、线上默认、测试版本、最近调用、最近问题。
2. 编排工作台：图形化步骤、当前选中节点、可编辑字段、差异摘要。
3. 接口调用：按 runId 聚合真实调用。
4. 版本与草稿：线上默认、草稿、历史、回滚。
5. 验收与发布：真实测试、样本包、逐功能门禁、人工验收。

页面文案要求：

- 少用“recipe / executor / provider / workflow”作为主文案。
- 主文案使用“业务入口、处理步骤、执行能力、结果、验收、回滚”。
- 内部 ID 只放在复制、排障和详情里。

## 8. 测试计划

1. 控制点测试
   - 修改图裂变一个参数标签，确认测评端、OpenAPI、交付材料和门禁不会出现第二套文案。

2. 草稿测试
   - 复制图裂变当前默认版本为草稿。
   - 修改重绘幅度默认值或 profile。
   - 保存草稿但不影响线上默认。

3. 编排校验测试
   - 删除必需组件时必须失败。
   - VL 输出字段缺失时必须失败。
   - ComfyUI 路由标签无可用节点时必须失败。

4. 真实运行测试
   - GPU 自有能力必须真实跑。
   - 第三方商业模型可抽检，但跳过必须记录原因。

5. 回滚测试
   - 发布草稿后可切回上一已验收版本。
   - 未验收版本不能作为默认版本。

6. 页面走查
   - 非研发用户能在业务能力页面判断：当前默认是谁、草稿改了什么、最近真实调用是否成功、失败卡在哪一步。

## 9. 封版标准

v0.3 具备封版条件时，必须满足：

1. 四个核心业务完成控制点盘点，并标明保留/派生/删除/兼容。
2. 业务组件目录能覆盖当前四个核心业务的主要步骤。
3. 管理端可以从线上版本复制草稿，并保存受控 recipe 修改。
4. 草稿不会影响线上默认版本。
5. 逐功能门禁能读取草稿和默认版本的配方差异。
6. runId 详情能把业务步骤和底层能力调用作为父子关系展示。
7. 文档索引和 TODO 切到 v0.3，不再把 v0.2 当当前执行目标。

## 10. 风险

| 风险 | 表现 | 处理 |
| --- | --- | --- |
| 编排器做得过重 | 开发周期拉长，页面变复杂 | v0.3 只做受控编辑，不做自由拖拽建图 |
| 草稿影响线上 | 测试改动误伤业务 | 默认版本只读，草稿单独保存，发布必须门禁通过 |
| 控制点清理误删兼容字段 | 老业务方调用失败 | 对外字段先保留兼容，内部逐步归一 |
| 组件抽象过细 | 用户看不懂，维护更复杂 | 只抽业务能理解的节点，内部子步骤隐藏到详情 |
| 多模型参数差异大 | schema 难统一 | 统一任务状态和结果，不强行统一所有模型参数 |
