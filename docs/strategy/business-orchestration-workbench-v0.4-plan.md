# v0.4 业务编排工作台产品化方案

最后更新：2026-05-19

## 1. 版本定位

v0.3 已经把业务组件目录、草稿编辑、草稿发布门禁和 runId 父子链路打通。

v0.4 要解决的是“能用但还不好用、能看但还不够清楚、能排障但链路还偏散”的问题。核心目标是把业务能力页从技术配置页升级为业务工作台，让平台管理员能按业务入口、版本族、编排步骤、接口调用和验收证据完成一条闭环。

本版本名称：**业务编排工作台产品化版**。

## 2. 当前问题

1. 业务名称和版本关系还不够清楚。图裂变下面有 Coze 版、自有 ComfyUI 版、GPT Image 2 版、颜色锁定版等，用户很难判断它们是同一业务的不同版本，还是全新业务分类。
2. 编排图已经存在，但更多是“展示图”。用户还不能围绕图上的节点完成查看参数、创建草稿、修改受控字段、验证、发布这一套操作。
3. 页面仍有一些说明型大段文案。用户真正需要的是“现在谁在线、哪个版本在跑、最近是否成功、失败卡在哪、下一步做什么”。
4. 控制点仍有残留。业务版本、测评端、OpenAPI、交付文档、前端兜底和 smoke 检查之间还可能出现字段、枚举、默认值漂移。
5. 接口调用清单和能力调用清单仍偏分散。业务方调用的是一个接口，但内部会产生 VL、ComfyUI、OpenAI、评分、回填等多个子步骤；管理端需要按 runId 先看业务任务，再下钻子步骤。
6. 业务运行步骤列表和详情页存在加载慢的问题。排障页必须优先轻量摘要，详细请求、响应和长文本按需展开。

## 3. 设计原则

1. **业务入口优先**：先按“花纹提取、图裂变、扩图、裂变评分”等业务入口组织，再展示版本、组件和底层能力。
2. **版本族清晰**：同一业务下的版本必须有继承关系、发布时间、更新时间、更新说明和默认状态；技术版本号只做辅助信息。
3. **图上操作闭环**：编排图不是装饰图。节点至少支持查看、复制为草稿、编辑受控字段、查看最近运行、查看错误。
4. **后端真源驱动前端**：字段、枚举、默认值、错误码、接口样例优先从 `BusinessCapability`、组件目录和错误码总表派生。
5. **业务任务归一**：接口调用、轮询、子能力、结果回填、回调和计费都归到同一个 runId 下面，能力调用只作为子步骤证据。
6. **先受控后自由**：v0.4 不做任意代码、任意 HTTP、复杂条件分支；先把现有业务链路的受控编辑和发布流程做稳。

## 4. 必做范围

### 4.1 业务命名与版本族

- 给业务能力建立明确层级：业务入口 -> 版本族 -> 具体版本 -> 处理组件。
- 图裂变类版本合并到同一业务入口下展示，除非业务特性发生明显变化，例如“四方连续裂变”可作为独立业务入口。
- 每个版本展示：
  - 业务名称
  - 版本名称
  - 继承来源
  - 发布时间
  - 更新时间
  - 最新更新说明
  - 当前状态：线上默认、草稿、历史、停用
- 新增或改名规则：如果不确定是“新功能”还是“版本更新”，必须先确认，不允许随意改功能名。

### 4.2 编排图工作台

- 继续使用 `@xyflow/react`，不引入新的重型编排引擎。
- 编排图数据仍由后端 recipe 和组件目录生成，前端只负责交互和受控编辑。
- 节点交互：
  - 点击节点查看本节点业务说明、输入、输出、错误、路由和最近运行。
  - 默认版本节点只读。
  - 草稿版本节点可编辑受控字段。
  - 节点能跳转到最近失败 runId 或最近成功样本。
- 去掉无意义的全局空白说明框，保留必要的节点详情面板和差异摘要。

### 4.3 草稿编辑产品化

- 页面上形成固定流程：选择业务 -> 选择默认版本 -> 复制草稿 -> 修改节点 -> 验证 -> 真实测试 -> 验收 -> 发布。
- 草稿差异必须用业务语言展示，例如“重绘幅度默认值从 80 调整为 70”，而不是只显示 JSON diff。
- 发布前展示阻断项和可通过项，避免用户只看到“不能发布”。

### 4.4 接口调用中心与 runId 排障

- 新增或强化“接口调用”视角：业务方调用了哪个入口、用哪个 key、返回哪个 runId、当前状态是什么。
- 一个 runId 下展示：
  - 入口请求
  - 业务版本
  - 处理步骤
  - 子能力调用
  - 结果回填
  - 回调或轮询
  - 计费记录
- 业务运行列表默认只加载摘要，详情、步骤大字段、请求响应按需加载。

### 4.5 对外接口与交付文档派生

- 两类接口都要清楚：
  - Coze 工具箱接口：用于 Coze 工作流接入。
  - 中台业务 API：给业务方直接调用。
- 对外文档必须按接口独立成章，包含：
  - 请求地址
  - 认证方式
  - 必填参数
  - 可选参数
  - 枚举值
  - 返回字段
  - 状态枚举
  - 错误码
  - JSON 样例
- v0.4 优先做“从业务版本 schema 生成文档检查项”，不要求一次性生成所有正式交付文档。

### 4.6 页面视觉与文案降噪

- 首页只展示结论和入口，不堆叠长说明。
- 业务能力页按“入口、版本、编排、运行、验收”组织。
- 文案少用 `recipe/executor/provider/workflow` 作为主词，改为“业务版本、处理步骤、执行节点、模型服务、结果回填”。
- 错误展示优先给用户下一步动作，技术详情放到“复制排障信息”。

## 5. 不做范围

1. 不做完整 Coze/Dify 级低代码平台。
2. 不做自由代码节点、自由 HTTP 节点和插件市场。
3. 不做客户端重构。
4. 不做正式支付和商业套餐。
5. 不把 Coze 已有工作流强制迁入中台；Coze 仍作为接入层和实验层。
6. 不为 158/233 单台服务器写特殊业务规则；服务器差异通过执行节点健康、标签、模型完整性和路由策略处理。

## 6. 验收标准

v0.4 具备封版条件时，必须满足：

1. 业务能力页能清楚区分业务入口、版本族、默认版本、草稿和历史版本。
2. 图裂变相关版本不再靠技术名区分，能看到继承关系和更新说明。
3. 编排图节点可点击查看详情，默认版本只读，草稿可编辑受控字段。
4. 草稿发布链路完整：验证、真实测试、验收、发布或阻断原因都能看到。
5. 接口调用中心能按 runId 查看一次业务任务和它的子步骤。
6. 业务运行详情加载速度可接受，大字段按需展开，不拖慢列表。
7. 测评端和管理端关键文案统一，“相似度”这类裂变误导词不再出现。
8. 对外接口文档、错误码、状态枚举和样例经过检查，不再靠口头解释。

## 7. 测试计划

1. 业务版本测试
   - 打开图裂变业务，确认 Coze、自有 ComfyUI、GPT Image 2、颜色锁定版本归属清楚。
   - 验证发布时间、更新时间、更新说明和默认状态正确。

2. 编排图测试
   - 点击每个节点，确认右侧详情能显示输入、输出、路由和最近运行。
   - 默认版本不可编辑。
   - 草稿版本可编辑受控字段，保存后不影响默认版本。

3. 接口调用测试
   - 真实调用一个中台业务 API。
   - 用 runId 在管理端找到入口、步骤、结果、错误或回调记录。

4. 性能测试
   - 业务运行列表只加载摘要。
   - 步骤详情按需展开。
   - 大字段不会导致列表刷新失败。

5. 文案测试
   - 管理端和测评端不把内部技术字段作为主标题。
   - 错误主提示是业务语言，技术明细可复制。

6. 发布前测试
   - 后端测试、前端类型检查和构建通过。
   - 发布 smoke 能覆盖业务接口、Coze 工具箱、测评入口和逐功能门禁。

## 8. 风险与处理

| 风险 | 表现 | 处理 |
| --- | --- | --- |
| 页面继续堆功能 | 用户看不到主线 | 每页只保留当前动作和下一步动作，说明文字移到详情 |
| 编排编辑过度自由 | 发布风险上升 | v0.4 只开放受控字段，不开放任意节点 |
| 版本族整理误伤老入口 | 业务方找不到原接口 | 接口路径不变，只调整管理端展示和文档归类 |
| 前端继续硬编码参数 | 字段漂移复发 | 以 backend schema 和组件目录为真源，前端仅做展示兜底 |
| runId 详情过重 | 列表慢、详情打不开 | 摘要和详情分离，大字段懒加载 |
