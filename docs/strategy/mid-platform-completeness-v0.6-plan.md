# v0.6 中台能力治理与客户端支撑底座方案

最后更新：2026-06-03

本文是 v0.6 主版本方案。v0.6 主线仍然是中台，主语是**能力**，不是项目。中台不负责把行业业务流程硬编码成固定端到端链路，也不以项目管理软件为产品目标。业务流程由客户端组装；中台负责把底层模型、工作流、第三方 API 和媒资能力组装成稳定、可治理、可观察、可计费、可迭代的业务能力。能力定义与边界以 `docs/strategy/ability-definition-v0.6.md` 为准。

口径修正：

- 中台只有能力、能力版本、路由、调用、结果、质量、成本和错误。
- 管理端围绕能力治理，测评端围绕能力验证。
- 客户端业务组装在客户端完成；本阶段客户端只输出方案和边界，不进入中台开发主线。
- 多次能力调用需要关联时，中台只保存调用上下文和资产证据；现有 `projectId` 只能视为兼容字段，不作为中台产品概念继续扩展。

## 1. 版本定位

建议版本名：**v0.6 中台能力治理与客户端支撑底座版**。

v0.5 已完成平台打磨、业务流可视化、质量复盘和页面降噪的第一轮封版。v0.6 的重点不是让中台变成客户端流程引擎，也不是把“项目”做成新的中心对象，而是让中台具备支撑多个客户端业务流程的能力完整性。

核心目标：

- 把原子能力组装成稳定业务能力，而不是把行业流程写死在中台。
- 建立能力管理、封装、优化、迭代、灰度、回滚和质量复盘机制。
- 让客户端可以用业务 API 调用花纹提取、裂变、产品图、模特图、视频等业务能力。
- 为每次能力调用提供 `runId`、可选客户端上下文、资产沉淀和质量/成本证据。
- 管理端能围绕能力观察版本、路由、质量、成本、失败卡点和调用证据，但不接管客户端动线。
- 所有端遵守清晰边界，避免客户端绕过中台直连原子能力。

## 2. 三层架构边界

```text
原子能力层
  -> 中台能力组装层
    -> 客户端业务流程层
```

### 2.1 原子能力层

对象：

- ComfyUI workflow。
- OpenAI、KIE、火山、百度、VL 等模型能力。
- image-ops / vendor-api-ops 等内部能力服务。

职责：

- 执行单个技术能力。
- 返回原始或半结构化结果。
- 不直接面向普通业务方或客户端。

### 2.2 中台能力组装层

对象：

- 能力目录、业务能力 API，例如 `pattern_extract`、`fission`、`product_design`、`outpaint`、`image_edit`、后续 `model_shot`、`promo_video` 等。
- 业务版本、路由、能力绑定、默认参数、质量样本、成本、错误码、运行证据。
- 调用上下文、资产沉淀、选择记录、交付证据。

职责：

- 把一个或多个原子能力包装成稳定业务能力。
- 对外只暴露业务参数、`runId`、状态、结果和业务错误。
- 记录能力版本、路由、执行节点、成本、质量标注、样例表现和回滚证据。
- 提供通用 InvocationContext / Asset / Selection / DeliveryEvidence 证据底座。
- 允许客户端声明“这个 run 属于哪个客户端上下文、哪个业务步骤”，但不决定步骤顺序。

中台不负责：

- 不决定用户下一步必须做什么。
- 不写死花纹到产品图再到视频的固定流程。
- 不维护客户端行业模板和页面动线。
- 不把客户端业务流程做成低代码工作流编辑器。

### 2.3 客户端业务流程层

对象：

- PODI Studio Preview 或业务方自己的前台。
- 行业模板、工作单/项目页面、阶段顺序、用户选择、下一步推荐、最终交付体验。

职责：

- 组装业务流程。
- 决定用户看到哪些阶段、先做什么、下一步做什么。
- 调用中台业务 API 发起能力运行。
- 把 `clientContextId`/兼容 `projectId`、`flowStepKey`、`clientRequestId` 等上下文传给中台。
- 选择候选结果进入下一步。
- 组织最终交付包体验。

客户端不负责：

- 不配置 executor、workflow、LoRA、密钥和底层路由。
- 不直连原子能力、测评 API、ComfyUI、vendor-api 或 image-ops。
- 不自行定义对外业务错误契约。

## 3. 各端职责

| 端 | 第一职责 | 可以做 | 不应该做 |
| --- | --- | --- | --- |
| 中台 backend | 能力组装和业务 API | 业务能力、版本、路由、质量、成本、错误、资产和调用证据 | 固定客户端业务流程 |
| 管理端 | 能力治理和观察 | 能力版本、路由、质量、调用证据、失败卡点 | 面向业务用户生产内容 |
| 测评端 | 内部验证和回归 | 能力测试、批量样例、质量对照、LoRA 批测 | 作为客户端正式前台 |
| 客户端 | 业务流程组装 | 业务动线、行业模板、阶段体验、结果选择、交付体验 | 直连原子能力或管理配置 |
| Coze | 接入和实验 | 快速业务接入、轻量工作流 | 反向决定中台业务模型 |

## 4. v0.6 中台要补齐的能力

### 4.1 业务能力 API 完整性

客户端要能通过稳定业务 API 组装业务流程。中台需要继续补齐：

- 花纹提取。
- 图裂变。
- 扩图。
- 图编辑。
- 产品图生成。
- 多角度 / 组图。
- 模特图。
- 推广视频。

每个业务能力都必须具备：

- 请求 schema。
- 响应 schema。
- 错误码。
- 业务版本。
- 能力绑定和路由。
- OSS 结果沉淀。
- 质量标注入口。
- 成本和调用记录。
- 管理端观察入口。

### 4.2 能力治理闭环

v0.6 的核心不是新增一堆接口，而是让每个能力可控、可解释、可迭代。

每个能力至少要能回答：

- 当前默认版本是什么，候选版本是什么，为什么这么选。
- 底层依赖哪些原子能力、执行节点、模型、LoRA 或第三方 API。
- 最近调用量、成功率、失败类型、平均耗时和成本如何。
- 哪些样例效果好，哪些样例效果差，差在哪里。
- 是否有质量标签、问题标签、分流规则、替代版本和回滚版本。
- 参数、提示词、workflow、LoRA 或模型变化是否可追溯。
- 客户端调用时能否只看到业务参数，而不是底层技术细节。

### 4.3 调用上下文和资产证据底座

中台可以提供通用调用上下文，但上下文不是中台主视角，也不是固定流程引擎。它只是能力调用闭环的证据索引。

中台记录：

- 客户端上下文 ID。
- 能力输入/输出资产。
- 业务 run 与客户端步骤的关联。
- 用户选择了哪些结果。
- 交付包包含哪些资产和 run 证据。

客户端决定：

- 工作单或项目属于什么行业流程。
- 工作单或项目有哪些阶段。
- 阶段先后顺序。
- 哪个阶段调用哪个业务能力。
- 哪个结果进入下一步。

对象与 API 草案只作为历史参考。当前中台主线以 `docs/strategy/ability-definition-v0.6.md` 和 `docs/strategy/ability-api-gap-v0.6.md` 为准。

### 4.4 业务 run 的上下文扩展

现有 `/api/business/{business}/runs` 应支持可选上下文：

- `clientContextId` / 兼容 `projectId`
- `flowStepKey`
- `flowStepName`
- `inputAssetIds`
- `clientRequestId`
- `flowTemplateId`

这些字段只用于记录和观察，不用于中台强制判断流程顺序。

### 4.5 资产和选择记录

中台需要把业务输出沉淀为可复用资产：

- 输入资产。
- 输出资产。
- 来源 `runId`。
- 来源业务能力。
- 客户端步骤。
- 质量标签。
- 是否被选中。

选择记录是业务事实，不等于中台流程决策。它只记录“用户选择了哪张图进入哪个客户端声明的下一步”。

### 4.6 交付包底座

中台可以生成交付包，但交付包内容由客户端或业务方选择。

中台负责：

- 校验资产权限。
- 汇总资产、runId、参数摘要、质量标签。
- 脱敏内部字段。
- 生成 manifest 或 ZIP。
- 提供下载地址。

客户端负责：

- 决定哪些资产进入交付包。
- 决定交付包展示方式。
- 决定行业话术和最终用户体验。

## 5. P0 / P1 / P2 任务

### P0：能力优先边界和契约定稿

1. 更新三端边界：中台组装和治理能力，客户端组装业务，中台不以项目为主语。
2. 定稿能力治理口径、业务能力 API 和调用上下文证据 API。
3. 定稿业务 run 上下文字段。
4. 定稿客户端并行交接文档。
5. 明确客户端禁止绕过业务 API。

### P0：能力治理和 API 缺口清单

1. 盘点现有核心业务能力是否足够客户端串联。
2. 明确产品图、组图、多角度、模特图、推广视频对应的业务能力包装。
3. 每个能力补请求、响应、错误、版本、路由、质量证据、样例、成本和回滚口径。
4. 管理端按能力展示“默认版本、候选版本、质量、失败、成本、路由和优化动作”。

### P1：调用上下文底座

1. 新增或复用调用上下文、资产、run 关联、选择记录、交付证据。
2. 现有业务 run 支持写入客户端上下文。
3. 输出自动沉淀到能力输出资产。
4. 管理端能按能力、runId、客户端上下文查询相关 run 和资产。

### P1：客户端支撑 API

1. 调用上下文兼容查询。
2. 资产登记和查询。
3. 业务 run 客户端上下文写入。
4. 选择记录。
5. 交付包生成。

### P2：管理端能力治理与联调

1. 管理端增加能力治理视图，并在能力详情中挂接 runId、调用日志、输出资产和质量证据。
2. 客户端联调中发现的接口缺口进入中台 TODO。
3. 形成首批客户端未来业务组装所需的中台能力清单和验收标准。

## 6. 非目标

v0.6 中台不做以下事情：

- 不做客户端完整页面。
- 不写死端到端行业流程。
- 不做低代码工作流编辑器。
- 不承诺一键全自动生成。
- 不开放客户端配置 executor、workflow、LoRA 和密钥。
- 不让客户端调用测评 API、原子能力 API 或 Coze 工具箱 API。

## 7. 验收标准

v0.6 中台封版时必须能回答：

1. 客户端未来业务组装所需的能力是否都有稳定业务 API 或明确缺口。
2. 每个业务能力是否有版本、路由、质量、成本、错误和回滚证据。
3. 输出是否能沉淀为受控资产。
4. 资产选择是否能被记录并追溯。
5. 交付包是否能按客户端选择生成。
6. 管理端是否能先从能力维度查到版本、路由、质量和错误，再从 runId 或客户端上下文查到资产和调用证据。
7. 客户端是否没有绕过中台直连底层能力。
8. 文档、错误码、接口契约和测试是否同步。

## 8. 当前决策

- v0.6 主线是中台能力治理与客户端支撑底座。
- 客户端负责业务流程组装；当前中台侧只输出方案、边界和能力缺口，不进入客户端实现。
- 中台负责能力包装、版本治理、路由、质量、成本、调用上下文、资产、选择、交付证据和观察。
- 项目/工作单不是中台主视角；如需关联多次调用，只作为客户端上下文字段进入能力调用证据。
- 旧客户端资料只作为历史参考，不复活旧代码和旧测试结论。
