# 中台细化执行计划（2026-05-07）

## 目标

把当前开发从“口头推进”改成“清单推进”。后续每一项工作必须能回答四个问题：

1. 用户在哪个页面能看到？
2. 对外接口或内部链路在哪里？
3. 怎么验收成功？
4. 做完后记录到哪个文档和回归报告？

本计划只覆盖当前中台主线：`backend/`、`podi-admin-web/`、`podi-eval-web/`、`image-ops-service/`、`vendor-api-ops/` 和文档。客户端暂不进入本阶段。

## 发现的问题

1. 当前唯一 TODO 的颗粒度仍然偏大，容易变成“做一块、忘一块”。
2. 新功能有时已经写进代码，但没有同步暴露到管理端或文档，用户只能靠我们口头说明。
3. 中台自有 API、原子能力 API、Coze 工具箱 API 三类入口之前容易混在一起，业务方和内部人员都难判断该用哪一个。
4. 业务能力的验收证据、真实巡检、回调、计费、回滚还没有完全沉到同一张“上线证据”视图。
5. ComfyUI 两台机器的路由、队列、缺模型、成功但无回填等问题需要持续做成测试用例和页面证据，不能靠临时排查。
6. 账单、权限、商业化框架可以保留骨架，但不能干扰当前核心主线。
7. 文档入口已经清理一轮，但仍需要用“当前有效 / 历史资料 / 待验证”三种身份持续标记，避免旧资料误导开发。

## 同步前端整改规则

后续不再把前端整体整改压到最后。每个编号任务完成时，必须同步判断对应页面是否需要调整：

1. 后端新增或调整入口，管理端必须能看到入口、用途、状态和下一步动作。
2. 新增能力或模型，能力目录、模型弹药库、能力测试和能力调用日志必须同步可见。
3. 新增错误或门禁，页面必须转成业务能理解的提示，不把底层错误码当主提示。
4. 新增调度或路由策略，运行线路或 ComfyUI 纳管页必须能看到路由证据和失败原因。
5. 如果某项暂不做页面，必须在 TODO 里写清楚原因、风险和后续入口。

本轮先从 `API 开放` 页执行同步整改：页面已展示业务 API、原子能力 API、Coze 工具箱，并新增“同步交付门禁”，直接标注页面、文档、错误、冒烟四个状态。

## 当下优先级

1. 先完成 A2/A3/A4：API 入口已经有页面，必须和文档、错误、冒烟检查对齐。
2. 再完成 B1/B2/B3：把管理端当前已做功能继续显性化，减少“功能做了但看不到”。
3. 然后完成 C1/C2/C3：把三主业务从“能跑”推进到“能验收、能回滚、能解释失败”。
4. 同步推进 E1/E2/E3：ComfyUI 路由和队列是业务稳定底座，必须持续用测试和页面证明。
5. 账单、商业化、客户端、完整前端重设计后置，不抢当前中台主线。

## 执行规则

- 开发完成不等于结束，必须同步页面入口、接口文档、错误码、测试和 TODO 标记。
- 每次阶段性收口至少执行：相关单测或构建、浏览器页面走查、`git diff --check`、临时产物清理。
- 线上事故相关链路继续作为发版守护，不作为每日新增功能主线。
- 不再新增散落 TODO。新任务先进入 `docs/strategy/todo-master-2026q2.md` 当前执行单，再实施。
