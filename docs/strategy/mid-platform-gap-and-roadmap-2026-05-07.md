# 中台目标差距分析与后续开发方案（2026-05-07）

## 结论

当前中台已经不是“从零开始”的状态，业务 API、原子能力、Coze 工具箱、管理端、测评端、ComfyUI 双机路由、第三方模型治理、账单骨架都已经存在。

真正的偏差不在“有没有功能”，而在 **是否已经形成稳定、可运营、可验收的平台闭环**。

当前判断：

| 维度 | 当前成熟度 | 结论 |
| --- | --- | --- |
| 代码底座 | 约 65% | 后端路由、服务、模型和管理端模块都已铺开，能承接继续建设。 |
| 平台闭环 | 约 45% | 入口、证据、巡检、回滚、错误、文档还没有完全闭成一条链。 |
| 用户可理解程度 | 约 45% | 页面已有降噪，但仍有大量底层概念和历史入口干扰判断。 |
| 稳定性工程 | 约 55% | 事故后补了 smoke、巡检、队列和兼容性检查，但还没有做到每条主业务都有持续证据。 |
| 商业化准备 | 约 35% | 账单、套餐、成本是骨架，可做内部核对，暂不具备正式对外收费平台能力。 |

所以后续不能再按“缺什么补什么”推进，而要按平台分层补闭环：

```text
业务入口
  -> 业务版本
  -> 原子能力
  -> 路由调度
  -> 执行面
  -> 结果回填
  -> 回调/轮询
  -> 日志/成本
  -> 验收/回滚
  -> 页面可判断
```

只要这条链上任何一段只能靠人工口头确认，就还不是成熟中台。

## 目标平台画像

目标中台不是“后台配置页面”，而是 AI 能力运营平台。它应该做到：

1. 业务方只拿稳定业务 API，不需要懂模型、节点、工作流和队列。
2. 平台管理员能在管理端判断“能不能上线、哪里有风险、下一步做什么”。
3. 开发接入方能用原子能力 API、能力目录、模型弹药库和日志快速接入新能力。
4. Coze 继续作为接入和实验入口，但不再是核心编排真源。
5. ComfyUI、image-ops、vendor-api-ops 只做执行面，不承载平台状态和业务契约。
6. 每条主业务都能追溯版本、路由、执行节点、输出、回调、成本和验收证据。
7. 新能力接入必须同步页面、文档、错误、测试和回归记录。

### 主要偏差

| 目标 | 当前偏差 | 影响 |
| --- | --- | --- |
| 业务 API 是主入口 | Coze 工具箱和历史工作流仍然承担大量实际业务入口 | 新能力上线仍可能需要手改 Coze，版本切换和灰度不够集中。 |
| 业务闭环证据统一 | 验收、巡检、回调、计费、执行节点证据分散在脚本、日志和页面不同位置 | 出问题时仍需要人工拼链路，用户无法一眼判断。 |
| 管理端先总后分 | 总览已经增强，但业务能力、能力目录、ComfyUI 页面仍有底层字段外露 | 非技术用户仍会被概念干扰。 |
| 新能力接入标准化 | 有方法论和部分台账，但不是强制流程 | 容易出现“能力能跑，但页面/文档/错误/测试漏一项”。 |
| ComfyUI 多机利用可证明 | 已有双机路由和兼容性检查，但真实业务分布证据还不够常态化 | 可能再次出现某台机器没跑或队列没吃满，靠人眼发现。 |
| 错误契约完整 | 有错误规范，但三类 API 的错误示例还需逐项对齐 | 业务方遇错时可能不知道是重试、换参数还是找平台处理。 |
| 商业化可对外 | 目前是运营骨架和内部核对能力 | 不能直接作为正式收费、客户自助充值和外部开票系统。 |
| 文档真源稳定 | 入口已清理，但旧文档仍多，深层历史内容可能被搜索命中 | 后续开发容易误读历史方案。 |

## 分层差距明细

### 1. 业务层

目标：花纹提取、图裂变、扩图是平台级业务产品，不只是底层 workflow 包装。

现状：

- 三条主业务 API 已存在。
- 业务版本、默认版本、灰度、回滚、验收记录已存在。
- 管理端已有主业务编排地图和上线证据块。

差距：

- 巡检结果还没有稳定沉淀到业务版本证据里。
- 业务运行详情虽然有闭环视图，但总览、业务页、脚本报告之间仍未完全同源。
- 业务 API 的错误和重试建议还需要和 Coze 工具箱完全对齐。

下一步：

- 把真实巡检结果写入业务版本验收或证据字段。
- 业务详情、总览、发版 smoke 读取同一套证据。
- 对三主业务建立固定用例：成功、缺参、队列满、执行节点不可达、成功无回填、回调失败。

### 2. 原子能力层

目标：所有图、视频、文字、VL、第三方 API 都是可治理的原子能力。

现状：

- 能力目录、schema、默认参数、测试、日志已具备。
- 输出类型已开始区分图片、视频、文字、结构化结果和资源。
- 第三方模型弹药库已接入 Key、出网、成本、验收。

差距：

- 新能力接入流程仍主要靠工程习惯，没有强制清单阻断。
- 能力 schema、错误码、测试、文档之间可能漂移。
- `mock` / 历史兼容 / 占位能力仍需持续压缩，避免混入生产判断。

下一步：

- 建立“新增能力五件套”：schema、执行节点、管理端测试、接口/错误文档、台账记录。
- 能力目录增加“是否可进入业务组合”的明确状态。
- 能力测试结果要能反向影响业务版本上线门禁。

### 3. 调度与执行层

目标：调度层能聪明地分配任务，执行面只执行，不承担平台逻辑。

现状：

- ComfyUI 双机节点已经接入。
- Coze 工具箱提交时会检查队列、尝试换节点、返回队列错误。
- 发布 smoke 有队列汇总和兼容性检查。

差距：

- 真实业务任务分布到 158/233 的证据没有常态展示。
- 队列满、节点不通、缺模型、成功无回填四类问题还需要统一到业务层和测评层。
- ComfyUI 纳管页面功能较多，边界容易扩大，需要保持“轻纳管，不替代 ComfyUI 本体”。

下一步：

- 巡检脚本强制记录实际执行节点。
- 管理端 ComfyUI 任务页展示最近真实业务分布。
- 缺模型/缺节点检查纳入发版前阻断，不靠用户手测。

### 4. 接入层

目标：业务 API 是长期主入口；Coze 是接入和实验入口；未来 MCP/技能/客户端也复用业务 API。

现状：

- 管理端已新增 API 开放页，三类 API 已分开展示。
- 文档已有 business、abilities、coze 三个模块。

差距：

- Coze 工作流仍然是当前大量业务的实际入口。
- 业务 API、原子能力 API、Coze 工具箱在错误、示例和冒烟检查上还没有完全同口径。
- 未来 MCP/技能接入方式还没有落成正式接口策略。

下一步：

- 先把 API 开放页、接口文档、错误码和冒烟清单对齐。
- 新 Coze workflow 优先调用业务 API，不再拼底层能力。
- 后续 MCP/技能只接业务 API 和必要的原子能力 API，不直接接执行节点。

### 5. 管理端

目标：管理端是运营控制台，不是底层字段仓库。

现状：

- 导航已分为总览、业务能力、能力弹药库、运行保障、调用与成本、系统与权限。
- 模块指南已覆盖每个一级入口。
- 总览已有上线结论、运营驾驶舱、战略指标、主业务证据、今日处理顺序。

差距：

- 业务能力、能力目录、ComfyUI 等页面仍有技术概念前置。
- 页面功能多，用户仍可能不知道“现在最该点哪里”。
- 做好的后端能力有时没有第一时间露到前端。

下一步：

- 每个页面顶部固定为：结论、原因、下一步动作、风险。
- 底层字段默认折叠到详情。
- 建立功能暴露台账：新增后端能力必须说明前端入口。

### 6. 测评端

目标：测评端是内部回归和效果验证工具，不是业务方正式前台。

现状：

- 工作流卡片、业务分类、历史状态、非图片输出已降噪。
- 巡检脚本支持限流和失败归类。

差距：

- 测评结果和业务版本上线证据还没有完全打通。
- Coze 工作流和中台业务 API 的对应关系仍需要持续维护。

下一步：

- 测评成功记录可以转成业务版本验收证据。
- 测评端继续作为发版回归面，不抢管理端主线。

### 7. 商业化基础

目标：后续能对外开放 API、收费、限流、统计和结算。

现状：

- 有钱包、套餐、账单、套餐发放、月结、商业报表雏形。
- 业务运行记录已预留成本、额度、来源字段。

差距：

- 正式支付、开票、客户自助、价格策略、合同月结未完成。
- 当前不应作为本阶段主线，否则会稀释中台核心闭环。

下一步：

- 保持账单为内部核对骨架。
- 等业务 API、调用统计、成本口径稳定后，再进入正式商业化阶段。

## 后续开发方案

### 同步前端整改规则

从本轮开始，前端整改不再等所有后端能力完成后统一处理。每个开发项都必须同步判断是否需要页面调整，并按以下口径交付：

| 开发项类型 | 必须同步的前端动作 | 不允许的情况 |
| --- | --- | --- |
| 新增业务入口 | 管理端业务能力或 API 开放页必须能看到入口、用途、当前状态和下一步动作 | 接口已存在但页面找不到 |
| 新增原子能力 | 能力目录、能力测试、能力调用日志必须能看到能力、输入、输出类型和最近结果 | 只能靠接口或数据库判断能力是否可用 |
| 新增模型/第三方 API | 模型弹药库必须显示 Key、出网、计价、验收和失败样本 | 模型已接入但无法在页面判断能否上线 |
| 新增调度/路由策略 | 运行线路或 ComfyUI 纳管页必须展示路由证据、队列和失败原因 | 只能靠日志确认打到哪台机器 |
| 新增错误或门禁 | 页面必须转成业务可理解提示，并给下一步动作 | 页面直接展示底层错误码作为主提示 |
| 新增文档或接口契约 | API 开放页必须同步标注入口类型、文档状态和冒烟状态 | 文档更新但用户不知道在哪里用 |

执行要求：

1. 每个 TODO 编号完成时，必须同时判断“是否有对应前端入口”。
2. 如果暂不做页面，也要在 TODO 中说明原因和后续入口。
3. 页面验收优先本地浏览器走查，记录到回归报告。
4. 后端、文档、错误、测试和前端状态不一致时，该任务不能标记 `done`。

### 第一阶段：把入口和契约钉死

目标：先解决“谁该用哪个入口、接口怎么错、怎么自检”。

任务：

1. 对齐 API 开放页与 `business/abilities/coze` 三份接口文档。
2. 补齐三类 API 的错误码和错误示例。
3. 补 API 冒烟清单，覆盖 OpenAPI、业务提交、任务查询、工具箱导入地址。
4. 管理端总览和 API 开放页明确告诉用户：业务方用业务 API，内部编排用原子能力 API，Coze 用工具箱。
5. API 开放页同步展示页面、文档、错误和冒烟检查四个交付状态。

验收：

- 任意用户打开管理端 `API 开放`，能判断该用哪个入口。
- 文档和页面接口列表一致。
- 阶段发版前能跑或手工执行一套 API smoke。

对应 TODO：A2、A3、A4、B1。

### 第二阶段：把三主业务做成真正产品闭环

目标：花纹提取、图裂变、扩图从“能跑”变成“能上线、能验收、能回滚、能解释失败”。

任务：

1. 把真实巡检结果写入业务版本验收或上线证据。
2. 总览、业务能力页、发版 smoke 读取同一套业务证据。
3. 业务运行详情六段闭环继续补齐：版本、能力、节点、输出、回调、计费。
4. 三主业务固定异常用例：缺参、队列满、节点不可达、成功无回填、回调失败。

验收：

- 每条主业务在管理端都能看到默认版本、最近成功样本、最近失败、回滚版本、验收状态。
- 巡检脚本输出能追溯到 runId、taskId、实际执行节点和输出链接。
- 业务 API 可独立完成提交和查询，不依赖 Coze。

对应 TODO：B3、C1、C2、C3、C4、C5。

### 第三阶段：把能力和模型治理变成强流程

目标：新增能力不再靠经验补齐，而是有强制门禁。

任务：

1. 新能力接入五件套落地：schema、执行节点、管理端测试、错误/文档、台账。
2. 能力目录增加“能否进入业务组合”的判断。
3. 模型弹药库和业务版本门禁统一，缺 Key、缺出网、缺计价、缺验收时阻断默认版本。
4. 输出类型全链路一致：图片、视频、文字、VL、结构化、资源。

验收：

- 新能力接入后，管理端、测评端、接口文档和回归报告都能找到对应记录。
- 生视频、文字、VL 不再被当作生图处理。

对应 TODO：D1、D2、D3、D4。

### 第四阶段：把 ComfyUI 多机稳定性做成证据化运行保障

目标：不再等用户发现某台机器没跑、队列没吃满、缺模型。

任务：

1. 真实巡检记录实际执行节点，区分 158/233。
2. 管理端展示最近业务任务在两台机器上的分布。
3. 发版 smoke 阻断缺模型、缺节点、节点不可达、只有单机可路由。
4. 队列满统一返回可读错误和重试建议。

验收：

- 双机路由不靠口头确认，有页面和脚本证据。
- 233 或 158 缺依赖时，发版前发现。
- 成功无回填不能进入成功闭环。

对应 TODO：E1、E2、E3、E4。

### 第五阶段：管理端整体产品化整改

目标：把管理端从“功能很多”整理成“判断清楚、操作清楚、风险清楚”。

任务：

1. 总览首屏只保留上线、业务、能力、成本、风险和今日处理顺序。
2. 每个模块顶部统一：结论、原因、下一步动作、风险。
3. 底层字段折叠到详情区。
4. 页面改动必须本地浏览器走查并记录。

验收：

- 用户不用理解执行器、节点、workflow，也能完成日常运营判断。
- 做好的功能不会藏在页面深处找不到。

对应 TODO：B2、B4、B5。

### 第六阶段：测评端和商业化后置收口

目标：不让非当前主线打断中台闭环。

任务：

1. 测评端只作为回归和验收面，阶段发版前复跑。
2. 账单继续保持内部核对骨架，不做正式支付和开票。
3. 客户端继续后置，等中台主链路稳定后再重启。

验收：

- 中台主链路未稳定前，不再被客户端或完整商业化分散。

## 执行原则

1. 不再为了单个现象临时改结构。
