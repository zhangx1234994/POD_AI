# v0.5 平台打磨版决策方案

最后更新：2026-05-26

本文是下一阶段任务清单和方案草案，用于决策；在确认前不替代 `todo-master-2026q2.md`。

## 1. 版本定位

建议下一阶段定义为：**v0.5 平台打磨版**。

核心目标不是继续扩新能力，而是把已经跑通的中台、测评端、管理端和核心业务能力打磨到业务方愿意持续使用。

本阶段关键词：

- 打磨平台：状态判断清晰、主路径顺、异常能定位。
- 打磨能力：核心能力有稳定样例、质量标准和失败边界。
- 打磨交互：页面少解释、多结论，用户知道下一步点哪里。
- 打磨细节：加载态、空态、错误态、文案、按钮、表格密度、版本关系都要经得起真实使用。
- 少就是多：每个页面先删冗余、再调布局，最后才考虑新增信息。
- 进入迭代期：围绕每个业务能力持续看效果、标问题、做小改、留证据、再放量。

### 1.1 简洁红线

v0.5 的打磨不是继续叠模块，而是主动减少默认可见内容。以下规则作为所有任务的硬约束：

- 首屏最多回答 3 个问题，不能同时承担总览、文档、排障、统计、发布和周报。
- 一个页面默认只服务一个主要角色，其他角色需要的信息进入详情、标签页或抽屉。
- 每张卡片最多 1 个主结论、1 个关键指标、1 个主动作。
- 状态标签默认最多 4 个，超过的折叠为“更多标签”。
- 表格首屏默认最多 7 列；runId、错误、版本、状态、时间、动作优先，技术细节进详情。
- 长说明文案默认不超过 2 行；背景解释进帮助弹层或文档。
- 原始 JSON、workflow 名、executor 名、模型全名、厂商原始返回，不作为业务方和运营首屏信息。
- “暂无数据 / 未加载 / 待检查”不能伪装成风险；必须和真实失败视觉区分。

### 1.2 每项任务的删减要求

每个 v0.5 任务都必须写清楚：

- 首屏只保留什么。
- 默认折叠什么。
- 直接删除或降级什么。
- 保留下来的信息服务哪个角色。

没有删减清单的页面改造，不进入实现。

### 2.1 管理端总览

现状优点：

- 已经有“线上稳定性与封版判断”“平台功能入口地图”“上线结论”等打磨方向。
- 入口比早期清晰，开始用业务语言表达状态。

问题：

- 加载中、待检查、真实风险混在一起展示，用户容易把“数据未加载”误判成“线上有风险”。
- `主业务 0/3`、`主业务 4/3` 这类数字口径不直观，容易引发不信任。
- 页面同时承担封版判断、入口地图、周报、门禁、巡检、统计看板，首屏重点不够聚焦。

设计方向：

- 总览首屏只回答三件事：现在能不能用、哪里阻塞、下一步做什么。
- 把状态拆成四类视觉语义：正常、真实风险、待人工确认、数据未加载。
- 用“最近更新时间”和“数据来源”标识替代模糊的待检查。

### 2.2 管理端业务能力页

现状优点：

- 业务入口概览已经接近正确方向：按花纹提取、图裂变、图编辑、裂变评分、扩图展示。
- 近 24 小时调用、成功率、最近结果对运营有价值。

问题：

- “业务能力”进入后默认落在调用清单，版本管理、业务链路、调用清单之间的关系仍需更清晰。
- 调用清单列非常密，runId、来源、版本、入口证据、步骤、成本、资源都在一行，排障信息有了但阅读成本高。
- “有 20 条未匹配入口日志”需要更强解释：这是异常、历史数据、内部巡检，还是可忽略？

设计方向：

- 业务能力页改成“业务入口总控 + 业务运行排障”两层。
- 入口总控只看默认版本、最近样本、风险和推荐动作。
- 运行排障按 runId 展开，默认隐藏底层步骤和成本细节。

### 2.3 管理端接口调用页

现状优点：

- 已经按 runId 聚合提交、轮询、异常，这是正确主线。
- 能直接看到最近接口异常、提交任务、轮询结果和关联任务。

问题：

- 页面同时展示业务 API、调用清单、按业务找接口、原子能力、Coze 工具箱，信息层级仍偏重。
- `接口异常 17` 与 `问题 runId 0` 同屏出现，但没有直接说明“这些异常是否已恢复 / 是否影响业务方”。
- 对业务方交付来说，最重要的不是开放能力 45 个，而是当前推荐接哪个业务 API。

设计方向：

- 接口调用页首屏先给“业务方接口健康结论”。
- 异常要分为：参数错误、权限错误、服务错误、已恢复历史错误。
- API 文档、Key、Coze 工具箱放在二级标签，不抢首屏判断。

### 2.4 管理端 ComfyUI 资源页

现状优点：

- 已经有“服务器纳管 -> 能力部署 -> 运行健康 -> 调度效果”的正确闭环。
- 节点重启后检查命令和同构思路清楚。

问题：

- 默认打开“素材库 / LoRA”，而运维最先关心的是服务器健康、队列、节点差异和任务回填。
- LoRA 表格有大量 `—`、`未检测`、复制文件名，像资产底账，不像运维页首屏。
- “资源目录 / 同步发布 / 节点运维”仍偏内部，业务视角不容易判断“158/233 是否能接任务”。

设计方向：

- ComfyUI 默认页改为“线路健康与队列”。
- 资源目录只作为二级资产页；LoRA 表格要加完整度评分和缺字段提示。
- 节点同构差异要形成 checklist：模型、LoRA、插件、workflow、关键节点、真实样例。

### 2.5 测评端首页

现状优点：

- 分类、近 72 小时成功次数、失败样本和功能卡片已经能帮助研发选择入口。
- 能把业务能力和历史运行数据结合展示。

问题：

- 图裂变类卡片过多，技术版本名、标签、近期输出、支持批量、输入输出、底层链路都在卡片内，业务方难以判断应该用哪一个。
- “推荐使用 / 灰度对照 / 历史版本 / 不建议使用”需要更强分层。
- 首页像能力市场，不像业务方试用工作台。

设计方向：

- 首页默认只展示 3-5 个推荐业务能力。
- 历史版本折叠到“对照版本 / 旧版本”。
- 卡片只保留：推荐程度、适用场景、最近成功、是否有失败、进入工作台。

### 2.6 测评端功能工作台

现状优点：

- 单个功能里已有输入、参数预设、运行状态、结果对比、历史打标。
- 对研发排障和质量复盘有价值。

问题：

- 单页过长，输入区、结果区、历史记录、20 条历史样本全部平铺，第一次使用很难聚焦“提交一次测试”。
- 历史记录里每条都带图片对比、评分、备注、参数，导致页面非常长。
- 结果对比和历史打标是两个不同任务，应该拆开。

设计方向：

- 功能工作台拆成三段：运行一次、看结果、复盘历史。
- 当前运行固定在首屏，历史记录放独立标签或右侧抽屉。
- 输入区要明确“必填、推荐、专家参数”，默认隐藏专家参数。

### 2.7 登录页细节

问题：

- 密码框 placeholder 使用圆点，视觉上像已经填了密码，容易误导。

设计方向：

- 密码 placeholder 改成“请输入密码”或为空。
- 登录页减少大面积装饰色，保留专业、简洁、安全感。

## 3. 角色视角评审

v0.5 不能只从研发、管理员或“页面模块”视角评审。每个打磨项都要能映射到真实角色的任务，否则容易继续做成信息完整但不好用的平台。

### 3.1 运营人员视角

运营人员每天关心：

- 今天平台是否能正常对外服务。
- 哪些业务能力近期可推荐给业务方试用。
- 哪些能力有失败、质量波动或成本异常。
- 业务方反馈一个 runId 时，应该让谁处理、下一步是什么。
- 近期用量、成功率、成本和可计费情况能否汇报。

当前痛点：

- 管理端总览有很多状态，但“今天是否可以推荐业务方使用”还不够直接。
- 测评端首页版本过多，运营无法判断推荐哪个版本。
- 接口调用页能看到异常数量，但需要进一步解释是否影响业务方。
- 成本和计费信息分散，运营难以形成客户维度说明。

v0.5 覆盖项：

- `P0-2 管理端总览状态结论页`：给出可用 / 观察中 / 阻塞结论。
- `P0-3 测评端推荐业务入口`：减少版本噪音，让运营知道推荐能力。
- `P0-5 核心业务质量卡`：形成业务方可理解的能力说明和质量边界。
- `P0-6 业务流可视化与流程监控`：能看到业务是否卡在提交、路由、执行、回填或回调。
- `P0-7 出图效果复盘与质量标签体系`：把“效果不好”变成可统计的问题标签。
- `P1-1 接口调用中心打磨`：把异常解释成是否影响业务方。
- `P2-1 商业化前置闭环`：补客户维度用量和成本口径。

验收问题：

- 运营能否在 3 分钟内整理“今天可推荐哪些能力、哪些不建议推荐”？
- 面对业务方反馈，运营能否只用 runId 判断是否需要升级给运维或研发？
- 运营能否解释某个客户近 7 天使用量和成本？

### 3.2 运维人员视角

运维人员每天关心：

- 114 控制面是否健康。
- 158 / 233 等能力机是否在线、队列是否堆积。
- ComfyUI 节点是否同构，插件、模型、LoRA 是否缺失。
- 发布后是否有连接池、后台线程、队列回填、OSS 回填问题。
- 出问题时先止损、再定位、再恢复。

当前痛点：

- 总览和 ComfyUI 页已经有很多诊断，但默认视图还没有完全按运维优先级排序。
- ComfyUI 页默认进入 LoRA 素材库，运维首先想看的是线路健康和队列。
- “待检查 / 未检测 / 未加载”容易和真实故障混淆。
- 节点同构需要 checklist，不应该靠翻表格和日志拼判断。

v0.5 覆盖项：

- `P0-1 平台使用式体检机制`：固定检查 health、队列、接口、页面状态。
- `P0-2 管理端总览状态结论页`：把数据未加载和真实风险分开。
- `P0-6 业务流可视化与流程监控`：把阶段卡点和回填状态可视化。
- `P1-2 ComfyUI 运维页改成线路健康优先`：默认看线路、队列、同构和回填。
- `P1-5 视觉降噪和设计系统收敛`：统一状态语义，避免误判。

验收问题：

- 158 或 233 异常时，运维能否在 1 分钟内知道是节点离线、队列卡住、插件缺失还是回填问题？
- 发布后是否能一眼确认连接池和 finalize loop 没有回归？
- 节点重启后是否有明确的恢复检查顺序？

### 3.3 业务方 / 设计运营视角

业务方和设计运营关心：

- 我要完成图编辑、图裂变、扩图、花纹提取时，从哪里开始。
- 哪个能力是推荐版本，哪个只是历史对照。
- 输入什么、会得到什么、多久能出结果。
- 失败时我应该提供什么信息。
- 平台升级后我是否需要改接入方式。

当前痛点：

- 测评端首页更像能力市场，业务方容易被多个技术版本干扰。
- 工作台参数和历史记录过多，第一次使用不容易完成一次测试。
- 图编辑虽然已跑通，但业务方如何使用、如何更新仍需更清晰。
- 业务方不应该理解 ComfyUI、模型、workflow、节点等底层概念。

v0.5 覆盖项：

- `P0-3 测评端首页推荐业务能力入口`：只展示推荐业务。
- `P0-4 核心功能工作台重构`：先完成一次测试，再看历史和专家参数。
- `P0-5 核心业务质量卡`：明确输入、输出、成功标准和失败边界。
- `P0-7 出图效果复盘与质量标签体系`：让业务方反馈能进入质量改进闭环。
- `P1-4 图编辑业务方交付体验`：明确托管组件和源码组件更新方式。
- `P2-2 能力治理和历史版本清理`：历史版本默认折叠。

验收问题：

- 业务方第一次进入测评端，是否知道应该点哪个能力？
- 业务方能否不理解底层模型也完成一次图编辑或图裂变测试？
- 平台升级后，业务方是否知道自己是否需要更新组件或改参数？

### 3.4 能力工程师 / 开发接入方视角

能力工程师关心：

- 新能力或新模型如何接入。
- 参数 schema、默认值、错误码、测试样例是否完整。
- 模型、LoRA、workflow、执行节点是否绑定正确。
- 一个失败 runId 如何下钻到 ability log、executor、vendor invocation。
- 历史版本和候选版本如何对照。

当前痛点：

- 页面降噪不能把研发排障所需信息删掉，只能分层折叠。
- 测评端历史记录对研发有价值，但不应该压住业务方主路径。
- ComfyUI 资源和能力目录之间还需要更明确的“资源 -> 能力 -> 业务”关系。

v0.5 覆盖项：

- `P0-4 核心功能工作台重构`：历史复盘和专家参数保留，但放到二级区域。
- `P0-6 业务流可视化与流程监控`：从业务失败下钻到具体阶段和证据。
- `P0-7 出图效果复盘与质量标签体系`：给分流、调参、换 LoRA 提供样例依据。
- `P1-1 接口调用中心打磨`：runId 能继续下钻到底层证据。
- `P1-2 ComfyUI 运维页改成线路健康优先`：资源同构和真实任务命中可追踪。
- `P1-3 分流规则与 LoRA 候选治理`：把候选优化变成可验收的版本资产。
- `P2-2 能力治理和历史版本清理`：推荐、候选、历史版本分层。

验收问题：

- 工程师能否从业务失败一路下钻到具体能力日志和执行节点？
- 被折叠的技术细节是否仍然可复制、可排障、可复盘？
- 新能力上线前是否能完整看到 schema、错误码、样例和真实运行证据？

### 3.5 平台负责人 / 管理决策者视角

管理决策者关心：

- 平台是否稳定到可以对外试用或商业化。
- 哪些业务能力有增长价值，哪些只是技术验证。
- 近 7 天成功率、成本、失败原因、客户使用量是否能说明趋势。
- 下一步资源应该投向能力、体验、稳定性还是商业化。

当前痛点：

- 当前平台有数据，但战略指标和客户维度趋势还不够成体系。
- 总览页有周报和战略指标雏形，但与日常运营判断还没完全衔接。
- 成本数据是平台记录口径，不等于商业财务口径。

v0.5 覆盖项：

- `P0-5 核心业务质量卡`：判断哪些能力可重点投入。
- `P0-6 业务流可视化与流程监控`：判断瓶颈在流程哪一段。
- `P0-7 出图效果复盘与质量标签体系`：判断能力质量是否具备迭代空间。
- `P1-1 接口调用中心打磨`：识别接口质量和接入问题。
- `P1-3 分流规则与 LoRA 候选治理`：判断优化收益是否值得放量。
- `P2-1 商业化前置闭环`：客户、成本、额度、账单统一口径。
- 平台使用式体检报告：给阶段汇报提供证据。

验收问题：

- 负责人能否看到五个核心业务的成功率、成本和质量趋势？
- 是否能区分“技术上可跑”和“业务上可交付”？
- 是否能判断下一阶段该投稳定性、体验、能力质量还是商业化？

### 3.6 角色与页面映射

| 角色 | 高频入口 | 首要问题 | v0.5 必须给出的答案 |
| --- | --- | --- | --- |
| 运营人员 | 管理端总览、业务能力、流程监控、质量复盘、测评端首页 | 今天哪些能力能推荐？ | 推荐能力、风险能力、客户反馈如何处理 |
| 运维人员 | 总览、ComfyUI、运行线路、流程监控、调度监控 | 哪个节点或链路异常？ | 节点、队列、同构、回填、日志是否正常 |
| 业务方 / 设计运营 | 测评端首页、功能工作台、图编辑组件 | 从哪里开始，用哪个版本？ | 推荐入口、输入输出、失败时提供 runId |
| 能力工程师 | 能力目录、ComfyUI、接口调用、工作台历史、质量复盘 | 如何接入和排障？ | schema、版本、能力日志、执行节点、样例证据 |
| 平台负责人 | 总览、质量卡、流程监控、周报、成本报表 | 是否可交付、是否值得投入？ | 成功率、成本、趋势、风险和下一步资源投向 |

### 3.7 覆盖度结论

现有 v0.5 方案已经覆盖了平台打磨的主路径，但需要补强三点：

- 运营视角：要能直接判断“今天推荐什么、暂停什么”。
- 运维视角：ComfyUI 默认页必须从 LoRA 素材库切到线路健康。
- 业务方视角：测评端必须弱化历史版本和技术版本名，突出推荐能力和一次测试。

因此 v0.5 的优先级不调整，但每个 P0/P1 任务的验收都要加角色检查，避免只完成页面改版。

### 3.8 角色兼容设计准则

每个被打磨页面必须先写清楚三件事：

- 第一服务角色：这个页面默认帮助谁完成任务。
- 第二服务角色：谁会偶尔进入，但不应主导首屏。
- 不服务角色：哪些底层细节不应该暴露给当前页面的主要用户。

页面设计规则：

- 一个页面只能有一个第一服务角色。否则首屏必然变成大杂烩。
- 第一服务角色看到结论和动作；第二服务角色通过详情、标签页或抽屉看到证据。
- 运维和能力工程师需要的底层字段不删除，但默认折叠。
- 业务方和运营人员看到的主标题必须是业务语言，不用模型名、workflow 名或 executor 名做主标题。
- 所有状态都必须说明“影响什么”和“下一步做什么”，不能只显示成功、失败、待检查。
- 所有页面都必须先做删减清单，再做视觉优化；不能用新卡片掩盖旧噪音。

建议页面角色归属：

| 页面 | 第一服务角色 | 第二服务角色 | 默认隐藏内容 |
| --- | --- | --- | --- |
| 管理端总览 | 运营人员 / 平台管理员 | 运维、负责人 | 底层日志、workflow、模型明细 |
| 业务能力 | 运营人员 / 平台管理员 | 业务方只读、能力工程师 | 原始 recipe、底层步骤明细 |
| 接口调用 | 运营人员 / 开发接入方 | 运维、业务方只读 | 原始 request/response 大字段 |
| ComfyUI 资源 | 运维人员 | 能力工程师 | LoRA 全量底账、测试节点噪音 |
| 测评端首页 | 业务方 / 设计运营 | 运营人员、能力工程师 | 历史版本、灰度版本、底层链路 |
| 功能工作台 | 业务方 / 能力工程师 | 运营人员 | 专家参数、历史全量记录 |
| 质量卡 | 运营人员 / 平台负责人 | 业务方、能力工程师 | 原始日志、厂商返回 |

### 3.9 业务流可视化与效果迭代原则

v0.5 必须把“业务流程怎么看、效果怎么复盘、优化怎么进入版本”做成平台机制。这里的可视化不是做复杂低代码编排器，而是让每个 runId 和每个业务能力都能被观察、被比较、被轻量优化。

业务流可视化原则：

- 以 runId 为主线，不以底层 taskId、workflowId 或 executorId 为主线。
- 一个业务流默认展示 7 个阶段：提交入口、版本命中、输入预处理、路由/分流、主执行、结果回填、回调/计费。
- 每个阶段只显示结论：状态、耗时、关键输入输出、错误码、下一步动作。
- 技术证据仍可下钻：ability log、executor、vendor invocation、ComfyUI prompt/history、OSS 资源。
- 可视化必须支持两种视图：单个 runId 的流程图、某个业务能力近 24 小时/7 天的流程监控汇总。

流程监控原则：

- 监控不是只看成功失败，还要看排队、运行中、回填中、超时、已恢复历史失败。
- 每个业务能力要有阶段耗时：提交到排队、排队到执行、执行到回填、回填到可见结果。
- ComfyUI 类能力必须显示节点命中、队列等待、running 收敛、OSS 回填。
- 第三方模型类能力必须显示厂商状态、重试、耗时、成本和错误码。
- 监控页默认给结论，详情里才展示原始字段和长日志。

效果迭代原则：

- 每个核心业务都要定期抽样看出图效果，不能只看接口成功。
- 结果必须打质量标签，至少包含：可用、可接受但需优化、不可用、需人工复核。
- 问题必须归类，不只写“效果不好”。常见分类包括：主体漂移、颜色漂移、边缘不自然、文字变形、花纹丢失、拼接缝、模糊、风格不一致、结果缺失、耗时过长。
- 图像输入也要归类，例如：复杂背景、文字/Logo、人物/脸、规则纹理、非规则插画、低清图、超宽/超高图、边缘主体、强色彩约束。
- 轻量优化必须走闭环：观察问题 -> 标注图类 -> 提出假设 -> 建候选规则/LoRA/参数 -> 小样本对比 -> 登记结论 -> 再决定是否切默认。

分流与 LoRA 迭代原则：

- 某类图效果不好，优先考虑业务分流，例如图裂变按图案风险、主体类型、文字密度、颜色约束分路。
- 某类图稳定性不高，优先考虑 LoRA / workflow / 参数候选，而不是直接改默认全局配置。
- 新 LoRA 或新路由不能直接替换默认版本，必须先成为 candidate，保留与当前默认的对照样例。
- 每次分流或 LoRA 切换都要记录：触发图类、适用范围、对照样例、收益、风险、回滚方式。
- 小改动也要留证据；没有样例和对照，不进入默认业务版本。

任务：

- 在测评端或管理端为五个核心业务增加效果复盘视图。
- 将历史打标从“评分/备注”升级为“质量档位 + 问题标签 + 输入图标签 + 建议动作”。
- 每个核心业务建立固定回归样例池，至少 5 个样例，后续逐步扩展。
- 每周输出一次“质量问题 TopN”和“推荐轻量优化项”。

验收：

- 平台能回答“哪一类图效果不好”，而不是只知道某次失败。
- 每个核心业务都有最近样例、质量分布和问题 TopN。
- 新优化必须能追溯到具体问题标签和样例。

建议优先级：P0。

### P1-1：接口调用中心打磨

目标：让接口排障从“看很多日志”变成“按 runId 看结论”。

设计方案：

- 首屏展示：
  - 最近 24 小时接口是否正常。
  - 是否有集中 5xx。
  - 是否有集中 4xx。
  - 是否存在影响业务方的问题 runId。
- 异常分层：
  - 用户参数错误。
  - 权限/Key 错误。
  - 系统错误。
  - 已恢复历史错误。

删减清单：

- 首屏只保留：接口健康结论、异常 TopN、问题 runId、推荐动作。
- 默认折叠：原始请求、响应体、完整 header、Coze 工具箱清单、原子能力清单。
- API 文档和 Key 管理进入二级标签，不占默认首屏。
- 直接删除或改写：只有数字没有解释的指标，例如“接口异常 17”必须变成“17 条接口异常，0 个影响中的 runId”。
- 表格默认只显示关键列：runId、业务、状态、错误摘要、最近时间、动作。

任务：

- 把 `接口异常 17 / 问题 runId 0` 解释成自然语言结论。
- 给错误码 TopN 增加“是否需要处理”和“建议动作”。
- 接口文档和 Coze 工具箱移动到二级区域。

验收：

- 业务方反馈问题时，管理员能用 runId 在 1 分钟内定位状态。
- 首屏不出现原子能力长表和 Coze 工具箱长表。

建议优先级：P1。

### P1-2：ComfyUI 运维页改成线路健康优先

目标：让 ComfyUI 页面先回答“节点能不能接任务、队列是否卡住、依赖是否一致”。

设计方案：

- 默认标签改成“线路健康”。
- 四个区块：
  - 节点在线和并发。
  - 队列和 running 收敛。
  - workflow / 模型 / LoRA / 插件同构。
  - 最近真实任务命中和回填。
- LoRA 素材库移到二级标签，增加完整度提示。

删减清单：

- 首屏只保留：节点在线、队列、running 收敛、同构差异、最近真实任务。
- 默认折叠：LoRA 全量表、模型全量表、同步任务历史、测试节点。
- LoRA 表默认只展示异常项和缺字段项；全量底账需主动切换。
- 长命令不在首屏展示，只保留“复制检查命令”。
- 禁止首屏出现：几十行 LoRA 文件名、连续 `—` 字段、未检测项平铺。

任务：

- 将服务器/队列/任务诊断上移。
- LoRA 表格增加“缺基座模型 / 缺触发词 / 未检测”筛选。
- 给 158 / 233 增加同构差异摘要。
- 默认隐藏测试节点和低优先级素材。

验收：

- 158 或 233 出问题时，页面能告诉用户先修哪个环节。
- 运维首屏不需要滚动就能看到 158 / 233 状态。

建议优先级：P1。

### P1-3：分流规则与 LoRA 候选治理

目标：把“哪类图效果不好就分流、哪类图不稳定就换 LoRA”做成受控的小迭代机制，而不是临时改默认配置。

设计方案：

- 为核心业务建立候选优化池：route-rule、LoRA、workflow、参数预设、模型候选。
- 每个候选优化必须绑定问题标签和输入图标签，例如“文字密集图裂变文字变形”“低清花纹提取丢细节”。
- 候选优化状态：draft、candidate、validated、default、paused、rejected。
- 对照方式：同一批样例跑当前默认和候选方案，记录质量变化、耗时变化、成本变化、失败变化。
- 发布方式：候选先进入测评端对照和小流量，不直接切默认。

删减清单：

- 首屏只保留：候选名称、适用图类、解决的问题、对照结论、是否可切默认。
- 默认折叠：完整参数、LoRA 文件全名、workflow JSON、全部历史样例。
- 不展示未绑定问题标签的候选优化，避免候选池变成资源堆。

任务：

- 为图裂变先建立分流规则台账，沿用现有“图案风险/主体类型/颜色约束”思路。
- 为扩图和花纹提取建立 LoRA / workflow 候选记录，标注适用图类和不适用图类。
- 在质量复盘中增加“建议动作”：调参数、分流、换 LoRA、换模型、暂停推荐、人工复核。
- 在业务版本或 metadata 中记录候选优化的适用范围、对照样例和回滚方式。

验收：

- 任一次分流或 LoRA 切换都能说明为什么改、影响哪类图、对照结果是什么。
- 默认版本切换前必须有候选状态和样例证据。
- 不再出现“因为某次失败就全局改默认”的优化方式。

建议优先级：P1。

### P1-4：图编辑业务方交付体验

目标：让业务方知道图编辑怎么用、怎么升级、出错怎么办。

设计方案：

- 推荐交付方式：托管组件优先。
- 源码组件作为高级接入方式，提供版本号和升级指引。
- 接入文档按业务模式拆分：
  - 局部编辑。
  - 参考图替换。
  - 删除修补。
  - 补色校正。
  - 扩展画布。

删减清单：

- 业务方文档首页只保留：怎么接入、怎么提交、怎么查询、怎么升级、失败给什么信息。
- 默认折叠：OpenAI/GPT Image 2 细节、prompt 编译细节、mask 生成内部实现。
- 每个模式只给一个最小请求样例，不平铺所有高级字段。
- 更新方式只给两条：托管组件自动更新、源码组件按 changelog 升级。

任务：

- 输出图编辑业务方使用说明。
- 增加组件版本和更新日志。
- 增加“业务方升级方式”说明：托管组件自动更新，源码组件提供 changelog 和最小 diff。

验收：

- 业务方不用理解 GPT Image 2，也能知道如何接入图编辑。
- 接入文档首页不超过 1 屏半。

建议优先级：P1。

### P1-5：视觉降噪和设计系统收敛

目标：减少页面视觉噪音，让所有页面有一致的信息密度和状态表达。

设计原则：

- 少大段解释，多状态结论。
- 卡片只承载一个对象，不把页面 section 都做成卡片。
- 状态颜色统一：绿色可用、橙色待确认、红色阻塞、灰色无数据。
- 表格默认展示结论字段，技术字段进详情。
- 标签数量控制，超过 4 个折叠。
- 删除无动作的装饰卡片和重复模块。
- 减少同义文案，例如“可用 / 最近可用 / 状态正常”不能在同一对象上重复出现。

删减清单：

- 全局清理：重复说明、无数据空卡、无动作标签、长副标题。
- 全局折叠：技术字段、历史记录、底层链路、原始响应。
- 全局保留：结论、关键指标、主动作、更新时间。

任务：

- 梳理管理端和测评端状态色、标签、表格、空态、加载态。
- 删除重复说明文案。
- 建立页面视觉 QA checklist。
- 建立“首屏噪音检查表”：标签数、卡片数、空态数、长文案数、可见主按钮数。

验收：

- 核心页面截图能明显减少文字密度和标签数量。
- 每个核心页面都能说明本轮删掉或折叠了哪些内容。

建议优先级：P1。

### P2-1：商业化前置闭环

目标：先把成本、额度、账单解释清楚，再谈支付。

任务：

- 统一客户、API Key、业务能力、成本、额度、失败退款口径。
- 接口调用中心和业务运行页展示可计费/不计费原因。
- 做客户维度用量报表。

删减清单：

- 首屏只保留：客户、用量、成功交付、成本、是否可收费。
- 默认折叠：厂商成本明细、内部成本分摊、钱包底层流水。
- 直接删除或降级：无法解释的账务字段和历史实验性指标。

验收：

- 能解释某个客户近 7 天跑了什么、成功多少、成本多少、是否该收费。
- 非财务人员也能看懂客户用量口径。

建议优先级：P2。

### P2-2：能力治理和历史版本清理

目标：减少业务方看到的旧版本和灰度版本。

任务：

- 对 45 个 active abilities 和 49 个测评工作流做推荐级别标记。
- 不再推荐的版本默认隐藏。
- 历史版本保留追溯和回滚，但不进入默认业务入口。

删减清单：

- 默认入口只展示 recommended 和 candidate。
- legacy 只在“历史 / 对照”中出现。
- hidden 不在业务方和运营默认视图出现。
- 能力卡片不再用技术接入时间作为主要排序依据。

验收：

- 测评端默认只暴露推荐能力和候选能力。
- 历史版本不会干扰业务方选择。
- 图裂变默认不再出现十几个平级入口。

建议优先级：P2。

## 5. 推荐实施节奏

### 第 1 周：先打磨主路径

- 平台使用式体检机制。
- 管理端总览状态结论页。
- 业务运行详情增加 runId 七阶段流程图骨架。

- 业务能力页增加流程监控摘要，覆盖近 24 小时/7 天阶段耗时和卡点。
- 五个核心业务质量卡。
- 五个核心业务建立效果复盘视图、质量标签和固定样例池。
- 接口调用中心结论化。
- ComfyUI 线路健康页。

### 第 3 周：统一视觉和治理历史版本

- 图裂变分流规则台账首版。
- 扩图、花纹提取 LoRA / workflow 候选治理首版。
- 状态色、标签、表格、加载态统一。

- 图编辑交付体验说明。
- 业务方试用路径全链路走查。

### 固定迭代节奏

- 每天：看流程监控，重点检查 failed、running 超时、queued 堆积、回填中卡住、已恢复历史失败。
- 每周两次：抽样查看五个核心业务的出图效果，每个业务至少 5 个最近样例，记录质量档位、问题标签和输入图标签。
- 每周一次：输出质量问题 TopN，决定是否进入轻量优化：调参数、分流、换 LoRA、换 workflow、换模型或暂停推荐。
- 每次优化前：必须有问题标签、样例对照、影响范围和回滚方式；没有证据不切默认。

## 6. 需要你决策的问题

### 决策 1：下一阶段是否命名为 v0.5 平台打磨版

推荐：同意。

理由：v0.4.1 已经完成稳定性封版，继续叫稳定性版本会掩盖下一阶段真正目标。v0.5 应明确转向体验、质量和可交付。

### 决策 2：v0.5 是否禁止新增大业务能力

推荐：同意。

理由：当前能力数量已经足够，短板是打磨和稳定交付。新增大能力会继续扩大测试、文档和运维面。

允许例外：

- 修复现有核心能力。
- 为核心业务补小组件或质量检测。
- 为业务方交付补必要接口。

### 决策 3：核心业务优先级

推荐顺序：

1. 图编辑
2. 图裂变
3. 扩图
4. 花纹提取
5. 文字裂变

理由：图编辑最接近组件化交付，图裂变是最大主业务，扩图和花纹提取是高频素材处理，文字裂变仍需质量打磨。

### 决策 4：测评端定位

选项 A：继续内部研发工具。

选项 B：升级为业务方试用/验收工作台。

推荐：选 B。

理由：如果测评端仍是研发工具，业务方永远依赖我们解释；如果变成试用/验收工作台，就能直接暴露真实体验问题。

### 决策 5：管理端设计方向

选项 A：信息完整优先，继续保留较高密度。

选项 B：结论优先，细节折叠。

推荐：选 B。

理由：管理端已经有足够细节，下一步需要降低判断成本。

### 决策 6：历史版本是否默认折叠

推荐：同意。

理由：业务方不应该在图裂变首页看到 12 个同等权重版本。历史版本保留给对照、回滚和研发排障。

### 决策 7：是否允许我每轮都跑真实页面走查

推荐：同意。

方式：

- 每轮至少覆盖管理端 3 个页面、测评端 2 个页面。
- 页面截图进入 `output/playwright/platform-audit-*`。
- 结论进入 `docs/testing/*platform-polish-walkthrough.md`。

如果涉及真实模型成本，先只跑已有历史结果和无成本操作；需要提交真实任务时再单独说明。

### 决策 8：业务流可视化与效果复盘是否作为 v0.5 核心机制

推荐：同意。

理由：下一阶段进入迭代期，平台不能只证明接口成功，还要证明流程可监控、结果可复盘、优化可追溯。业务流可视化负责定位问题发生在哪一段，效果复盘负责判断哪类图不适合当前方案，候选治理负责把分流、换 LoRA、调参数变成可验证的小改动。

边界：

- 不做复杂低代码编排器，只做 runId 七阶段可视化和业务能力流程摘要。
- 不追求一次性覆盖所有图类，先覆盖五个核心业务的固定样例池和问题 TopN。
- 不允许未经过候选对照的新 LoRA、新路由、新参数直接成为默认版本。

## 7. 最小可执行版本

如果希望控制范围，建议 v0.5 MVP 只做这 9 件：

1. 平台使用式体检机制。
2. 管理端总览状态结论页。
3. 测评端首页推荐业务入口。
4. runId 七阶段业务流可视化。
5. 业务能力流程监控摘要。
6. 图编辑工作台打磨。
7. 图裂变工作台打磨。
8. 五个核心业务质量卡和效果复盘标签。
9. 分流规则与 LoRA 候选治理最小台账。

MVP 不做：

- 新增大业务能力。
- 正式支付。
- 完整客户端重构。
- 复杂低代码编排器。
- 全量自动化质量评分；先以人工抽样和轻量标签为主。

## 8. 验收口径

v0.5 封版时必须回答：

- 业务方第一次打开测评端，是否知道该用哪个能力？
- 管理员第一次打开总览，是否知道平台现在能不能用？
- 一个 runId 出问题，是否能 1 分钟内定位到提交入口、版本命中、输入预处理、路由/分流、主执行、结果回填、回调/计费中的具体卡点？
- 每个核心业务是否能看到近 24 小时/7 天的流程健康、阶段耗时和主要卡点？
- 五个核心业务是否都有质量卡、样例和最近稳定性数据？
- 五个核心业务是否都有出图效果复盘、质量档位、问题 TopN 和输入图标签？
- 是否能回答“哪一类图效果不好、哪一类图稳定性不高、建议怎么轻量优化”？
- 分流、换 LoRA、换 workflow、调参数是否都有候选记录、样例对照、影响范围和回滚方式？
- 是否禁止没有样例证据的默认版本变更？
- 图编辑是否有明确的业务方接入和更新方式？
- 页面是否明显少了内部术语、重复标签和无效长文案？
- 每个核心页面是否明确删掉、折叠或下移了哪些冗余内容？
- 首屏是否只保留主结论、关键指标和主动作？
