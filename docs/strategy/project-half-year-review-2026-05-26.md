# POD 项目阶段回顾与半年会材料（2026-05-26）

数据截止：2026-05-26 14:36 CST。本文用于项目半年会沟通，不替代当前唯一执行清单 `todo-master-2026q2.md`。

## 会议目标

这次会议不只复盘“做了多少功能”，而是要回答四个问题：

1. 我们从项目初期到现在，真正验证成立的判断是什么？
2. 哪些问题是阶段性事故，哪些问题是组织方式和产品方法的问题？
3. 当前数据证明平台已经具备哪些生产能力，还缺哪些商业化前提？
4. 下一阶段应该继续加能力、做产品化、做商业化，还是先稳住质量体系？

## 建议沟通维度

### 1. 战略定位：我们到底在做什么

当前已经形成的清晰判断：

- POD 不是单纯“模型能力市场”，也不是把 ComfyUI / OpenAI / KIE / 火山接口简单包一层。
- POD 的核心价值是把分散模型能力组织成稳定的专业设计生产流程：业务入口、版本、路由、任务、素材沉淀、质量评测、回调、计费和可观测。
- 当前主线应继续围绕“专业设计生产平台”，优先服务设计团队、电商运营、内容团队和内部业务方，而不是过早泛化成低代码平台。

需要会上确认：

- 未来 1-2 个季度，北极星指标是否继续采用 `WAU-Task` / 有效业务任务数，而不是能力调用数。
- “业务能力”是否继续作为产品主入口，“原子能力”只作为内部编排和高级开发入口。

### 5. 稳定性和事故复盘：我们学到了什么

近期已经形成的硬规则：

- 封版不能只看接口返回成功，必须看业务 runId 是否闭环、ComfyUI 队列是否收敛、OSS 是否回填、接口调用中心是否出现集中 4xx / 5xx。
- ComfyUI / GPU 类能力必须跑真实任务，不能只看节点 `/health`。
- 业务接口、测评端、管理端和文档必须同步，否则能力实际不可交付。
- 单台机器的问题不能轻易写成长期业务特判，应优先修复节点同构和工作流配置。
- 历史失败不能直接等同封版阻塞，要区分“未恢复失败”和“已被后续成功覆盖的历史失败”。

v0.4.1 事故整改已经完成的闭环：

- 数据库连接池从隐式默认改为显式配置。
- 发布 smoke 增加 `QueuePool` 和 `business run finalize loop failed` 日志扫描。
- ComfyUI 队列诊断区分“观察中”和“疑似卡住”。
- 114 发布后 30 分钟观察窗口通过：业务 failed / running / queued / unresolved 均为 0，ComfyUI blocked / settling 为 0，近 1 小时接口无 4xx / 5xx。

仍需关注：

- route-preview 仍有过 30s 超时记录，虽然最近 2 小时无新增，但说明预览链路不能过重。
- 能力层整体失败率偏高，尤其早期 158 印花提取节点历史失败较多，后续要区分历史配置问题和当前真实稳定性。
- callback 状态在业务运行中目前基本为 `none`，说明回调还没有真正成为生产闭环主路径。

### 6. 产品体验：功能可跑通不等于可交付

近期复盘反复暴露的问题：

- 页面和交互验证经常晚于后端功能验证。
- 管理端曾过度暴露内部字段和长说明，非研发用户很难判断“现在能不能用、哪里异常、下一步做什么”。
- 测评端如果只是参数面板，业务方仍不知道如何稳定使用能力。
- 图编辑这类能力不仅需要 API，还需要托管组件、交互动线、样例、错误提示和更新机制。

下一阶段产品体验的判断：

- 管理端继续做视觉降噪：优先展示结论、状态和下一步，技术细节折叠。
- 测评端要从“开发自测页面”升级为“业务方验收和试用工作台”。
- 面向业务方的图编辑/扩图/花纹能力，优先交付托管组件和稳定版本说明；源码组件更新机制再作为第二层能力。

- callback 未成为主路径。
- 业务成功、成本扣减、失败退款、套餐额度、客户维度用量还没有形成完整账务闭环。

建议会议上不要把商业化理解成“接支付”，而应先确认：

- 哪些业务能力可以被定价。
- 哪些结果算有效交付。
- 失败、重跑、人工复测如何计费。
- API 客户和托管组件客户是否采用同一套餐口径。

### 8. 文档和协作方式：记录能力强，但需要继续降噪

正面：

- 项目有完整的策略、方案、复盘、测试、发布、错误契约和接口文档。
- 近期已经收敛到 `todo-master-2026q2.md` 作为唯一待办入口。
- 发布记录和封版验证比早期明显成熟。

问题：

- 文档数量已经达到 310 个，历史方案、过程记录、旧客户端资料容易干扰当前判断。
- 有些 TODO 和方案在阶段结束后没有及时降级为历史资料。
- 新能力开发时，文档、错误码、接口、测评端、管理端仍容易不同步。

建议：

- 保持“当前回顾 -> 唯一 TODO -> 当前方案 -> 标准规范 -> 历史资料”的阅读顺序。
- 每个版本只保留一个当前主线文档，历史方案必须明确“仅追溯”。
- 新增能力前先写功能定性卡和错误契约，再开发。

## 需要形成的阶段结论

### 结论 1：项目已经证明了中台主线成立

证据是 1,509 次业务运行、50,914 次业务 API 调用、6,845 次测评运行，以及 v0.4.0 / v0.4.1 的线上封版。我们已经能把模型、ComfyUI、OSS、测评、管理端、API Key 和业务版本串成生产链路。

### 结论 2：下一阶段不能继续以“堆能力”为主

45 个 active abilities 已经足够证明接入能力。真正短板是核心业务的稳定性、体验、质量评价、成本闭环和业务方接入方式。继续盲目加能力，会放大测试、文档、路由、错误契约和运维成本。

### 结论 3：业务入口比原子能力更重要

用户不关心背后是 ComfyUI、GPT Image 2、KIE 还是火山；用户关心“图裂变、扩图、花纹提取、图编辑能否稳定产生可用结果”。因此默认产品入口应继续是业务能力，原子能力保留给内部编排、测评和高级开发。

### 结论 4：质量体系要从发版后观察前移到开发过程

v0.4.1 已经把 smoke、health-watch、日志扫描、真实巡检和观察窗口补起来，但更理想的状态是：新能力在进入开发前就有功能定性卡、错误契约、验收样例、成本口径和页面动线。

### 结论 5：商业化前先完成“可交付标准”

当前平台有成本记录和 API Key 记录，但客户可交付还需要：

- 明确每个业务能力的输入限制、成功标准、失败重跑策略。
- 明确 SLA / 预期耗时 / 结果质量边界。
- 明确套餐、额度、成本、退款和客户维度报表。
- 明确托管组件和 API 接入的版本升级方式。

## 下一阶段建议

### P0：稳定性和观测常态化

- 每日固定查看 health、health-watch、业务运行异常、ComfyUI 队列、接口调用中心、OSS 回填和 backend 关键日志。
- 把 route-preview 30s 超时作为专项优化，避免预览链路触发重任务或长等待。
- 区分历史失败、已恢复失败、当前未恢复失败，避免封版判断被历史噪音污染。
- 给核心业务建立按日成功率、P50 / P90、成本、失败原因 TopN 的固定看板。

### P1：核心业务产品化

- 聚焦 3-5 个主业务：图裂变、扩图、花纹提取、图编辑、文字裂变。
- 每个业务沉淀一页“业务定性卡”：目标用户、输入、输出、不可承诺内容、成功标准、错误列表、成本和样例。
- 测评端改造成业务方可试用的工作台，而不是只服务研发的参数测试台。
- 图编辑优先完善托管组件使用、版本更新说明、样例包和错误提示。

### P1：管理端视觉降噪

- 首页先回答“线上是否稳定、是否能封版、哪里阻塞”。
- 业务能力页先展示默认版本、最近成功样本、最近失败、成本和接口入口。
- 接口调用中心突出集中 4xx / 5xx、异常客户、异常路径和最近变化。
- ComfyUI 资源页继续以线路健康、队列收敛、节点同构为主，减少内部字段干扰。

### P2：商业化闭环

- 建立客户 / API Key / 业务能力 / 成本 / 额度 / 账单的统一口径。
- 明确有效交付和失败退款规则。
- 把 callback、账务流水、成本快照和客户报表纳入真实业务链路。
- 先做内部运营可解释，再考虑正式支付和外部套餐。

### P2：文档治理和组织方式

- 当前主线继续只有一个 TODO 入口。
- 历史客户端、旧迁移方案、阶段过程文档继续归档降噪。
- 新能力必须同时提交：业务定性卡、接口文档、错误码、测评入口、管理端入口、真实样例和发布门禁。

## 会上建议直接讨论的问题

1. 下季度是否明确“不以新增能力数量作为目标”，改为以核心业务成功率、有效任务数、业务方可用性为目标？
