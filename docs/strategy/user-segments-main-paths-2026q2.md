# 用户分层与主路径图（2026Q2）

> 状态：accepted-for-IA
> 日期：2026-04-30
> 用途：作为管理端信息架构、权限边界、业务 API 文档和前端易用性整改的输入。

## 1. 结论

当前平台先按三类用户设计，不再让所有人面对同一套“中台配置大杂烩”。

| 用户类型 | 核心目标 | 主要入口 | 不应该被迫理解 |
| --- | --- | --- | --- |
| 业务方 | 稳定提交图像任务并拿到结果 | 业务 API、Coze 接入、业务能力只读页 | ComfyUI 节点、模型密钥、执行线路、队列细节 |
| 平台管理员 | 管业务版本、套餐账单、账号权限和发版风险 | 管理端总览、业务能力、账单费用、账号权限、发布前门禁 | 底层 JSON 细节，除非进入高级配置 |
| 开发接入方 | 接入新模型、新能力、新执行资源并排障 | 模型与 API、原子能力、执行资源、接口文档 | 业务收费话术和运营催收细节 |

设计原则：

- 业务方只看业务结果，不看平台内部。
- 管理员先看“现在要处理什么”，再进入具体模块。
- 开发接入方可以看到底层细节，但入口必须按能力、模型、资源聚合，而不是散在多个页面。

## 2. 业务方主路径

### 路径 A：提交业务任务

1. 拿到业务入口：图裂变、扩图、花纹提取。
2. 传入图片地址、必要参数、业务方请求 ID。
3. 收到 `runId` 和任务状态。
4. 通过查询接口或回调拿最终图片。
5. 出错时只提供 `runId/requestId/traceId` 给平台排查。

业务方页面和文档必须强调：

- 不需要知道底层模型。
- 不需要知道当前默认版本是哪一个，除非他们主动查询。
- 不需要因平台切版本而改入参。

### 路径 B：查看接入是否正常

1. 登录只读业务能力页。
2. 查看自己有权限的业务能力。
3. 查看最近调用成功率、失败样本、回调状态。
4. 将失败任务的 `runId` 交给管理员处理。

业务方不开放：

- 模型密钥。
- 执行线路。
- 工作流模板。
- 其他业务方数据。

### 路径 C：费用与额度确认

1. 查看当前套餐余量和到期提醒。
2. 查看已消费额度和近期任务数量。
3. 收到套餐预警或续费提醒。
4. 由管理员创建购买订单、确认付款、申请发票。

业务方如果后续开放账单页，只给“余额、套餐、消耗、订单、发票”五类信息，不展示内部成本和厂商价格。

## 3. 平台管理员主路径

### 路径 A：每天先看总览

1. 打开总览。
2. 看主业务是否正常：花纹提取、图裂变、扩图。
3. 看“当前先处理什么”：失败、回调、计费、能力健康、发版门禁。
4. 跳转到对应模块处理。
5. 处理后回到总览确认风险下降。

总览页必须避免：

- 第一屏堆配置表。
- 第一屏展示大段底层字段。
- 把“异常原因”藏在二级表格里。

### 路径 B：发布或切换业务版本

1. 进入业务能力。
2. 选择图裂变、扩图或花纹提取。
3. 查看当前默认版本、发布时间、最近调用、失败样本。
4. 对比候选版本和线上版本。
5. 申请或审批默认版本切换。
6. 必要时一键回滚。
7. 运行发布前门禁和巡检记录。

管理员需要看到：

- 版本差异。
- 灰度范围。
- 底层主要能力来源。
- 最近失败是否与新版本相关。

管理员不应被迫先读：

- 完整 workflow JSON。
- ComfyUI 节点编号。
- 第三方原始返回。

这些信息只放在详情和排障区。

### 路径 C：收费、套餐和对账

1. 进入账单费用。
2. 先看异常扣费、待定价、钱包失败。
3. 查看用户或业务方账单。
4. 创建套餐购买订单。
5. 确认付款后自动入账套餐额度。
6. 申请发票并标记已开票。
7. 使用月结和催收通知处理长期客户。

账单页主语言必须是业务语言：

- “购买订单”优先于“充值流水”。
- “套餐余量”优先于“package balance”。
- “待开票 / 已开票”优先于“invoice status”。

## 4. 开发接入方主路径

### 路径 A：接入第三方模型

1. 进入模型与 API。
2. 新增或检查厂商密钥。
3. 同步或录入模型目录。
4. 设置模型能力边界：是否支持蒙版、多图、视频、文本。
5. 设置并发、冷却、额度和计价。
6. 运行最小验收。
7. 绑定到原子能力。

开发接入方需要看到：

- 厂商、模型、接口类型。
- 出网状态。
- 密钥状态和最近错误。
- 成本规则和成功未计费风险。

### 路径 B：接入 ComfyUI / image-ops 能力

1. 进入执行资源。
2. 确认服务器或能力服务在线。
3. 导入 workflow 或能力模板。
4. 绑定输入字段、输出位置和运行线路。
5. 设置并发、标签和兜底策略。
6. 在原子能力里测试。
7. 再交给业务能力组合使用。

开发接入方需要看到底层细节，但仍要按“服务器 -> 模板 -> 能力 -> 业务”的顺序组织，不应散落在多个入口。

### 路径 C：排查线上失败

1. 从业务方拿到 `runId/requestId/traceId`。
2. 在业务运行记录中定位任务。
3. 查看业务步骤进度和当前卡点。
4. 进入能力日志、执行资源、模型与 API 定位底层失败。
5. 修复配置或执行服务后复测。
6. 必要时回滚业务默认版本。

排障页面必须提供复制入口：

- `runId`
- `taskId`
- `abilityLogId`
- `vendorInvocationId`
- 错误码和错误摘要

## 5. 页面与权限映射

| 页面 | 业务方 | 平台管理员 | 开发接入方 |
| --- | --- | --- | --- |
| 总览 | 不开放 | 可看、可处理 | 可看 |
| 业务能力 | 只读自己范围 | 可管理版本、灰度、回滚 | 可看配方和底层来源 |
| 账单费用 | 后续只读简版 | 可管理套餐、订单、发票、月结 | 只看计费风险摘要 |
| 账号权限 | 不开放 | 可管理 | 不开放或只读 |
| 模型与 API | 不开放 | 看风险摘要 | 可管理 |
| 原子能力 | 不开放 | 看健康摘要 | 可管理 |
| 执行资源 | 不开放 | 看服务状态 | 可管理 |
| 发布前门禁 | 不开放 | 可运行、可登记 | 可运行、可排障 |

## 6. 对后续前端整改的要求

1. 每个页面都要有“当前先处理什么”。
2. 业务方页面不出现英文技术词作为主标题。
3. 管理员页面第一屏不展示 JSON。
4. 开发接入页面保留高级配置，但必须折叠或放详情。
5. 同一业务对象只出现一次主入口，避免“能力、workflow、executor、Coze”多处重复管理。
6. 错误提示必须按“发生了什么、先做什么、保留错误码”呈现。

## 7. 验收口径

本分层文档完成后，后续 IA 和页面整改按以下问题验收：

- 业务方是否能只凭 `runId/requestId/traceId` 完成沟通。
- 管理员是否能在 30 秒内知道今天先处理什么。
- 开发接入方是否能按“模型 / 能力 / 资源 / 日志”定位问题。
- 新能力上线是否不要求业务方改入参。
- 账单、订单、发票、套餐是否能用业务语言解释清楚。
