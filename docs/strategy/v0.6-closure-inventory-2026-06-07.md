# v0.6 收口盘点清单

日期：2026-06-07

状态：首轮盘点完成，进入整改排序。本文是 `docs/strategy/v0.6-closure-standardization-plan.md` 的执行清单，目标是先把问题定义清楚，再分批整改。

## 盘点原则

- 中台主语仍然是能力、能力版本、路由、调用、结果、质量、成本、错误、证据和审计。
- 测评端只围绕能力验证和能力体验，不引入项目/工作单作为主概念。
- 客户端负责业务流程组装；中台只提供稳定、可组合、可追溯、可控的能力。
- 对话式改图可暂时归在图编辑分类下用于发现，但长期归宿是 Agent Runtime，必须和可视化/画布式图编辑拆开。
- 每个问题都按影响对象、证据入口和建议处理方式落地，不只写感受。

## 结论摘要

P0 先处理四类问题：

1. 任务提交成功和 `Q1001/Q1002` 错误契约已完成第一轮硬化；发布前只保留回归验证和业务方示例复核。
2. Agent 对话改图、直接图编辑、能力工作台的交互状态模型仍需标准化。
3. `product_design` 固定样例 seed 和测试已补齐；发布前剩线上导入、真实效果复盘和推荐版本门槛。
4. API 文档、错误码总表、前端错误映射、测评端文档之间需要同步校准。

P1 处理能力缺口和长期治理问题：

1. `product_image_set`、`model_shot`、`promo_video` 先补能力契约，不急于全部实现。
2. 多能力 Agent Runtime 先定义不可执行/需追问/需确认的边界。
3. 控制面长期预聚合、质量复盘和接口调用中心继续标准化。

P2 处理体验、文档和技术债：

1. 视觉降噪进入交互状态模型之后再逐页做。
2. 历史客户端、旧项目主语和旧路线文档继续降噪。
3. Pydantic/FastAPI 兼容警告等低风险技术债排入封版前清理。

## P0 清单

### P0-1 任务提交成功和错误契约口径不完整

归类：接口契约 / 错误契约 / 业务接入口。

影响对象：业务方接入开发、客户端团队、测评端、接口调用中心、运维排障。

当前状态：已完成第一轮整改，发布前保留回归验证。`Q1002 / COMFYUI_EXECUTOR_UNAVAILABLE` 已同步到错误码总表、业务 API 文档、Coze 文档、接口一致性准则、管理端/测评端错误映射和解析回归测试；本节作为问题来源和验收口径保留。

问题描述：

- 后端 Coze 插件会返回 `ERR|Q1002|COMFYUI_EXECUTOR_UNAVAILABLE`，此前错误码总表和前端错误映射主要只覆盖 `Q1001 / COMFYUI_QUEUE_FULL`。
- 业务方容易把“接口返回了内容”误认为“提交成功”，尤其在输出中只判断是否包含 `QUEUE_FULL` 时，会漏判执行器不可用。
- 当前已固化“提交成功不等于回调成功”的判断规则，但仍需在发布前跑一次回归，防止后续页面或文档再次漂移。

证据入口：

- `backend/app/routers/coze_podi_plugin.py`：已有 `Q1002 / COMFYUI_EXECUTOR_UNAVAILABLE` 返回路径。
- `docs/standards/error-catalog.md`：已覆盖 `Q1001/Q1002`。
- `podi-admin-web/src/utils/errorMessageMap.ts`、`podi-eval-web/src/utils/errorMessageMap.ts`：前端错误映射已覆盖 `Q1002`。
- `docs/standards/interface-consistency.md`：已有“提交成功不等于回调成功”的基本定义。
- `docs/comfyui-routing-technical.md`：已有 `Q1002` 技术说明，但未同步到对外 API 口径。

建议处理方式：

- 发布前复核 `Q1002 / COMFYUI_EXECUTOR_UNAVAILABLE` 在错误码总表、错误消息映射、业务 API 文档、Coze 文档和测评端说明中仍一致。
- 固化提交成功判断：HTTP 2xx、存在真实 `runId/taskId`、状态为 `queued/running`、无 `ERR|`、无 `errorCode`，才算提交成功。
- 区分 `Q1001` 和 `Q1002`：前者是容量拒绝，后者是路由候选为空、节点不可用或兼容节点不可达。
- 增加测试覆盖：队列满、无可用执行器、执行器不可达、网络波动重试后恢复。

验收口径：

- 业务方按文档实现判断后，不会把 `ERR|Q1002|...` 当成成功任务。
- 前端和接口调用中心能展示“节点不可用/无兼容节点”，并给出可执行下一步。
- 错误码总表、API 文档、前端映射和测试口径一致。

### P0-2 核心交互缺少统一状态模型

归类：交互治理 / 测评端 / 管理端。

影响对象：业务方、运营人员、运维人员、能力工程师、平台负责人。

问题描述：

- 测评端首页已完成推荐区、版本列表常显、辅助导航等第一轮降噪，但核心工作台的状态模型还没有统一成规范。
- Agent 对话改图已经按消息流整改过，但后续继续演进时仍需要固定规则：图片结果进入消息流、二轮基于最新成功结果、新任务隔离、执行状态可见、历史可追溯。
- 直接图编辑和 Agent 对话改图仍容易被误认为同一功能的两个模式，需要在页面、文档和接口上持续保持拆分。

证据入口：

- `docs/eval/eval-platform.md`：已记录样例起步、版本列表常显、辅助导航、AI 图片助手和直接图编辑拆分。
- `docs/standards/version-acceptance-template.md`：已有角色视角和页面验收要求。
- `docs/standards/agent-runtime-regression-matrix.md`：已有 Agent Runtime 回归矩阵。
- `podi-eval-web/src/App.tsx`：已有版本列表、辅助导航、Agent 状态等实现，但状态模型散落在页面代码中。

建议处理方式：

- 新增一份“能力测评端交互状态模型”标准，覆盖空态、样例、上传、提交、排队、执行、成功、失败、重试、历史、排障。
- 每个页面按用户视角复核：业务方看结果，运营看样例和质量，运维看队列/节点/错误，能力工程师看版本/参数/回滚。
- 后续页面改动先写状态模型，再做视觉和布局。

验收口径：

- 用户第一次进入能力页时，知道选哪个入口、上传什么、点哪里、结果在哪里、失败后做什么。
- Agent 类页面像聊天式工作台，不再退回任务表单式体验。
- 直接图编辑和对话式改图在入口、文案、接口和测试报告中保持独立。

### P0-3 `product_design` 固定样例和质量门槛待线上闭环

归类：能力缺口 / 样例质量 / 封版门禁。

影响对象：客户端团队、业务方、运营人员、能力工程师。

问题描述：

- `product_design` 已进入业务 API 范围，代码层已补 5 类默认固定样例 seed 和回归测试；当前剩余风险是线上尚需导入样例、跑真实效果复盘、沉淀质量标签和推荐版本门槛。
- 客户端后续要做端到端业务时，产品设计能力会成为中间关键能力；如果中台只说“有接口”，但没有稳定样例和质量证据，客户端会被迫自行试错。

证据入口：

- `docs/api/modules/business.md`：已包含产品设计业务接口说明。
- `docs/strategy/ability-api-gap-v0.6.md`：明确 `product_design` 需要进入真实测试和质量样例闭环。
- `backend/app/services/business_seed.py`：已有产品设计能力 seed。
- `backend/app/services/business_quality_sample_seed.py`：已补产品设计 5 类默认固定样例 seed。
- `backend/scripts/seed_default_quality_samples.py`：可在部署后重复导入默认固定样例。
- `backend/tests/test_business_api_contract.py`：已有产品设计契约测试基础。
- `podi-admin-web/src/features/admin/integration/business.tsx`：已有产品设计测评样例提示。

建议处理方式：

- 固定至少 5 类产品设计样例：服装、家纺、箱包、包装、电商主图。代码层已提供默认 seed 并有回归测试；线上需部署后执行导入脚本并复查测评端样例数量。
- 每类跑真实线上链路，记录输入、输出、耗时、执行节点、成本、质量标签、问题标签。
- 明确推荐版本门槛：成功率、平均耗时、可接受质量比例、主要失败类型。

验收口径：

- `product_design` 不只“接口可调用”，还要有可复用样例和质量证据。
- 测评端/管理端能看到最近样例、质量结论和是否推荐。
- 客户端团队可以按中台样例决定是否接入，而不是重新摸索。

### P0-4 API 文档和错误文档需要同源校准

归类：文档治理 / 接口一致性。

影响对象：业务方接入开发、客户端团队、内部测试、运维。

问题描述：

- 现有规范已经要求“请求 + 响应 + 错误”，但历史文档中仍存在错误码、成功判断、状态字段和示例不完全同步的情况。
- Agent、Coze、Business、ComfyUI 路由、接口调用中心各自有部分说明，但缺一轮按接口逐项核对。

证据入口：

- `docs/standards/error-contract.md`
- `docs/standards/interface-consistency.md`
- `docs/standards/error-catalog.md`
- `docs/api/modules/business.md`
- `docs/api/modules/coze.md`
- `docs/api/modules/agent.md`

建议处理方式：

- 先从 P0-1 的提交成功和 `Q1002` 开始补齐，再逐个业务接口核对请求、响应、错误、轮询、回调、回填和重试。
- API 文档变更必须同步错误码总表、测评端业务接入文档和前端错误消息映射。
- 新增接口或状态字段时，同时补测试和验收报告模板。

验收口径：

- 业务方只看文档就能完成接入和失败判断。
- 文档中的错误码、前端展示、后端返回和测试断言一致。

## P1 清单

### P1-1 `product_image_set`、`model_shot`、`promo_video` 能力契约缺口

归类：能力缺口 / 客户端支撑。

影响对象：客户端团队、业务方、产品负责人。

问题描述：

- 这三类能力是端到端客户端业务闭环的重要组成，但当前不应该把客户端流程塞进中台。
- 中台需要先定义能力边界、输入输出、错误、成本、样例和是否实现的判断标准。

证据入口：

- `docs/strategy/ability-api-gap-v0.6.md`
- `docs/strategy/ability-definition-v0.6.md`
- `docs/standards/agent-runtime-regression-matrix.md`
- `docs/strategy/client-agent-pack-v0.6/04-api-contract.md`

建议处理方式：

- `product_image_set`：先判断是独立业务 API，还是客户端多次调用 `product_design` 后再沉淀。
- `model_shot`：先选一个品类和有限参数集验证。
- `promo_video`：首版优先图生视频，定义时长、画幅、回调和成本。

验收口径：

- 每个候选能力至少有一页能力契约和固定样例计划。
- 未实现前，Agent 或客户端调用时必须明确“不可执行/需人工确认/需候选方案”。

### P1-2 多能力 Agent Runtime 的路由边界需要提前定义

归类：Agent Runtime / 后端控制面。

影响对象：平台负责人、能力工程师、客户端团队。

问题描述：

- 当前 Agent MVP 已能支撑对话式改图，但未来会加入方法论、流水线、多能力路由、上下文压缩和成本控制。
- 如果继续只靠提示词判断，后续会出现路由不稳定、误调用高成本能力、上下文污染和不可追溯问题。

证据入口：

- `docs/strategy/business-agent-runtime-v0.6.md`
- `docs/standards/agent-runtime-regression-matrix.md`
- `docs/api/modules/agent.md`

建议处理方式：

- 保持轻量 Agent Runtime，不引入重型通用 Agent 平台。
- 后端负责白名单、schema 校验、置信度阈值、风险/成本检查、执行边界、必要人工确认、幂等和审计。
- LLM 只辅助意图识别、上下文摘要和方案生成，不直接授权最终工具调用。

验收口径：

- 每次工具调用都有 routeReason、confidence、baseImageRole、parentRunId 或等价证据。
- 未接入能力必须返回可解释的不可执行或追问，不静默失败。

### P1-3 控制面长期治理还缺后台预聚合和质量视图

归类：控制面 / 可观测性 / 运营效率。

影响对象：运维人员、运营人员、平台负责人。

问题描述：

- v0.6.3 已用短 TTL 和并发折叠解决读接口压力，但长期看仍需要后台预聚合和质量复盘视图。
- 当前可以先作为收口盘点和标准化项，不急于马上实现。

证据入口：

- `docs/strategy/v0.6.3-control-plane-hardening-plan.md`
- `docs/strategy/todo-master-2026q2.md`

建议处理方式：

- 先明确哪些指标必须在线实时，哪些可以后台聚合。
- 后续把成功率、失败分布、耗时、成本、质量标签、推荐版本状态沉淀为统一能力视图。

验收口径：

- 管理端不再依赖大字段和完整步骤明细刷新主页面。
- 运营能按能力看到质量趋势，运维能按能力看到故障趋势。

### P1-4 文档入口和历史资料仍需持续降噪

归类：文档治理 / 团队协作。

影响对象：新 agent、新同事、客户端团队。

问题描述：

- 需要继续明确“当前入口”和“历史参考”的边界。

- `docs/strategy/README.md`
- `docs/strategy/todo-master-2026q2.md`
- `docs/client/`
- `docs/handover/`

建议处理方式：

- 当前入口只保留总 README、战略 README、唯一 TODO、当前收口方案和本盘点清单。
- 历史资料保留但标注“仅历史参考”。
- 客户端资料待 v0.6 收口后再刷新交接包。

验收口径：

- 新 agent 不会误以为当前已经进入 v0.7。
- 不会把客户端业务组装误放进中台主线。

## P2 清单

### P2-1 视觉降噪应排在状态模型之后

归类：交互视觉 / 前端体验。

影响对象：业务方、运营人员。

问题描述：

- 页面视觉确实需要继续优化，但如果没有状态模型，视觉调整容易变成局部补丁。

建议处理方式：

- 先完成 P0-2 的状态模型。
- 再逐页处理信息密度、层级、按钮位置、空态示例、错误提示和移动端适配。

验收口径：

- 视觉调整必须说明主任务在哪里、哪些内容被删掉/折叠/上移、用户下一步动作是否更清楚。

### P2-2 低风险技术债和兼容警告

归类：技术债 / 封版清理。

影响对象：开发维护者。

问题描述：

- 低风险框架兼容警告、历史字段兼容、旧命名残留不直接阻塞当前收口，但应在封版前清理或登记。

建议处理方式：

- 收口整改期间只处理影响接口、状态、错误、交互和文档一致性的技术债。
- 其余进入封版报告剩余风险。

验收口径：

- 不让低风险技术债干扰 P0 整改节奏。
- 封版报告中有明确剩余风险和后续版本建议。

### P2-3 客户端交接包需在 v0.6 收口后刷新

归类：客户端协作 / 后续路线。

影响对象：客户端团队、新 agent、平台负责人。

问题描述：

- 当前客户端资料可以作为历史参考，但 v0.6 收口期间会调整能力契约、错误契约和 Agent 边界。
- 如果现在刷新客户端交接包，容易很快过期。

建议处理方式：

- v0.6 收口先完成中台能力边界、接口文档、错误契约和样例质量。
- 收口封版后，再输出新的客户端能力调用包。

验收口径：

- 客户端团队拿到的是已收口后的稳定能力边界，不是中途版本。

## 建议整改批次

### 批次 A：错误契约和提交成功标准

范围：P0-1、P0-4。

状态：P0-1 已完成第一轮整改；本批次在发版前只跑回归验证和业务方示例复核。

动作：

- 复跑 `Q1002` 解析测试，确认 `ERR|Q1002|...` 不会被判为提交成功。
- 复核提交成功判断口径：HTTP 2xx、真实 `runId/taskId`、`queued/running`、无 `ERR|...`、无 `errorCode`。
- 复核业务方可用的错误判断示例，避免外部系统只判断 `QUEUE_FULL`。

### 批次 B：交互状态模型

范围：P0-2。

动作：

- 新增能力测评端交互状态模型。
- 按图编辑、AI 图片助手、花纹提取、产品设计四类核心路径先做走查。
- 后续 UI 改动先按状态模型验收。

### 批次 C：产品设计样例质量闭环

范围：P0-3。

动作：

- 固定 5 类样例。
- 线上真实跑一批。
- 输出质量标签、问题标签和推荐版本判断。

### 批次 D：能力缺口契约

范围：P1-1、P1-2。

动作：

- 为 `product_image_set`、`model_shot`、`promo_video` 输出能力契约草案。
- 明确未接入能力在 Agent 和客户端调用中的不可执行/追问/候选方案口径。

## 下一步建议

建议先执行批次 A。原因是它直接影响业务方是否误判任务成功，也是最近线上和测试服已经暴露过的问题；同时改动范围可控，能快速形成标准化示范。
