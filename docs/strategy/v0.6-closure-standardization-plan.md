# v0.6 收口整改与标准化方案

日期：2026-06-07

## 版本定位

v0.6 当前不进入 v0.7。这个阶段不是扩张新版本，而是把 v0.6 之前沉淀下来的缺失内容补齐，把不合理的交互、接口、文档和处理机制统一整改，形成可继续迭代的标准底座。

本阶段重点是“补齐、纠偏、标准化、复盘优化”：

- 补齐缺失能力、缺失样例、缺失文档和缺失错误契约。
- 纠偏不合理的信息架构、页面动线、Agent 交互和业务边界。
- 标准化任务提交、路由、队列、执行、回填、回调、失败、重试和封版判断。
- 复盘长期踩过的坑，把经验沉淀到规则、测试和文档中。

## 边界

### 当前目标

- 当前主线仍是 v0.6 收口。
- 中台继续只围绕能力、能力版本、路由、调用、结果、质量、成本、错误、证据和审计。
- 测评端继续只围绕能力验证和能力体验，不引入项目/工作单主概念。
- 客户端继续由独立团队或新 agent 并行推进；中台只输出能力边界、业务 API、调用上下文、禁止项和验收标准。
- 对话式改图可以暂时归在图编辑分类下用于发现，但长期归宿仍是 Agent Runtime；它必须和可视化/画布式图编辑保持命名、交互、API 边界和能力定义拆分。

### 当前非目标

- 不启动 v0.7 开发主线。
- 不在本仓库实现新客户端。
- 不把中台改成项目管理产品。
- 不一次性扩张所有产品图、组图、模特图、视频能力。
- 不为了视觉好看重做页面；先解决用户动线、状态、结果、错误和下一步动作。

## 处理步骤

### 1. 版本口径回收

目标：把当前执行入口从 v0.7 回调到 v0.6 收口整改版。

范围：

- 唯一 TODO。
- 总文档入口。
- 战略索引。
- v0.6.3 控制面方案。
- Changelog。

验收：

- 新 agent 只看 `docs/README.md`、`docs/strategy/README.md` 和唯一 TODO，就能判断当前仍在 v0.6 收口阶段。
- v0.7 只作为后续路线储备，不作为当前执行入口。

### 2. 全量盘点缺失项

目标：先盘清问题，再进入整改，避免继续凭局部体验补丁推进。

盘点维度：

- 能力缺失：能力定义、推荐入口、固定样例、质量标准、错误契约、成本估算是否完整。
- 接口缺失：请求、响应、错误、状态、示例、成功判断、回调/轮询说明是否完整。
- 交互缺失：首屏主任务、下一步动作、结果位置、历史任务、错误重试、移动端可用性是否清楚。
- 流程缺失：提交、排队、执行、回填、回调、失败、重试、超时、取消、幂等是否标准化。
- 文档缺失：当前入口、历史资料、客户端边界、错误规范、发布 SOP 是否冲突或陈旧。

验收：

- 输出一份 v0.6 收口盘点清单，按 P0/P1/P2 分级。
- 每个问题必须有归类、影响对象、证据入口和建议处理方式。

### 3. 业务逻辑和处理机制标准化

目标：把长期靠经验判断的流程固化成标准契约。

必须标准化的问题：

- 什么叫任务提交成功。
- `runId/taskId` 生命周期。
- 能力、能力版本、推荐版本、候选版本、默认版本的关系。
- 路由到执行节点的判断逻辑。
- `Q1001 / COMFYUI_QUEUE_FULL` 和 `Q1002 / COMFYUI_EXECUTOR_UNAVAILABLE` 的边界。
- 队列满、节点不可用、兼容候选为空、网络波动的不同处理。
- OSS 回填、结果入库、回调、轮询、失败重试、超时的标准流程。
- Agent 对话改图、直接图编辑和后续 Agent Runtime 的边界。

验收：

- 每条机制都有一份可引用文档或规范位置。
- 关键机制有回归测试或巡检脚本覆盖。

### 4. 交互治理专项

目标：解决“能跑但不好用、每页局部修、没有整体交互规划”的问题。

方法：

- 每个核心页面先写用户动线：用户来这里要完成什么。
- 每个复杂交互先写状态模型：空态、加载中、排队中、执行中、成功、失败、可重试、需确认、需追问。
- 每个能力工作台先定义首屏主任务、结果区域、历史区域和排障区域。
- Agent/ChatBot 类界面按消息流、工具调用、执行状态、结果图片、历史任务和新任务隔离设计，不再手搓临时表单式聊天。
- 使用 Product Design 和前端交互技能作为设计 brief 和验收辅助，但以业务方、运营、运维、能力工程师、接入开发者、平台负责人六类视角为最终判断。

验收：

- 核心页面都有用户动线和状态模型。
- 页面整改后必须用浏览器模拟用户操作，不只看截图。
- 每次页面改动必须说明删掉、折叠、保留或上移了什么。

### 5. 接口文档和错误契约补齐

目标：让业务方和客户端团队能按文档正确接入，不依赖聊天记录或人工解释。

每个业务接口必须补齐：

- 请求字段。
- 响应字段。
- 成功判断口径。
- `runId/taskId` 和状态字段。
- 错误码。
- 参数错误、依赖失败、队列满、节点不可用、超时、供应商失败。
- 轮询、回调、回填和重试说明。
- 示例 JSON。

验收：

- 修改过的接口同步 API 文档、错误码总表和接口一致性规范。
- `ERR|...`、`errorCode`、HTTP 状态码和业务状态的判断口径一致。
- 测评端文档能直接复制给业务方联调。

### 6. 能力缺口和样例质量补齐

目标：把客户端未来会用到的能力先标准化，不急于全部实现。

范围：

- `product_design`：补固定样例、线上实测、效果复盘和推荐版本门槛。
- `product_image_set`：先定义能力契约、输入输出、错误、样例和成本。
- `model_shot`：先定义模特图能力边界、素材要求、失败原因和质量标签。
- `promo_video`：先定义视频能力边界、时长、输入资产、回调、成本和失败恢复。

验收：

- 每个候选能力至少有定义、样例、错误契约和是否进入实现的判断标准。
- 不把客户端流程硬塞进中台。

### 7. 全链路回归和封版报告

目标：收口完成后用真实业务证明稳定，而不是只靠单元测试或局部页面走查。

范围：

- 所有 Coze 接口。
- 所有自有业务接口。
- 每个核心接口至少 5 个真实案例。
- 关键提交接口做 3-5 并发。
- 管理端排障链路。
- 测评端真实用户动线。
- 接口调用中心、任务状态、结果回填和 OSS 一致性。

验收：

- 输出 v0.6 收口封版报告。
- 报告必须包含已覆盖错误场景、剩余风险、回滚方式和下一阶段建议。

### 8. 复盘沉淀

目标：把这段时间踩过的坑变成规则，不再反复靠人工提醒。

沉淀内容：

- 哪些机制必须标准化。
- 哪些交互模式以后禁止再出现。
- 哪些错误契约必须强约束。
- 哪些能力可以进入下一阶段。
- 哪些问题必须在开新版本前解决。

验收：

- 更新事故改进日志、交付方法论、接口一致性准则和当前 TODO。
- v0.6 收口结束后，再评估是否进入 v0.7。

## 默认执行顺序

1. 先完成版本口径回收。
2. 做全量盘点清单，只盘点不改功能。
3. 根据盘点结果锁定 P0：路由/错误契约、核心交互、核心接口文档。
4. 按 P0 分批整改，每批都做真实页面和接口验证。
5. 补 P1 能力缺口、样例和质量标准。
6. 跑全链路回归。
7. 输出 v0.6 收口封版报告和下一阶段建议。
