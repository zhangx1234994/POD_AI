# v0.6.3 中台能力控制面硬化方案

日期：2026-06-04
最后更新：2026-06-05

## 版本定位

v0.6.3 不是重新定义中台，也不是开客户端实现分支。它是在 v0.6.2 封版后，把中台能力体系从“功能能跑通”继续推进到“控制面可承压、能力可治理、Agent 可持续演进、文档和验收有硬标准”的小版本。

当前主语仍然是能力：能力定义、能力版本、路由、调用、结果、质量、成本、错误、证据和审计。客户端负责业务流程组装，中台只提供可组合、可追溯、可控的能力。

2026-06-05 补充验收：线上提交 `88d48dce` 已完成 AI 改图助手 5 组 Agent 验收和控制面 20 并发基准，记录见 `docs/testing/2026-06-05-v0.6.3-88d48dce-agent-control-plane-validation.md`。该提交仍归入 v0.6.3 当前主线，不另起 v0.6.1 口径。

## 非目标

- 不把中台改成项目管理产品。
- 不复活旧客户端代码，不在本仓库实现新客户端。
- 不让前端直接调用 ComfyUI、OpenAI、KIE、火山、百度等厂商接口。
- 不引入重型通用 Agent 平台；v0.6.3 继续使用轻量 Agent Runtime，但要把会话、路由、上下文和确认执行边界做扎实。
- 不为了新增能力堆页面入口；新增前必须先定义能力契约、验收样例、错误契约和回滚口径。

## 开工验收标准

以下标准在开发前即生效，封版时逐项核对。

### 范围边界

- 本版必须覆盖：能力控制面读接口承压、Agent Runtime MVP 整改、能力治理页面降噪、固定样例/质量证据闭环、文档清理和验收报告。
- 若修改业务入口、能力路由、Agent、模型调用、结果回填或交互验收，必须跑真实业务全链路；成本不是跳过理由。
- 若只修改文档或纯样式，也要说明不影响接口、路由、数据库和线上任务状态。

### 响应速度

- `/health` p95 <= 300ms。
- 管理端/测评端高频只读接口 p95 <= 1500ms。
- 业务提交接口 p95 <= 3000ms，不含模型运行时长。
- 业务查询/轮询接口 p95 <= 1000ms。
- 控制面 20 并发只读成功率 100%，p95 <= 3000ms。
- 本版重点关注 `/api/admin/business/capabilities`、`/api/admin/business/usage-summary`、`/api/admin/business/api-key-usage`、`/api/admin/comfyui/queue-summary`，不能再依赖全量 JSON 实时扫描支撑高频看板。

### 真实业务回归

- 受影响业务每个入口至少 5 个真实案例，参数随机并覆盖边界。
- 核心业务巡检至少覆盖 `pattern_extract`、`fission`、`outpaint`；若本版触碰 `product_design`、`image_edit`、`text_fission`，对应能力也必须进入 live patrol。
- Agent 改图若有代码变更，至少覆盖 5 组真实对话：首轮改图、二轮续改、新任务隔离、模糊意图追问、重复确认幂等。
- 每条真实任务必须闭环到 runId、结果 URL、OSS 回填、执行节点证据、接口调用中心记录和页面展示。

### 并发与稳定性

- 核心只读接口 20 并发成功率 100%。
- 业务提交按影响范围设置 3-5 并发真实任务，观察队列、数据库连接、执行节点路由和回填。
- 发布观察窗口内新增集中 5xx/异常 4xx 为 0。
- 业务 `failed/running/queued/unresolved` 不得出现异常残留。
- ComfyUI 至少两台支持服务器可见，总 running/pending 正常收敛，feed gap 为 0。
- 数据库不得出现新的 `QueuePool`、死锁、锁等待超时或 finalize loop 回归。

### 错误路径

新增或修改接口必须覆盖并记录：

- 缺少必填字段。
- 依赖服务失败。
- 超时。
- 队列满或并发限制。
- 鉴权失败。
- 低置信度需要追问。
- Agent 旧方案确认。
- Agent 确认中重复点击。
- 下游供应商失败。

错误码必须同步 `docs/standards/error-catalog.md`，接口说明必须包含请求、响应和错误。

### 文档门禁

- 本版变更必须同步唯一 TODO、相关方案、API 文档、错误码、测试报告、版本记录和事故改进日志。
- 每次封版后清理陈旧入口：旧客户端主线、旧项目主视角、过期 Coze 迁移说明、已废弃页面说明不能继续占据当前主线。
- 验收报告必须记录实际命令、真实业务报告路径、响应速度、并发结果、线上观察结论和保留风险。

## 工作包

### P0-1 控制面读接口预聚合与承压治理

目标：把 v0.6.2 暴露出的看板实时统计压力继续收敛，避免高频页面依赖全量 run/step JSON 扫描。

范围：

- 为业务使用摘要、接口调用中心、能力版本指标、质量样例统计建立轻量聚合或短 TTL 缓存。
- 对会访问外部执行节点的摘要接口采用短 TTL 加同 key 在途请求合并，避免并发刷新形成下游探测风暴。
- 高风险接口只返回首屏必需字段，详情按需加载。
- 明确缓存失效边界和最大陈旧时间。
- 补并发基准脚本和封版阈值；脚本入口为 `backend/scripts/control_plane_read_benchmark.py`。

验收：

- 20 并发控制面读接口全部通过。
- p95 达到本方案响应速度标准。
- 大字段、原始响应、步骤明细不会在列表接口默认加载。
- `business_api_usage` 等管理端高频读接口允许短 TTL 可见延迟，但导出和业务执行链路保持实时查询。

### P0-2 Agent Runtime MVP 整改

目标：把 AI 改图助手从“能聊天并提交任务”整改成可持续演进的 Agent Runtime 样板。

范围：

- 对话流按聊天瀑布呈现，结果图片作为消息进入流，不沉底。
- 同一会话二轮续改默认基于上一轮成功输出，不再回到原始图。
- 新任务必须显式隔离上下文。
- 每次方案保留 `routeReason`、`confidence`、`baseImageRole`、`parentRunId`、`missingFields`。
- 低置信度或输入不足时追问，不能直接执行。
- 确认执行幂等，重复点击不重复创建下游 run。
- golden cases 固化到测试，覆盖规则 planner 和模型 planner 兜底路径。

验收：

- 5 组真实对话全链路通过。
- 多轮续改、新任务隔离、重复确认和模糊意图都有可见证据。
- 后端仍是工具调用最终控制面，前端不直接决定底层能力。

### P0-3 能力治理和测评端降噪

目标：让运营、运维、业务方、能力工程师进入页面后先看到当前结论和下一步动作，而不是被无关模块和历史内容打散。

范围：

- 测评端能力分类只展示当前分类相关主能力和辅助能力。
- 推荐版本区域保持展开，版本列表不再空折叠。
- 辅助工具要有独立导航，但不得抢占业务方主路径。
- 首次使用能力时提供合适示例、图例和固定样例，不用硬文字说明堆页面。
- 清理“项目”主视角文案，中台和测评端只按能力表达。

验收：

- 业务方第一次进入能判断选哪个能力、用哪个版本、上传什么样例、结果在哪里看。
- 运维能快速看到路由、队列、执行节点和错误聚合。
- 运营能看到固定样例、质量标签和复盘入口。

### P1-1 首批能力缺口闭环

目标：继续把客户端未来业务组装需要的能力缺口转成中台能力契约，而不是把流程塞进中台。

范围：

- `product_design` 继续做线上实测、固定质量样例和效果复盘。
- `product_image_set`、`model_shot`、`promo_video` 先补能力定义、输入输出、错误码、成本和验收样例。
- 是否实现由验收样例和业务优先级决定，不一次性铺开所有能力。

验收：

- 每个候选能力至少有能力定义、推荐入口、错误契约、固定样例和封版门槛。

### P1-2 文档和规则清理

目标：保证文档能指导下一轮开发，而不是沉积历史噪音。

范围：

- 清理当前主线文档中的旧客户端、旧项目主语和过期阶段计划。
- 更新错误码、接口一致性、发布 SOP 和事故改进日志。
- 建立每个版本“开工验收标准 -> 开发 -> 真实回归 -> 封版报告 -> 复盘改进”的闭环。

验收：

- 新 agent 或新同事只看 `docs/strategy/README.md` 和唯一 TODO 就能恢复主线。
- 文档入口不再把历史方案误认为当前任务。

## 默认执行顺序

1. 先做 P0-1：控制面预聚合和承压治理，避免下一轮开发继续被看板性能拖住。
2. 并行设计 P0-2：Agent Runtime 整改方案和 golden cases，先把接口契约与测试口径定死。
3. 再做 P0-3：测评端和治理页面降噪，确保能力边界、推荐版本和辅助工具的交互不再混乱。
4. 最后推进 P1：能力缺口和文档清理，按实际测试效果决定是否进入实现。
