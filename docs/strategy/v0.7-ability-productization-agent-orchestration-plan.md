## 版本定位

v0.7 的目标不是继续堆功能入口，而是把 v0.6 已经跑通的中台能力体系推进到“可产品化、可观测、可优化、可被 Agent 和客户端稳定调用”的阶段。

中台主语仍然是能力：能力定义、能力版本、路由、调用、结果、质量、成本、错误、证据和审计。客户端负责业务流程组装，中台只提供稳定、可组合、可追溯、可控的能力。对话式改图继续暂放在图编辑分类下用于发现，但它的长期归宿是 Agent Runtime，不等同于可视化/画布式图编辑。

## 非目标

- 不把中台改成项目管理产品。
- 不在本仓库实现新客户端；客户端只消费中台能力和业务 API。
- 不让前端直接调用 ComfyUI、OpenAI、KIE、火山、百度等厂商接口。
- 不引入重型通用 Agent 平台；本阶段继续做轻量 Agent Runtime，但要把会话、路由、上下文、确认、审计和错误契约做扎实。
- 不一次性覆盖产品图、组图、模特图、视频的所有生产场景；先按固定样例和业务优先级逐个产品化。

## 开工验收标准

每个 v0.7 子版本必须在开工前写清以下口径，封版时逐项补证据：

- 响应速度：高频只读接口 p95 <= 1500ms，控制面 20 并发成功率 100%，业务提交接口 p95 <= 3000ms，不含模型运行时长。
- 真实业务：受影响能力至少 5 个真实案例；触碰 Agent、路由、模型调用、结果回填或交互验收时，成本不是跳过理由。
- 错误路径：缺参、依赖失败、超时、队列满、无可用执行器、低置信追问、重复提交、供应商失败必须有明确错误码和页面呈现。
- 并发稳定：涉及任务提交时至少做 3-5 并发真实任务，观察队列、数据库连接、执行节点路由和结果回填。
- 文档门禁：接口变更必须同步 API 文档、错误码总表、接口一致性规范、测试报告和 Changelog。
- 角色视角：每次页面或能力调整必须按业务方、运营、运维、能力工程师、接入开发者、平台负责人六类视角做一次批判性走查。
- 交互门禁：涉及页面、工作台、Agent 对话或任务流时，必须先写设计 brief、用户动线、状态模型、空态/错误态/加载态、首屏主任务和浏览器走查口径；不能再只按接口字段堆页面。

## 交互治理方法

新安装的设计和前端技能不直接替代产品判断，但必须进入 v0.7 的交互开发流程：

- Product Design brief：每个新页面、重构页面或复杂交互先确认“用户要完成什么、参考什么视觉系统、需要多少真实交互”，再开始实现。
- 前端交互准则：中台和测评端按工具型产品处理，优先工作面、状态结论、可执行动作和稳定布局，避免卡片堆叠、说明文字堆叠和无关入口抢占主路径。
- AI Elements / Chat UI 准则：涉及 Agent、对话、工具调用、推理/执行状态和 AI 文本展示时，优先采用成熟的消息流、tool call、markdown 渲染和状态呈现模式，不再手搓临时聊天界面。
- 六顶思考帽复核：交付前至少从业务方、运营、运维、能力工程师、接入开发者、平台负责人六个视角各挑一个问题，作为交互验收记录。

### P0-1 路由与错误契约硬化

目标：把最近 `Q1002 / COMFYUI_EXECUTOR_UNAVAILABLE` 暴露的“任务是否真正提交成功”问题收敛成稳定契约。

范围：

- 明确提交成功口径：HTTP 2xx、真实 `runId/taskId`、`queued/running` 状态、无 `ERR|`、无 `errorCode` 才算提交成功。
- 区分 `Q1001 / COMFYUI_QUEUE_FULL` 与 `Q1002 / COMFYUI_EXECUTOR_UNAVAILABLE`：队列满是容量拒绝，无可用执行器是路由候选为空或不可达。
- 补充路由拒绝原因：候选节点、标签匹配、节点状态、队列状态、探测失败、兼容性过滤、最终错误码。
- 更新 Coze、业务 API、测评端、管理端的错误展示和文档说明。
- 补回归测试：队列满、节点不可达、兼容候选为空、业务侧误判 `ERR|` 为成功、网络波动重试。

验收：

- 业务方无法把 `ERR|Q1002|...` 误判为成功任务。
- 管理端能看到为什么没有路由到 158/233/4090/5090。
- 每个路由拒绝都有可追溯证据，不依赖会话记忆判断。

### P0-2 全局交互治理与信息架构统一

目标：解决平台长期存在的“能用但不好用、每页局部修、没有整体交互规划”的问题。

范围：

- 建立中台/测评端统一的信息架构：能力选择、推荐版本、版本列表、辅助工具、任务状态、历史结果、质量复盘、排障证据各自有固定位置和优先级。
- 建立页面动线模板：能力首页、能力工作台、Agent 对话页、任务追踪、质量复盘、管理端能力治理页、执行节点/队列页。
- 建立状态模型：空态、加载态、执行中、排队中、成功、失败、可重试、需要追问、需要确认、不可执行。
- 建立交互验收标准：首屏主任务、下一步动作、错误可读性、结果可见性、历史可追溯、移动端基本可用、无无关入口抢占主路径。
- 对测评端和管理端做一轮角色走查，输出“全局交互问题清单”和第一批整改顺序。

验收：

- 新功能不允许再只有接口和表单，必须有用户动线和状态模型。
- 业务方第一次进入能知道选哪个能力、从哪里开始、结果在哪里、失败怎么办。
- 运维能快速看到路由、队列、节点、错误和下一步排障动作。
- 运营能看到样例、质量标签、复盘入口和默认版本切换证据。

### P0-3 Agent Runtime v2

目标：把 AI 图片助手从首个 Agent MVP 推进到可扩展 Agent Runtime 样板，为后续多能力路由和方法论流水线做准备。

范围：

- 会话状态：支持多轮上下文、当前基准图、历史结果、任务隔离、上下文压缩。
- 路由控制：LLM 可辅助识别意图，但后端必须执行白名单、schema 校验、置信度阈值、成本/风险检查和执行边界；只有低置信、高风险或高成本多阶段能力才需要人工确认。
- 能力调用：稳定当前 `business.image_edit` / `business.pattern_extract` 双白名单，其中普通自然语言图片任务默认走 GPT Image 2 质量优先路径，批量、快速、低成本或固定 SOP 才走专项加速路径；再扩展到受控能力集合。新增能力前必须先写 route schema 和 golden cases。
- 方法论预留：支持将“花纹提取 -> 裂变 -> 产品设计 -> 组图/模特/视频”拆成可审计的步骤模板，但不在中台硬编码客户端业务流程。
- 交互：聊天瀑布流、结果图片进入消息流、执行中状态清晰、新任务隔离明显、失败可重试且不污染上下文。

验收：

- Agent 七项 MVP 回归继续通过：首轮改图、二轮续改、新任务隔离、模糊意图追问、重复请求幂等、花纹提取质量优先路由、花纹提取专项加速路由。
- 新增至少一组“路由证据回归”：同一意图多次运行的 route key、confidence、base image role 和 missing fields 稳定。
- 后端保留完整审计：session、message、plan、tool call、runId、成本、错误、执行边界和必要人工确认。

### P0-4 首批能力产品化

目标：把客户端未来需要的业务组装能力转成中台能力契约，不把流程塞进中台。

范围：

- `product_design`：补固定样例、线上真实测试、效果复盘、推荐版本门槛。
- `product_image_set`：定义输入、输出、错误、成本、固定样例和是否需要组合多个底层能力。
- `model_shot`：定义模特图能力边界、输入素材要求、失败原因和质量标签。
- `promo_video`：定义视频能力边界、时长、输入资产、回调、成本和失败恢复。
- `product_commercialization`：新增产品设计后的商业化内容包 MVP，先输出产品理解卡、海外文案包、配图建议、视频分镜和可选 Veo3.1 Fast 单段商品展示视频。该能力不替代产品设计，也不在中台编排完整客户端业务流程。

产品商业化 MVP 口径：

- 文案场景先覆盖商品标题、五点描述、详情描述、广告短文案和关键词包。
- 输出语言显式支持 `en-US`、`zh-CN`、`bilingual`，默认面向海外销售使用 `en-US`。
- 配图作为 `visualAssetPlan` 输出，区分“只给建议”和“显式生成”；预览接口不隐式触发图片/视频成本动作。
- 视频先接 KIE Veo3.1 Fast 单段 5-8 秒，返回分镜、素材需求、prompt、任务 ID、OSS 视频和审核提示。
- 后续再按审核标准补多角度图、首尾帧、分段视频和合成链路。

验收：

- 每个候选能力至少有能力定义、推荐入口、错误契约、固定样例、成本估算和封版门槛。
- 是否进入实现由样例质量和业务优先级决定，不因为客户端需要就直接堆接口。
- `product_commercialization` MVP 必须通过后端契约测试、测评端手动预览、真实产品图视频生成验证和文档/错误码同步。

### P1-1 效果迭代与质量驾驶舱

目标：进入持续迭代期后，能定期看每个能力的出图效果，把“效果不好”变成可统计、可治理的问题。

范围：

- 固定样例包：按能力维护可复跑样例和输入标签。
- 质量标签：保留质量档位、问题标签、建议动作、候选 LoRA/workflow/model。
- 复盘节奏：按周或按版本查看成功率、失败原因、质量分布和候选版本表现。
- 治理动作：分流、调参、换 LoRA、换 workflow、暂停推荐、回滚默认版本。

验收：

- 能回答“哪类图效果不好、哪类图不稳定、下一步改什么”。
- 默认版本切换必须有样例对照、质量证据、影响范围和回滚方式。

### P1-2 控制面预聚合与观测

目标：把 v0.6.3 的短 TTL 和并发折叠继续演进为更稳定的后台预聚合，减少高频看板对实时明细扫描的依赖。

范围：

- 业务 usage summary、接口调用中心、能力版本指标、质量样例统计、ComfyUI 队列摘要的后台聚合。
- 指标新鲜度、最大陈旧时间、异常回退、导出实时查询边界。
- 线上观测：错误率、p95、并发、队列、数据库连接、执行节点可用性。

验收：

- 高频页面不依赖大 JSON 全量扫描。
- 聚合延迟可解释，导出和排障详情仍能获取实时或原始证据。

### P1-3 文档与客户端交接刷新

目标：持续清理冗余、陈旧和冲突文档，让中台、测评端、客户端边界长期保持一致。

范围：

- 清理旧项目主语、旧客户端资料、过期 WIP 和重复入口。
- 更新客户端交接包：只交付能力边界、业务 API、调用上下文、禁止项和验收标准。
- 每次封版同步 Changelog、测试报告、错误码、API 文档和当前 TODO。

验收：

- 新 agent 接手客户端时不会误以为中台负责业务流程组装。
- 新 agent 接手中台时不会把客户端页面或项目管理概念带回中台主线。

## 默认执行顺序

1. 先完成 P0-0，把 v0.6/v0.6.3 封口并切换当前任务入口。
2. 启动 P0-2，全局梳理测评端和管理端交互，形成页面动线、状态模型和第一批整改清单。
3. 并行设计 P0-3 的 Agent Runtime v2 schema、回归矩阵和后端控制面，但不先堆新能力。
4. 推进 P0-1，把提交成功、路由拒绝和错误契约作为 Agent/能力路由的底座继续硬化。
5. 再推进 P0-4，把首批能力缺口逐个产品化，先以样例、质量和契约判断是否实现。
6. P1 工作在 P0 稳定后持续滚动，避免质量复盘和预聚合再次变成临时补丁。
