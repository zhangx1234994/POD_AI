# v0.7 Kickoff 目标决策包

日期：2026-06-09

状态：会前规划稿。本文用于明天会议收敛下阶段目标，不等同于最终版本范围；最终 v0.7 内容以会议决策后的开工验收表和 TODO 拆分为准。

## 会议目标

明天会议要解决的不是“继续做哪些功能”，而是先确定 v0.7 的主线和边界：

- v0.7 到底解决中台的哪类核心问题。
- 哪些内容必须进入 P0，哪些只是 P1/P2 储备。
- Agent Runtime、能力产品化、交互治理、质量迭代和客户端协同之间的优先级。
- 每个方向的验收标准是什么，如何避免再次出现“做了功能但体验、文档、接口、错误契约不完整”的问题。

## 当前事实

| 维度 | 事实 |
| --- | --- |
| v0.6 状态 | 已以 `516ba656` 完成 114 线上封版验证 |
| 已跑通能力 | 花纹提取、图裂变、扩图、图编辑、产品设计、文字裂变、裂变评分、测评端 production workflow |
| 已有底座 | 能力、能力版本、业务 runId、执行节点、队列、错误码、接口调用记录、质量样例、Agent MVP |
| 暴露问题 | 页面信息密度和主路径仍需统一；Agent 还只是样板；能力产品化证据不足；质量复盘仍偏人工；文档需要持续降噪 |
| 基本边界 | 中台主语是能力，不是项目；客户端负责业务流程组装；中台负责能力封装、调用、路由、质量、成本、错误、证据和审计 |

## 推荐结论

我的建议是把 v0.7 定义为：

> 中台能力产品化与 Agent Runtime 成型版。

P0 主线建议只保留三件事：

1. 全局交互治理：把管理端和测评端从“功能堆叠”改成“能力工作台”。
2. Agent Runtime v2：把对话式改图从 MVP 做成可扩展、可审计、可回归的 Agent 样板。
3. 首批能力产品化：围绕客户端未来要调用的能力，把契约、样例、质量、错误和推荐门槛补齐。

路由与错误契约、质量观测、文档降噪作为横向门禁跟随 P0 一起做，不建议单独变成另一个大版本主题。

## 选择题

### 1. v0.7 主线选什么

| 方案 | 内容 | 优点 | 风险 | 建议 |
| --- | --- | --- | --- | --- |
| A. 继续补功能 | 继续接组图、模特图、视频等入口 | 看起来产出快 | 中台边界和体验债继续扩大 | 不建议 |
| B. 交互治理优先 | 先重构管理端/测评端信息架构 | 用户感知最直接 | Agent 和能力契约推进不足 | 可作为 P0 一部分 |
| C. Agent 优先 | 先把对话式改图做成 Agent Runtime 样板 | 长期价值高 | 若只做聊天界面会再次跑偏 | 可作为 P0 一部分 |
| D. 能力产品化优先 | 把能力版本、样例、质量、错误、推荐门槛做扎实 | 符合中台定位 | 用户短期可能感知不强 | 可作为 P0 一部分 |
| E. 三线合一 | 交互治理 + Agent Runtime + 能力产品化 | 能同时解决体验、架构和能力闭环 | 范围需要严格切片 | 推荐 |

### 2. Agent 要做多重

| 方案 | 内容 | 优点 | 风险 | 建议 |
| --- | --- | --- | --- | --- |
| 轻量聊天框 | 前端聊天 + 后端提交任务 | 快 | 很快变成一次性功能，后续会推倒 | 不建议 |
| 重型 Agent 平台 | 引入完整 Agent 平台/工作流编辑/多智能体 | 想象空间大 | 当前阶段过重，容易拖慢中台主线 | 不建议 |
| Agent Runtime v2 | 会话、上下文、路由 schema、工具白名单、审计、golden cases | 足够支撑下一阶段，又不失控 | 需要严格工程纪律 | 推荐 |

### 3. 新能力进入实现还是先定义

| 能力 | 建议口径 |
| --- | --- |
| `product_design` | 进入 P0 产品化：补固定样例、质量证据、推荐门槛和线上真实回归 |
| `product_image_set` | 先做 P0 契约定义和样例计划，是否实现看样例质量和业务优先级 |
| `model_shot` | 先做 P0 契约定义，重点明确输入素材要求、失败原因和质量标签 |
| `promo_video` | 先做 P0 契约定义，视频生成成本、时长、回调和失败恢复要先说清 |

### 4. 客户端是否进入 v0.7

建议：不进入本仓库 v0.7 实现范围。

v0.7 只输出客户端可消费的能力边界、业务 API、调用上下文、错误契约、样例和验收标准。客户端团队可以并行做端到端业务组装，但不应把客户端流程塞回中台，也不应让客户端直连原子能力或厂商接口。

## P0 候选范围

### P0-1 全局交互治理

目标：统一管理端和测评端的信息架构，让业务方、运营、运维、能力工程师、接入开发者都能快速找到主任务。

必须产出：

- 能力首页模板：推荐入口、版本列表、辅助工具、固定样例、最近运行。
- 能力工作台模板：输入、执行中、结果、历史、错误、排障。
- Agent 对话页模板：消息流、基准图、结果图、新任务隔离、执行状态。
- 管理端治理页模板：能力状态、默认版本、候选版本、质量证据、路由/队列/错误。
- 页面状态模型：空态、上传、排队、执行、成功、失败、可重试、需追问、需确认。

验收口径：

- 业务方首次进入能判断“用哪个能力、从哪里开始、结果在哪里、失败怎么办”。
- 运维能看到 runId、route key、执行节点、队列、错误码和下一步排障动作。
- 页面不再出现与当前能力无关的大面积入口抢占主路径。

### P0-2 Agent Runtime v2

目标：把对话式改图做成第一个可复用 Agent Runtime 样板。

必须产出：

- 会话模型：session、message、base image、latest output、new task、context summary。
- 路由模型：route key、confidence、missing fields、risk/cost flags、tool whitelist。
- 工具调用模型：plan JSON、schema validation、idempotency key、runId、audit log。
- 执行策略：普通单张自然语言图片任务优先 GPT Image 2；批量、快速、低成本或固定 SOP 才走专项能力。
- 回归矩阵：首轮改图、二轮续改、新任务隔离、模糊意图追问、重复请求幂等、质量优先路由、专项加速路由。

验收口径：

- 结果图片必须进入聊天瀑布流。
- 二轮修改默认基于上一轮成功结果，而不是回到原图。
- 新任务必须明确隔离，不污染旧上下文。
- 后端必须保留完整路由证据和工具调用审计。

### P0-3 首批能力产品化

目标：把“能调用”升级为“可推荐、可复盘、可迭代、可对外接入”。

必须产出：

- 每个核心能力的输入输出契约、错误契约、固定样例、质量标签、成本估算、默认版本门槛。
- `product_design` 的线上真实样例和推荐版本证据。
- `product_image_set`、`model_shot`、`promo_video` 的能力定义和样例计划。
- 默认版本切换规则：必须有样例对照、质量证据、影响范围和回滚方式。

验收口径：

- 每个 P0 能力至少 5 个真实案例或明确说明为什么本阶段只定义不实现。
- 能回答“这个能力现在是否可推荐、为什么可推荐、失败怎么办、成本大概多少”。

### P0-4 路由与错误契约硬化

目标：把提交成功、队列满、执行器不可用、供应商失败、网络波动等判断固化成统一契约。

必须产出：

- 提交成功口径：HTTP 2xx + 真实 runId/taskId + queued/running + 无 `ERR|` + 无 `errorCode`。
- `Q1001` 队列满和 `Q1002` 执行器不可用的页面提示、接口文档和业务方判断规则。
- 路由拒绝证据：候选节点、标签、节点状态、队列、探测、兼容过滤、最终错误码。
- Coze、自有业务 API、测评端、管理端一致的错误表达。

验收口径：

- 业务方不能再把 `ERR|Q1002|...` 误判为提交成功。
- 管理端能解释为什么任务没有路由到某台执行机。

## P1 候选范围

| 方向 | 说明 |
| --- | --- |
| 质量驾驶舱 | 固定样例复跑、质量标签、问题分布、候选版本对照、默认版本切换证据 |

## 非目标

- 不做项目管理系统。
- 不在中台实现客户端业务流程组装。
- 不让客户端直连 ComfyUI、OpenAI、KIE、火山、百度等厂商或原子能力。
- 不把对话式改图做成普通图编辑表单。
- 不引入重型通用 Agent 平台。
- 不把所有未来能力一次塞进 v0.7。
- 不上线真实支付、自动开票或正式商业套餐。
