## 关键结论

1. 两个新裂变版本都不依赖 Coze 工作流，主入口是中台业务 API：`POST /api/business/fission/runs`。
2. 业务接口排队机制和旧 Coze 工具箱机制在业务形态上一致：都是“提交任务 -> 返回 ID -> 轮询结果”。
3. 字段口径不同：旧 Coze 使用 `taskId/taskStatus`，中台业务 API 使用 `runId/status`。
4. 为兼容旧链路，`/api/coze/podi/tasks/get` 支持把业务 `runId` 填入 `taskId` 查询。
5. `bili` 统一定义为“裂变幅度 / 重绘幅度”，不是“相似度”；数值越大，变化越明显。
6. “新版”只能作为角标或测试状态，不能作为功能名称；功能名称必须能被业务方直接理解。
7. 今天的交付暴露出文档沉淀不足、测试闭环不够早、前端展示和接口文档没有同步到位的问题，后续必须按清单闭环。

### 能力交付准则

新增一个面向业务方的能力，不能只完成后端接口。最低交付清单：

1. 后端接口可提交和轮询。
2. 测评端能直接看到并测试。
3. 管理端能看到调用记录和链路证据。
4. 接口文档包含请求、响应、错误、参数说明。
5. JSON 请求/响应样例完整，且参数必填/可选写清楚。
6. 交付包不包含入库密钥，不把真实 Key 写进 Git。
7. 命名使用业务语言，不使用内部代号当主名称。

### 参数沉淀准则

凡是涉及聚合、映射、别名、默认值的参数，都必须写入契约文档。

本次已固定：

- `imageUrl` / `url`：原图地址别名。
- `maskUrl` / `mask_url`：蒙版地址别名。
- `bili`：裂变幅度 / 重绘幅度。
- `width/height`：ComfyUI 版本输出宽高。
- `size`：GPT Image 2 版本尺寸预设。
- `prompt`：可选，系统提示词和 VL 可兜底。
- `inputs`：扩展参数容器，优先级高于顶层参数自动复制。

### 轮询准则

- 业务方默认使用 `runId` 和 `/api/business/runs/get`。
- 旧 Coze 或旧业务不想改轮询逻辑时，可以用 `/api/coze/podi/tasks/get` 查询 `runId`。
- 底层能力 `taskId` 只给排障，不作为业务方必须理解的概念。
- 新业务能力尽量统一到业务 `runId` 模式，避免继续扩散多套轮询口径。
